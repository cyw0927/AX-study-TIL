# 1. Chapter 10 — 주문 취소 여부 분류

오늘 Chapter 10에서는 주문 데이터를 이용해 주문이 완료될지 취소될지를 분류하는 과제를 진행했다.

타깃은 다음처럼 정의했다.

- completed = 0
- cancelled = 1

주문 생성 직후 취소 여부를 예측하는 상황을 가정했기 때문에, 주문이 끝난 뒤에만 알 수 있는 정보나 원본 식별자는 Feature에서 제외했다.

과제에서는 단순히 모델을 만드는 것보다 다음 순서가 중요했다.

1. 데이터 확인
2. Feature 구성
3. Train / Validation / Test 분리
4. Baseline 학습
5. Validation에서 Threshold 선택
6. Final Test 평가
7. 실제 운영 가능 여부 판단

# 2. 실제 데이터 규모와 클래스 분포

최종 분석에는 총 248건이 사용됐다.

- completed: 184건
- cancelled: 64건
- 전체: 248건

취소 건수가 완료 건수보다 적기 때문에 단순 Accuracy만 보고 판단하면 안 됐다.

취소 주문을 얼마나 놓치지 않는지가 중요한 문제이므로 Recall과 F1-score를 같이 확인했다.

# 3. Logistic Regression과 Threshold

Baseline 모델로 Logistic Regression을 사용했다.

일반적인 이진 분류 기본 Threshold는 0.5이지만, 이번 과제에서는 Validation 결과를 보고 Threshold를 조정했다.

**최종 Threshold = 0.20**

Threshold를 낮추면 취소 가능성이 조금만 있어도 취소로 분류하기 때문에 Recall을 높일 수 있다.

하지만 그만큼 정상 주문을 취소로 잘못 판단하는 False Positive도 증가한다.

# 4. Final Test 결과

최종 Test 결과:

- Accuracy: 0.280
- Recall: 0.846
- F1-score: 0.379

Confusion Matrix:

- TN = 3
- FP = 34
- FN = 2
- TP = 11

취소 주문 13건 중 11건을 잡아서 Recall은 높았다.

하지만 정상 주문을 취소라고 잘못 판단한 FP가 34건이나 발생했다.

즉 취소를 놓치지 않는 능력은 높지만 정상 주문 오탐이 너무 많았다.

자동 Validation 기준은 통과했지만 실제 서비스에 바로 적용하기에는 성능이 부족하다고 판단했다.

**최종 운영 판단: 현재 사용 보류**

# 5. Validation PASS와 운영 적합성은 다르다

오늘 Chapter 10에서 가장 중요했던 점이다.

코드가 정상 실행되고 자동 검증을 통과했다고 해서 모델을 바로 서비스에 사용할 수 있는 것은 아니다.

**코드 실행 성공 ≠ 모델 운영 가능**

이번 모델은 Recall이 높지만 False Positive가 너무 많았다.

따라서 기술적으로 과제가 완료됐다는 것과 실제 업무에서 쓸 만한 모델이라는 것은 별도로 판단해야 한다.

# 6. 데이터 품질 문제 — 날짜 순서 오류

데이터를 확인하는 과정에서 signup_date가 order_date보다 늦은 데이터가 45건 발견됐다.

이런 상태에서 가입 후 경과 일수 같은 Feature를 그대로 계산하면 음수가 생길 수 있다.

잘못된 값을 억지로 정상 데이터처럼 사용하지 않고, 해당 파생 Feature를 결측 처리하는 방식으로 수정했다.

여기서 배운 점은 모델 문제처럼 보이는 오류도 실제로는 원본 데이터 품질 문제일 수 있다는 것이다.

모델 학습 전에 날짜·범위·관계 검증을 먼저 해야 한다.

# 7. Chapter 11 — LLM과 분석 질문 다듬기

Chapter 11에서는 LLM에게 데이터를 그대로 던져 분석시키는 것이 아니라, 안전하게 제공할 Context를 먼저 정의하고 LLM의 답을 실제 데이터 근거로 다시 검증하는 과제를 진행했다.

사용한 processed 데이터 규모:

- customers: 150행
- products: 100행
- orders: 300행
- order_items: 764행

Notebook은 총 8개 실행 단계가 있었고 8/8 실행, 오류 0으로 완료했다.

# 8. Safe Context

LLM에게 모든 데이터를 그대로 전달하지 않고 분석에 필요한 정보만 제공했다.

Safe Context에는 다음과 같은 정보를 넣었다.

- 분석 질문
- 실제 컬럼 구조
- 분석 범위
- PK / FK 검증 결과
- 병합 전후 행 수
- 익명 집계 결과
- 합계 일치 여부

반대로 원본 행 전체, 직접 식별자, Secret, 불필요한 개인정보는 넣지 않았다.

Safe Context Validation은 모든 항목이 PASS했다.

# 9. Prompt Contract

LLM에게 단순히 "이 데이터 분석해줘"라고 요청하는 대신 Prompt 자체에 분석 규칙을 명확하게 적었다.

주요 조건:

- 역할
- 목적
- 사용할 Context
- 계산 기준
- 출력 형식
- 금지 사항
- 검증 조건

계산 기준에는 다음 내용을 명시했다.

- order_status == completed만 집계
- line_total = quantity × unit_price
- 유효한 order_date만 사용
- 실제 데이터에 없는 원인을 만들어내지 않기
- 원본 고객 행이나 직접 식별정보 사용 금지

Prompt에 계약처럼 명확한 조건을 넣으면 LLM이 임의로 해석할 범위를 줄일 수 있다.

# 10. Evidence Matrix

LLM이 제안한 내용을 그대로 정답으로 사용하지 않고 실제 데이터로 다시 확인했다.

주요 검증 항목:

- 필수 컬럼 존재 여부
- line_total 계산 일치 여부
- product 병합 미매칭 여부
- source total과 group total 일치 여부

실제 검증에서는 line_total 불일치 0건, product 미매칭 0건을 확인했고 집계 합계도 일치했다.

반면 데이터만으로 증명할 수 없는 인과관계는 사실처럼 작성하지 않고 보류했다.

즉 LLM의 역할은 분석 후보를 제시하는 것이고 최종 판단은 Evidence로 확인해야 한다.

# 16. 현재 Codex 오류 가설

현재까지 확인한 내용은 다음과 같다.

- Codex 상태 DB 존재
- 프로젝트 미러 존재
- 상태 파일 계속 갱신
- 실제 작업 파일 존재

따라서 전체 설치가 완전히 망가진 것보다는 프로젝트를 앱과 연결하는 매핑 또는 잠금 상태가 꼬였을 가능성을 먼저 의심했다.

현재 우선순위 가설:

1. 프로젝트 metadata / mapping / routing 문제
2. stale metadata lock 또는 helper process 잠금 문제

아직 삭제나 초기화는 하지 않았다.

문제가 발생했을 때 가장 먼저 데이터를 지우는 대신 증상 확인 → 상태 파일 확인 → 프로세스/잠금 확인 → 원인 범위 좁히기 → 필요한 최소 조치 순서로 접근하는 것이 안전하다.

# 17. 오늘의 핵심 정리

- 분류 문제에서는 Accuracy 하나만 보면 안 된다.
- Threshold를 낮추면 Recall을 높일 수 있지만 False Positive가 늘 수 있다.
- 자동 Validation PASS와 실제 운영 가능 여부는 별개다.
- 원본 데이터 품질 문제를 모델 문제로 착각하지 않아야 한다.
- LLM에는 원본 데이터를 무조건 전달하지 않고 Safe Context를 구성할 수 있다.
- Prompt에는 역할·목적·계산 규칙·출력·검증 조건을 명확히 적는 것이 좋다.
- LLM의 제안은 Evidence Matrix로 다시 검증해야 한다.
- 데이터가 증명하지 못하는 인과관계는 LLM이 말해도 사실로 쓰면 안 된다.
- 개발 도구 오류도 바로 초기화하기보다 상태 파일과 로그를 먼저 확인하는 것이 안전하다.
- 프로젝트 파일이 살아 있는 것과 앱의 프로젝트 매핑이 정상인 것은 서로 다른 문제다.
