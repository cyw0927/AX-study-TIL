# 1. Chapter 14-1 자동화 과제

오늘 데이터 분석 수업에서는 관광 데이터를 자동 수집하고 분석 결과를 보고서로 만드는 파이프라인을 구성했다.

전체 흐름:

```text
NAVER 검색 관심도 수집
→ 관광공사 체류 강도 수집
→ 관광공사 소비 강도 수집
→ Python 분석
→ Gemini 요약
→ PDF 생성
→ 로그 기록
```

각 단계가 실패하면 다음 단계로 넘어가지 않는 fail-fast 방식으로 구성했다.

# 2. fail-fast 실행 구조

run_pipeline.py에서 각 스크립트를 순서대로 실행하도록 만들었다.

실행 순서:

```text
collect_naver.py
collect_tourism.py
analyze.py
generate_llm_report.py
generate_pdf.py
```

중간 단계가 실패하면 즉시 종료하고 로그에 실패 지점을 남기도록 했다.

자동화에서는 결과 파일이 일부 생성됐다는 이유만으로 성공이라고 판단하면 안 되고, 어느 단계까지 정상 실행됐는지 명확하게 남기는 것이 중요하다.

# 3. 관광공사 API 실제 사양 검증

처음에는 관광 API endpoint와 응답 필드가 비어 있는 상태였지만 실제 Swagger 응답을 기준으로 체류 강도와 소비 강도 API를 설정했다.

주요 endpoint:

- 지역별 관광 체류 강도
- 지역별 관광 소비 강도

서울 기준으로 각각 26건의 응답을 확인했다.

응답에서는 다음 항목을 사용했다.

- 기준월
- 시도명
- 시군구명
- 체류/소비 강도 값

특히 signguNm이 '_'인 행은 개별 시군구가 아니라 서울 전체 집계 행이므로 별도로 구분했다.

# 4. 지역 데이터 분석 방식

관광 데이터에서는 서울 전체 집계와 시군구 데이터를 분리했다.

시군구 데이터만 대상으로 최신 기준월의 강도 상위 10개 지역을 추출하고 그래프로 만들었다.

분석 과정에서 확인한 원칙:

- 시도 전체와 시군구 데이터를 섞지 않기
- 지역·기간 중복 검증
- 결측값 확인
- 숫자형 변환 확인
- 최신 기준월만 비교

단순히 API 응답이 200이라는 것보다 실제 데이터 구조가 분석 가능한 상태인지 검증하는 과정이 더 중요했다.

# 5. NAVER 검색 관심도와 관광 데이터의 차이

NAVER 검색 데이터의 ratio는 실제 검색 건수가 아니라 0~100 범위의 상대 관심도다.

반면 관광공사 데이터는 지역별 체류·소비 강도 지표다.

따라서 두 데이터를 같은 숫자처럼 직접 비교하거나 행 단위로 merge하지 않았다.

대신 각각 따로 분석한 뒤 하나의 보고서 안에서 함께 해석하도록 구성했다.

```text
NAVER Search Trend
= 검색 관심도

Tourism API
= 지역 관광 체류/소비 강도

직접 숫자 비교 X
별도 분석 후 패턴 설명 O
```

# 7. Gemini 보고서 생성

Python에서 계산한 검증된 결과만 Gemini에 전달해 한국어 분석 요약을 생성했다.

LLM에게 맡긴 것은 숫자 계산이 아니라 서술 정리다.

프롬프트에는 다음 제약을 넣었다.

- NAVER ratio를 실제 검색 건수라고 쓰지 않기
- 관광지표와 NAVER ratio를 직접 비교하지 않기
- 없는 숫자·지역·날짜를 만들지 않기
- 인과관계를 임의로 단정하지 않기
- 데이터 출처와 한계를 명시하기

즉 계산은 Python이 하고, LLM은 검증된 결과를 설명하는 역할로 제한했다.

# 8. Gemini API 오류 재시도

LLM API는 일시적으로 429 또는 503 오류가 발생할 수 있다.

그래서 무조건 한 번 실패했다고 전체 파이프라인을 끝내기보다, 일시 오류인 경우에만 최대 5번까지 재시도하도록 수정했다.

재시도 간격도 점차 늘어나도록 했다.

반대로 인증 오류나 다른 종류의 오류는 숨기지 않고 바로 실패하도록 했다.

자동화에서는 모든 오류를 재시도하는 것이 아니라 재시도해도 되는 오류와 즉시 중단해야 하는 오류를 구분해야 한다.

# 9. Markdown → PDF

# 11. Make 자동화용 API 사양 정리

로컬 Python 자동화와 별도로 Make 실습에서 사용할 관광 API 호출 조건도 문서화했다.

HTTP 모듈에서 체류 강도와 소비 강도를 각각 별도 호출하고, serviceKey는 문서나 스크린샷에 직접 노출하지 않도록 정리했다.

Make에서도 단순 HTTP 200만 확인하는 것이 아니라 응답 안에 실제 지역·기준월·강도 값이 있는지 확인해야 한다.

# 13. 번역과 윤문은 다른 작업

이미 번역이 끝났다고 해서 읽기 좋은 문장이 자동으로 완성되는 것은 아니다.

윤문에서는 다음을 다시 확인하게 된다.

- 문장 흐름
- 어색한 직역 표현
- 반복되는 표현
- 대화와 서술의 자연스러움
- 인용부호와 문장부호
- 원문의 의미를 유지하면서 한국어 가독성 확보

오늘 《삼총사》는 번역 완료 상태에서 한 단계 더 나아가 전권 윤문까지 완료한 상태가 됐다.
