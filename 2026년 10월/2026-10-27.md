## 1. v0.3 — 예측 확률 보정과 가설 검증

어제 구현한 v0.2 실데이터 MVP에서는 단순 과거 상승비율(B1)과 모멘텀(B2), 로지스틱 회귀, HistGradientBoosting, LightGBM을 비교했다.

오늘 v0.3에서는 기존 머신러닝 모델들의 **과도한 확신(overconfidence)**을 줄이기 위해 Platt 보정과 확률 축소(shrinkage)를 추가했다. 경제적 해석이 가능한 네 가설도 별도로 사전 등록해 시험했다.

- H1: 추세
- H2: 변동성 레짐
- H3: 금리 레짐
- H4: 단기 반전

이 과정에서 기존 v0.2 모델 성과가 다시 정확하게 재현되는지도 확인했다. 기존 지표 180행은 동일하게 유지됐다.

## 2. 통계적 유의성을 별도로 판단

후보 모델의 Brier 점수가 기준모델보다 낮다고 해서 실제 예측력이 검증됐다고 할 수 없다.

오늘의 비교 구조는 다음과 같다.

```text
9개 자산
× 2개 기간(5봉 / 20봉)
× 기준모델 B1을 제외한 14개 후보
= 252개 비교
```

같은 기간의 예측 오차 차이를 Newey–West HAC로 검정하고, 다수 후보를 동시에 살펴보면서 생기는 우연한 발견을 줄이기 위해 BH-FDR(q=0.10)을 적용했다.

실제 v0.3 결과:

| 검증 항목 | 결과 |
| --- | ---: |
| 홀드아웃 Brier가 B1보다 좋은 조합 | 103 / 252 |
| 다중비교 보정 전 p값 0.05 미만 | 4개 |
| BH-FDR 통과 | **0개** |
| 사전 등록 기준에서 지지된 후보 | **0개** |

즉 일부 후보가 특정 구간에서 더 좋은 숫자를 보였지만, **기준모델보다 우수하다는 충분한 증거는 확보하지 못했다.** 이 결과를 성능 향상으로 포장하지 않고 그대로 문서화했다.

## 3. 기존 홀드아웃을 반복해서 보면 생기는 문제

v0.2와 v0.3에서 이미 최근 2년 홀드아웃 성적을 확인했다. 이 결과를 계속 보면서 후보를 추가하면 모델이 실제 미래를 잘 맞히는 것이 아니라 **이미 본 데이터에 맞춰지는 선택 편향**이 발생할 수 있다.

따라서 새로운 후보의 성능은 과거 데이터를 다시 돌려 확인하는 방식만으로 주장하지 않고, **2026년 10월 27일 이후 실제로 발행한 예측을 미래 결과가 나온 뒤 평가**하는 방식으로 바꾸기로 했다.

## 5. Append-only SQLite 예측 장부

v0.4에서는 예측을 발행할 때 다음 데이터를 로컬 SQLite에 저장하도록 구현했다.

```text
예측 기준일
자산
예측 기간
모델
상승 확률
UTC 기록 시각
Git 커밋 SHA
실행 ID
기준 가격
통화
```

장부 위치:

```text
data/ledger/forward.sqlite3
```

고유 키는 `(forecast_date, asset, horizon, model)`이다. 같은 예측을 다시 실행해도 처음 기록된 확률을 수정하지 않고 중복 삽입을 막는다.

예측 이후 실제 가격을 알게 됐다는 이유로 과거 확률을 바꿀 수 없어야 정직한 전진 검증이 가능하다. 장부는 개인 로컬 데이터이므로 공개 GitHub에는 올리지 않는다.

## 6. 없는 값은 만들어내지 않기

모든 자산에서 모든 후보 모델을 반드시 실행할 수 있는 것은 아니다. 예를 들어 특정 금리 데이터가 없어 H3 후보를 사용할 수 없다면 그 후보의 확률을 임의로 생성하지 않는다.

실제로 계산한 사용 가능한 후보만 기록하며, 결측은 결측으로 남긴다. 이 동작도 별도 테스트로 확인하도록 했다.

## 7. 만기 후에만 채점

전진 검증의 핵심은 **예측 당시 알 수 없었던 결과가 실제로 나온 다음에만 평가하는 것**이다.

```text
예측 발행
→ 최초 기록 고정
→ 해당 자산의 5봉 또는 20봉 경과
→ 마지막 봉의 마감(+15분) 확인
→ 만기 이후 새로 수집한 실제 원자료 확인
→ 정답과 수익률 기록
→ B1과 후보 모델 비교
```

BTC는 달력일을 사용하고 주식·ETF·환율 등은 각 자산의 거래일 및 시장별 완료 시각을 고려한다.

다음 항목은 채점하지 않도록 구현했다.

- 결과 만기 전에 기록된 가격이 아직 없는 경우
- 만기 봉이 아직 끝나지 않은 경우
- 예측 기록 시각이 결과 만기보다 늦은 사후 예측
- 만기 이후 새로 수집한 원자료가 없는 경우
- 잘못된 기준가나 결측 데이터

채점값 역시 최초 결과를 보존하고 추후 공급자 데이터 수정으로 임의로 덮어쓰지 않는다.

## 8. 전진 검증의 최소 표본 규칙

새 예측이 몇 건 쌓였다고 바로 유의성을 평가하지 않는다.

```text
같은 날짜의 B1–후보 유효 쌍 ≥ 500
그리고 관측 기간 ≥ 540일
```

두 조건을 모두 충족해야 사전 등록된 통계 검정을 수행한다. 부족한 조합은 **표본 부족**으로 표시하며 252개 비교 모집단에서 임의로 제거하지 않는다.

따라서 v0.4 코드를 만들었다고 곧바로 예측 성능이 입증된 것은 아니다.

## 9. 새 채점 명령과 대시보드

만기가 된 예측을 별도로 채점하는 `scripts/score_ledger.py`를 추가했다.


실제로는 첫 예측 발행과 새로운 가격 데이터 수집 사이에 충분한 시간이 흘러야 한다.

Streamlit에는 전진 검증 장부 화면을 추가해 예측 수, 만기 채점 수, Brier, 유효 표본 부족 여부, 지지된 모델 수를 확인할 수 있도록 했다.

## 오늘의 핵심 정리

**백테스트에서 좋아 보이는 숫자와 미래에 실제로 맞히는 능력은 다르다.** 과거 홀드아웃을 반복해서 보고 조정하면 실험의 독립성이 약해진다.

그래서 미래 예측을 실제 발행 시점에 고정하고, 그다음에 관측된 결과만으로 채점하는 장부가 필요하다. 검정 조건을 구현 전에 고정하는 것도 중요하다.

결과가 좋지 않을 때 숨기지 않는 것이 분석 시스템의 신뢰성에 더 중요하다.

## 오늘의 회고

어제 GMIA가 실제 시장 데이터를 학습하고 대시보드에서 결과를 보여주는 단계로 발전했다면, 오늘은 **그 예측이 미래에도 통하는지를 정직하게 검사할 장치**를 만든 날이었다.

v0.3에서 252개 비교 중 지지된 후보가 없었다는 사실은 실망스러울 수 있지만, 오히려 모델이 무엇을 아직 증명하지 못했는지 명확하게 보여준다.

오늘 추가한 v0.4 장부는 곧바로 성능을 높여 주는 기능이 아니다. 앞으로 발행할 예측과 실제 결과를 변경할 수 없는 기록으로 쌓아 두고, 충분한 시간이 지난 뒤 기준모델과 비교하기 위한 기반이다.

코드와 CI까지는 확인했지만 실데이터 실행·채점·배포는 앞으로 진행해야 할 일로 남겨두었다.
