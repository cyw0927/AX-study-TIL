# 1. 프로모션 배너를 실제 페이지로 연결

기존 홈 화면에는 오픈런 쿠폰, 첫 구매, 신선 배송, 김장 쿠폰, 가족 김장체험 배너가 있었지만 처음에는 각각 단순 상품 목록이나 다른 화면으로 이동하는 정도였다.

오늘은 각 배너가 전용 프로모션 상세 화면으로 이동하도록 구조를 바꿨다.

예:

- 오픈런 쿠폰 → /promotions/openrun-coupon
- 첫 구매 혜택 → /promotions/first-box
- 신선 배송 → /promotions/fresh-delivery
- 김장 쿠폰 → /promotions/kimjang-coupon
- 가족 김장체험 → /promotions/family-kimjang

즉 배너가 단순 홍보 이미지가 아니라 실제 정보 흐름의 시작점이 되도록 만들었다.

# 2. 프로모션 상세 화면 구성

프로모션 페이지에서는 단순 설명만 보여주지 않고 다음 요소를 함께 제공하도록 구성했다.

- 행사 이미지
- 혜택 조건
- 관련 상품
- 이용 안내
- 페이지 내 이동
- 개별 메타데이터

컬리의 혜택 페이지처럼 행사 이미지 → 조건 → 상품 → 이용 안내 순서를 참고했지만, 이미지와 문구는 그대로 복제하지 않고 기존 못난이마켓 디자인과 테라코타 계열 스타일을 유지했다.

# 3. 프로모션 조건을 명확하게 정의

오늘 구현하면서 행사 조건도 구체적으로 정리했다.

예:

- 오픈런: 2만 원 이상 구매 시 2천 원 할인
- 첫 구매: 3만 원 이상 10% 할인, 최대 5천 원
- 김장 쿠폰: 배추·무·양파 4만 원 이상 15% 할인
- 가족 김장체험: 지정 토요일 일정과 참가비
- 배송: 2만 원 이상 무료, 미만 3,500원

프로모션 기능은 화면만 예쁘게 만드는 것보다 조건을 명확히 데이터로 정의하는 것이 중요했다.

# 4. 배너 전환 속도 조정

메인 배너 자동 전환 간격을 3초로 조정했다.

배너는 자동 전환뿐 아니라 다음 동작도 같이 고려했다.

- 페이드 전환
- 일시정지
- 마우스 호버
- 키보드 포커스
- 동작 줄이기 설정

자동 UI는 단순히 시간이 지나면 바뀌게 만드는 것보다 사용자가 제어할 수 있어야 한다.

# 5. 네비게이션에 혜택 메뉴 추가

프로모션 페이지를 만들고 끝내지 않고 데스크톱과 모바일 메뉴에서도 접근할 수 있도록 혜택 메뉴를 추가했다.

기존 흐름:

상품 / 레시피 / 농가 이야기

변경 후:

상품 / 레시피 / 농가 이야기 / 혜택과 이야기

새 기능을 만들었으면 사용자가 실제로 찾을 수 있는 진입점까지 연결해야 기능이 완성된다는 점을 확인했다.

# 6. 실제 쿠폰 발급과 쿠폰함

오늘은 화면용 프로모션 설명을 넘어 실제 계정 소유 쿠폰 기능도 연결했다.

핵심 흐름:

프로모션
→ 로그인 사용자에게 쿠폰 발급
→ 사용자 계정에 쿠폰 보관
→ 장바구니에서 보유 쿠폰 확인

기존처럼 별도 혜택 버튼만 보여주는 방식보다 사용자가 실제로 발급받은 쿠폰을 장바구니에서 확인할 수 있게 만드는 쪽으로 바꿨다.

이 작업을 통해 프로모션과 주문 흐름이 실제로 연결되기 시작했다.

# 7. 배송 배너 문구 개선

배송 배너는 오늘 여러 번 수정했다.

초기에는 기능 설명에 가까운 문구였지만 점차 쇼핑몰 브랜드 문구처럼 다듬었다.

예:

15시 전에 주문하면 오늘 자정 전 도착!

에서

오늘 고른 신선함, 오늘 밤 우리 집으로.

처럼 메인 메시지를 바꾸고, 실제 조건은 보조 문구로 분리했다.

브랜드 문구와 기능 설명을 한 문장에 모두 넣기보다 역할을 나누는 것이 화면 가독성에 더 좋았다.

# 8. 배너 디자인 반복 개선

배송 배너는 문구뿐 아니라 사진, 그라데이션, 텍스트 크기, 버튼 스타일도 반복해서 수정했다.

특히 사진 느낌이 너무 사라지지 않도록 배경 이미지를 살리고, 텍스트가 읽히는 범위에서 그라데이션을 조절했다.

혜택 목록 카드에서도 같은 배너 톤을 재사용해 홈과 상세 화면의 느낌을 맞추려 했다.

UI 작업은 한 번에 완성되는 것이 아니라 실제 화면을 보면서 계속 조정하는 과정이라는 점을 다시 느꼈다.

# 9. 팀원 작업 덮어쓰기 문제 복구

배너를 수정하는 과정에서 팀원이 PR #79에서 반영한 배송 배너 변경사항 일부를 내 후속 수정이 덮어쓴 문제가 있었다.

이를 확인한 뒤 팀원 변경사항을 다시 복구했다.

이 과정에서 배운 점:

- 최신 main 기준으로 작업하기
- 같은 파일을 여러 명이 수정할 때 변경 범위를 확인하기
- 내 디자인 개선이 팀원 기능을 삭제하지 않았는지 diff로 검토하기
- 문제가 생기면 내 버전을 고집하기보다 기존 팀원 작업을 복원하기

협업에서는 코드가 동작하는 것만큼 다른 사람의 변경 이력을 보존하는 것도 중요하다.

# 10. README 최신화

프로젝트 README가 초기 개발 상태를 기준으로 너무 길고 오래된 내용을 많이 포함하고 있어서 현재 상태에 맞게 다시 정리했다.

현재 README에는 다음 내용을 중심으로 남겼다.

- 프로젝트 소개
- 배포 사이트
- 팀 구성
- 현재 구현 상태
- 주요 기능
- 기술 스택
- 작업 요약 문서
- Notion / Redmine / 발표 자료 링크

초기에는 미완료라고 적혀 있던 로그인, 장바구니, 주문, 배포 기능 등이 실제 구현된 상태에 맞게 수정됐다.

# 11. 문서는 현재 상태를 보여줘야 한다

README는 단순 개발 계획서가 아니라 지금 프로젝트가 어디까지 왔는지 보여주는 문서다.

초기 계획과 현재 구현 상태가 많이 달라졌는데도 예전 내용을 그대로 두면 새로 들어온 사람이 프로젝트를 잘못 이해할 수 있다.

그래서 오늘은 오래된 계획 설명을 줄이고 실제 구현된 기능과 바로가기 중심으로 재구성했다.
