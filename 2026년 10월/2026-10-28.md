## 2. GMIA 구조를 다시 설계한 이유

GMIA는 단순히 금융 시계열 몇 개를 가져와 머신러닝으로 상승확률을 구하는 데서 끝나는 프로젝트가 아니다.

앞으로 함께 다뤄야 하는 범위:

- 세계 각국의 거시경제 지표와 발표 시점
- 주식·채권·금리·환율·원자재·가상자산
- 기업별 실적·PER·PBR 등 가치평가
- 국제정세·정책·공급망의 경제적 파급경로
- 자산 간 상관관계 변화와 시나리오 예측
- 공식 자료 검증과 뉴스 출처 관리
- 예측 결과 사전 기록·사후 채점·오류 분석
- 장기간 데이터 수집과 서버·대시보드 운영

오늘은 기존 프로젝트의 아키텍처가 이 목표에 비해 너무 단순하다고 보고, 지금까지의 코드·문서·남은 문제를 종합적으로 검토할 수 있는 상세 작업 명세를 정리했다.

## 3. 후속 아키텍처 PR과 main 병합 상태

기존 GMIA 코드의 데이터 저장 방식에서는 Parquet 원본과 메타 파일이 별도로 갱신될 때 서로 다른 시점의 파일이 섞일 위험이 있었다.

또 최초 예측만 보존한다는 규칙을 코드 호출 관례에만 의존하면, 다른 경로에서 데이터를 수정할 여지가 있었다.

후속 변경에서는 다음 방식을 다뤘다.

- 데이터와 메타를 불변 스냅샷으로 보존
- SHA-256 manifest로 입력 무결성 검사
- 현재 수집본을 가리키는 포인터와 특정 수집본 재현
- 실행 시 사용한 코드·데이터의 해시 기록
- SQLite 예측·채점 데이터의 일반적인 수정·삭제 차단
- 덮어쓰지 않는 온라인 백업 및 무결성 검사
- 데이터 이용 자격, 발표 시점과 수집 시점을 분리하는 계약

관련 PR:

- [#9](https://github.com/cyw0927/etc/pull/9): 기존 기능 브랜치에 병합
- [#10](https://github.com/cyw0927/etc/pull/10): 위 변경을 `main`에 반영하기 위한 후속 PR, **오늘 확인 시점 open**

따라서 #9가 병합됐다는 사실과 #10의 변경이 이미 `main`에 들어왔다는 주장은 다르다.

## 4. 실데이터 재현성과 예측 장부 검증

후속 아키텍처 PR 기록에서는 다음 결과를 확인했다.

```text
Yahoo Finance 시장 시계열: 10개
FRED 금리·거시 시계열: 7개
총 수집 성공: 17개
예측 출력: 18개
최초 전진검증 장부 기록: 270행
만기 채점: 0행
```

예측 270행은 18개 자산·기간 조합에 여러 후보 확률을 기록한 것이다. **270번의 예측 성공이나 270건의 사후 적중을 의미하지 않는다.**

깨끗한 작업트리에서 재실행했을 때 동일한 예측 결과가 재현되고 기존 장부 270행을 중복 삽입하지 않는지 검사한 기록도 남겼다.

CI는 Ubuntu·Windows 환경에서 코드·테스트·타입검사를 진행했다. 일부 시점에 실패한 실행도 있었지만 이후 수정된 실행은 성공했다.

## 5. v0.5 — 시점 검증을 통과한 기준 예측부터 분리

기존의 예측 파이프라인이 모든 데이터 공급원의 시점·시장 규칙을 완전히 입증한 것은 아니었다.

그래서 후속 연구에서는 우선 조건이 확인된 일부 자산에 대해 **독립적인 기준 예측 장부**를 만들고, 불확실한 공급원은 억지로 통과시키지 않는 접근을 택했다.

[GMIA PR #11](https://github.com/cyw0927/etc/pull/11)의 기록:

- 거래소 일정과 마감 시각 확인
- 실제 데이터 수집·발행 시각 구분
- 스냅샷 해시 검증
- 5개 적격 자산 × 5·20거래일 = 기준 예측 10개 기록
- BTC·FX·WTI의 봉·롤 정의가 확인되기 전까지 별도 발행 차단
- 로컬 테스트 59개 통과

**이 10개 기록은 연구용 기준 예측이며 기존 15개 모델의 성능을 개선했다고 주장할 수 없다.** PR도 오늘 확인 시점에는 미병합 상태다.

## 6. 예측 만기 계산을 독립적으로 검증

[GMIA PR #12](https://github.com/cyw0927/etc/pull/12)에서는 기준 예측의 만기를 거래소 일정에 맞춰 계산하고, 실제 결과가 나온 뒤에만 점수를 부여하는 기능을 분리했다.

핵심 조건:

```text
기준 시점의 예측 발행
→ 5봉 또는 20봉 실제 완료
→ 기준 가격·결측·수집 시점 검증
→ 첫 결과만 독립 장부에 기록
```

기존 예측 장부는 읽기 전용으로 두고 결과를 소급 수정하지 않는다.

로컬 테스트 65개는 통과했지만, 실제 10개 예측은 아직 만기가 도래하지 않아 **실제 만기 채점 성공은 확인되지 않았다.**

## 8. 실제 데이터가 있어도 즉시 운영 가능한 것은 아님

이번에 반복해서 확인한 원칙은 다음과 같다.

```text
API 응답 성공
≠ 데이터 정의가 정확함

과거 시계열 수집 완료
≠ 과거에 그 수치를 실제로 알 수 있었음

모델 학습 완료
≠ 미래 예측 성능 검증

테스트 통과
≠ 실제 만기 채점 완료

브랜치 PR 생성
≠ main 병합
```

특히 거시경제 데이터는 나중에 수정된 통계가 과거 기록을 덮어쓰는 경우가 있으므로, 실제 분석 시점에 이용 가능했던 값인지 확인해야 한다.

## 10. 비공개 협업 프로젝트 — 에너지 예측·정산 진단

## 12. 오늘의 핵심 정리

1. 개발 프로젝트는 기능 수만 늘리는 것보다 **데이터의 출처·시간·변경 이력·재현성**을 먼저 통제해야 한다.
2. 과거 백테스트를 반복해 확인할수록 새로운 가설은 미래 데이터로 검증하는 것이 중요해진다.

5. 협업에서는 기술 검증과 실제 운영·공학적 승인의 책임과 상태를 분리해야 한다.

어제는 GMIA의 v0.4 전진검증 장부를 구현했다면, 오늘은 기존 작업을 기본 브랜치에 정리하고 **장기간 믿고 운영할 수 있는 데이터 구조인지 다시 묻는 날**이었다.

특히 실데이터를 많이 모았다는 사실보다 그 데이터가 예측 시점에 사용 가능했고 원본이 나중에 바뀌지 않았으며 같은 입력으로 결과를 재현할 수 있는지가 중요했다.

후속 PR을 통해 실제로 확인되지 않은 BTC·환율·원자재·거시 데이터는 무리하게 운영에 연결하지 않고, 근거가 확보된 부분부터 독립적으로 실험하도록 방향을 잡았다.

협업 프로젝트에서도 합성 기술 검증과 최종 정산·설계 승인을 구분하면서, **테스트가 통과했다는 말과 실제 현장에서 사용할 수 있다는 말은 다르다**는 점을 다시 확인했다.
