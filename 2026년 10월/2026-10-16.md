# 1. Chapter 14-1 실제 자동화 검증 마무리

어제 만든 로컬 자동화 코드를 오늘은 실제 데이터와 외부 서비스 기준으로 다시 검증했다.

확인한 결과:

```text
NAVER Search Trend: 4개 키워드 × 13개월 = 52행
관광 체류 강도: 26행
관광 소비 강도: 26행
analysis_summary.csv: 30행
단위 테스트: 16개 PASS
```

로컬 Python 직접 실행, 배치 파일 재실행, Windows 작업 스케줄러 수동 실행까지 모두 성공 상태를 확인했다.

재실행 후에도 행 수와 요약 CSV 결과가 불필요하게 중복되지 않는지도 확인했다.

# 2. API Secret 보호

자동화 검증 과정에서는 정상 결과뿐 아니라 인증정보를 남기지 않는 것도 중요했다.

다음 항목은 Git에 올라가지 않도록 제외했다.

- .env의 API Key
- Make 개인 설정
- Raw API 응답
- 처리 중간 데이터
- 생성 PDF와 로그
- 인증정보가 포함될 수 있는 임시 파일

특히 API 오류 메시지나 URL에도 serviceKey가 그대로 노출되지 않도록 주의했다.

자동화 코드를 공개 저장소에 올릴 때는 동작 여부와 Secret 보호를 동시에 확인해야 한다.

# 3. Make에서 독립 자동화 구성

Chapter 14-1의 PART 2는 로컬 Python 결과를 Make에 올리는 방식이 아니라 Make가 각 API를 직접 호출하는 별도 자동화다.

오늘 실제 Make Scenario를 구성하고 다음 순서를 Run once로 확인했다.

```text
NAVER Search Trend
→ 관광 체류 강도
→ 관광 소비 강도
→ Gemini 요약
```

NAVER는 52행, 관광 API는 각각 26행, Gemini 호출은 HTTP 200 응답을 확인했다.

LLM 앞에서는 두 관광 API의 resultCode가 모두 0000인지 검사하도록 했다.

# 4. LLM 결과도 다시 검증

첫 Gemini 요약에서는 체류 강도와 소비 강도의 숫자 크기를 직접 비교하는 표현이 있었다.

하지만 두 값은 서로 다른 지표이기 때문에 단순히 119가 89보다 크다는 식으로 해석하면 안 된다.

그래서 프롬프트를 수정해 다음을 명시했다.

- NAVER ratio는 실제 검색 건수가 아님
- 체류 강도와 소비 강도는 서로 다른 지표
- 두 관광 지표의 숫자 크기를 직접 비교하지 않음
- 데이터에 없는 원인이나 숫자를 생성하지 않음
- 서로 다른 기간·지역 데이터를 인과관계처럼 설명하지 않음

수정 후 다시 실행한 결과를 입력 데이터와 대조했다.

# 5. Gemini 사용량 한도와 외부 서비스 실패

외부 서비스를 연결하면 코드가 정상이어도 서비스 자체의 제한 때문에 실패할 수 있다.

오늘 Make 전체 재실행 과정에서 다음 오류를 확인했다.

```text
503 = 일시적인 서버 혼잡
429 = Gemini 무료 일일 요청 한도 소진
```

이 경우 계속 무작정 재시도하지 않고 실제 서비스 한도 문제로 기록했다.

자동화 실패를 코드 버그와 외부 서비스 장애로 구분하는 것이 중요하다.

# 6. Gmail OAuth 오류와 복구

Make에 Gmail Send an email 모듈을 추가했지만 처음에는 다음 오류가 발생했다.

```text
403 insufficient authentication scopes
```

즉 Gmail 연결 자체는 되어 있었지만 메일을 보낼 권한 범위가 충분하지 않았다.

Google 권한을 다시 승인한 뒤 Gmail 모듈만 별도로 다시 테스트했다.

최종 확인:

- Gmail 모듈 Success
- 테스트 메일 1통 발송
- SENT 확인
- INBOX 수신 확인
- 한글 제목과 본문 확인

단, Gemini를 다시 호출한 전체 5개 모듈 일괄 성공은 쿼터 문제 때문에 아직 확인하지 않았다.

Make Scenario도 아직 On demand / Inactive 상태로 유지했다.

# 17. 오늘의 핵심 정리

```text
외부 API 자동화에서는
코드 성공과 서비스 인증/쿼터 성공을 구분해야 한다.

OAuth 연결은

Make의 Run once는

Seed 데이터는
원본 보존 → 전처리 → 중복/결측/참조 검증 후 적재한다.

공모전은
아이디어·활용사례·실제 모델링 대회의 성격을 구분해야 한다.
```

# 18. 오늘의 회고

오늘은 어제 만든 자동화가 실제 외부 서비스에서도 끝까지 연결되는지를 확인하는 데서 시작했다.

Gmail 403 오류나 Gemini 쿼터처럼 코드 밖에서 발생하는 문제를 직접 겪으면서 자동화에서는 프로그램 자체뿐 아니라 인증, 권한, 서비스 한도까지 운영 요소로 봐야 한다는 점을 확인했다.

Chapter 14-2에서는 데이터 수집과 화면을 직접 연결하지 않고 Make → Supabase → Dashboard로 역할을 나누면서 조금 더 서비스다운 구조를 만들기 시작했다.

동시에 공모전 두 개를 새로 검토하면서 같은 데이터·AI 분야라도 심사 대상이 아이디어인지, 활용 성과인지, 실제 예측 성능인지에 따라 준비 방식이 완전히 달라진다는 점도 정리할 수 있었다.
