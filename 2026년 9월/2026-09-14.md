# 1. AWS EC2는 무엇인가

EC2는 AWS에서 빌려 쓰는 가상 컴퓨터라고 생각하면 된다.

내 컴퓨터에서 HTML 파일을 만들었다고 해서 인터넷에 자동으로 공개되는 것은 아니다.

웹페이지를 인터넷에서 접속 가능하게 만들려면 대략 다음 흐름이 필요하다.

```text
내 PC에서 HTML/CSS 작성
↓
GitHub에 저장
↓
AWS EC2 서버 생성
↓
EC2 서버에 접속
↓
GitHub 파일을 서버로 가져오기
↓
Nginx 같은 웹서버가 파일을 보여주도록 설정
↓
EC2 Public IP로 접속
```

오늘은 이 흐름을 직접 따라가면서 각 단계의 역할을 조금씩 이해했다.

# 2. EC2 인스턴스 생성

처음에는 EC2 인스턴스를 여러 번 만들고 종료하면서 설정을 다시 확인했다.

최종적으로 Ubuntu 기반으로 다시 진행했다.

오늘 사용한 이미지 중 하나는:

```text
Ubuntu 26.04 LTS
```

EC2를 만들 때는 단순히 서버만 생성되는 것이 아니라 다음 요소들도 중요하다.

- 운영체제 이미지(AMI)
- 인스턴스 유형
- 키 페어
- 보안 그룹
- Public IP

특히 웹페이지를 외부에서 접속하려면 보안 그룹에서 HTTP 접근이 가능해야 한다.

# 3. Public IP의 의미

EC2 인스턴스를 만들면 외부에서 접속할 때 사용할 Public IP가 생긴다.

오늘 생성한 Ubuntu 서버에서는 Public IP가 별도로 할당되었다.

Public IP는 브라우저에서 웹페이지를 확인하거나 SSH 접속을 할 때 사용한다.

```text
내 PC
↓
인터넷
↓
EC2 Public IP
↓
Ubuntu 서버
```

다만 인스턴스를 종료하고 새로 만들면 IP가 바뀔 수 있다는 점도 주의해야 한다.

GitHub는 파일 보관 장소이고, EC2는 실제 실행되는 서버라고 구분해서 생각하면 이해하기 쉽다.

# 5. Nginx의 역할

HTML 파일을 서버 안에 저장만 해놓는다고 브라우저가 자동으로 보여주는 것은 아니다.

Nginx는 브라우저에서 요청이 들어왔을 때 HTML, CSS 같은 파일을 전달해 주는 웹서버다.

설치 예시:

```bash
sudo apt install nginx -y
```

정상 실행 여부는 다음과 같이 확인할 수 있다.

```bash
sudo systemctl status nginx
```

대략적인 구조는 다음과 같다.

```text
브라우저
↓ HTTP 요청
Nginx
↓
index.html / style.css
↓
브라우저에 페이지 표시
```

# 6. 정적 웹페이지 배포에서 파일 위치가 중요한 이유

Nginx는 기본적으로 특정 폴더 안의 파일을 웹페이지로 제공한다.

Ubuntu의 기본 Nginx 설정에서는 보통 다음 위치가 사용된다.

```text
/var/www/html
```

따라서 GitHub에서 가져온 `index.html`과 `style.css`를 Nginx가 읽는 위치에 두어야 한다.

예를 들면:

```bash
sudo cp index.html /var/www/html/
sudo cp style.css /var/www/html/
```

파일이 다른 위치에 있다면 Nginx 입장에서는 그 파일을 보여줄 수 없다.

오늘 실습을 통해 웹 배포에서 단순히 "파일이 존재한다"보다 "웹서버가 읽는 위치에 파일이 존재한다"가 중요하다는 점을 알게 됐다.

# 7. EC2 실행 / 중지 / 종료 차이

오늘 가장 헷갈렸던 부분 중 하나였다.

## 중지(Stop)

컴퓨터 전원을 잠깐 끄는 것과 비슷하다.

```text
실행 중
→ 중지
→ 다시 시작 가능
```

서버 자체는 남아 있기 때문에 나중에 다시 시작할 수 있다.

## 종료(Terminate)

서버 자체를 삭제하는 것에 가깝다.

```text
실행 중
→ 종료
→ 다시 시작 불가능
```

오늘 종료한 인스턴스를 다시 켜려고 했지만, 종료 상태에서는 다시 실행할 수 없다는 것을 확인했다.

즉 서버를 잠깐 안 쓸 생각이라면 `중지`, 정말 없앨 생각이라면 `종료`를 사용해야 한다.

# 8. 종료된 인스턴스가 목록에 남는 이유

EC2 인스턴스를 종료해도 콘솔 목록에서 바로 사라지지 않을 수 있다.

종료된 상태가 일정 시간 표시될 수 있고, 사용자가 직접 일반 파일처럼 즉시 삭제하는 방식은 아니다.

따라서 화면에 남아 있다고 해서 아직 실행되고 있는 것은 아니다.

상태를 먼저 확인해야 한다.

```text
Running     = 실행 중
Stopped     = 중지 상태
Terminated  = 종료 완료
```

# 9. 오늘 겪은 문제와 정리

## 1) 터미널에 붙여넣기가 제대로 안 됨

브라우저 기반 터미널이나 SSH 화면에서는 일반 Windows 프로그램과 붙여넣기 방식이 다를 수 있다.

명령어가 입력되지 않는다고 해서 명령 자체가 틀린 것은 아니므로 먼저 터미널 입력 방식부터 확인해야 한다.

## 2) Ubuntu로 다시 만들었는데도 바로 되지 않음

운영체제만 바꾼다고 배포가 자동으로 되는 것은 아니다.

다음 요소가 모두 맞아야 한다.

```text
EC2 실행 상태
+ SSH 접속 가능
+ Git 설치
+ 저장소 clone
+ Nginx 설치/실행
+ 파일 위치
+ 보안 그룹 HTTP 허용
```

한 단계라도 빠지면 브라우저에서 페이지가 나오지 않을 수 있다.

## 3) 인스턴스를 종료한 뒤 다시 켜려고 함

`Stop`과 `Terminate`의 차이를 정확히 몰랐기 때문에 생긴 문제였다.

앞으로 실습 서버를 잠시 보관해야 한다면 종료가 아니라 중지를 먼저 고려해야 한다.

# 10. GitHub와 AWS의 역할 차이

오늘 실습하면서 둘의 역할을 구분하는 것이 중요했다.

```text
GitHub
= 코드와 파일을 저장하고 버전을 관리하는 곳

AWS EC2
= 실제 서버를 실행하는 곳

Nginx
= EC2 안에서 HTML을 사용자에게 전달하는 프로그램
```

즉 GitHub에 HTML 파일이 있다고 해서 바로 홈페이지가 되는 것이 아니다.

```text
GitHub 파일
→ EC2로 가져오기
→ Nginx가 제공
→ 브라우저 접속
```

이 연결이 완성되어야 실제 배포가 된다.

# 13. 오늘의 회고

오늘은 명령어 하나를 외우는 것보다 웹페이지가 인터넷에 표시되기까지 어떤 요소들이 연결되는지 이해하는 것이 더 중요했다.

처음에는 GitHub의 HTML 파일을 AWS에 올리면 바로 실행될 것이라고 생각했지만, 실제로는 EC2라는 서버와 Nginx라는 웹서버가 필요했고 파일 위치와 네트워크 설정도 맞아야 했다.

또 EC2의 `중지`와 `종료`가 전혀 다른 기능이라는 것도 직접 실수하면서 확실히 알게 됐다.

앞으로 서버가 작동하지 않을 때는 무작정 다시 만드는 것보다 다음 순서로 하나씩 확인하는 습관이 필요하다.

```text
1. 인스턴스가 Running인가?
2. 서버에 접속되는가?
3. 필요한 프로그램이 설치되어 있는가?
4. GitHub 파일이 서버에 존재하는가?
5. Nginx가 실행 중인가?
6. HTML 파일이 Nginx가 읽는 위치에 있는가?
7. 보안 그룹에서 HTTP가 허용되어 있는가?
8. 올바른 Public IP로 접속하고 있는가?
```

오늘처럼 오류가 여러 개 겹쳐 보일 때도 단계별로 쪼개서 확인하면 어디서 문제가 생겼는지 찾을 수 있다.
