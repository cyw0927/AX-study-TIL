# 1. Chapter 01 과제 — 질문부터 다시 정의하기

처음 선택한 질문은 다음과 같았다.

```text
어떤 상품이 잘 팔리고 있나요?
```

처음 보면 간단한 질문이지만 실제 분석에서는 문제가 있다.

`잘 팔린다`라는 표현에 여러 기준이 섞여 있기 때문이다.

```text
판매 수량이 많은 상품
주문 금액이 큰 상품
주문 건수가 많은 상품
구매 고객 수가 많은 상품
```

따라서 오늘은 질문을 다음처럼 구체화했다.

```text
전체 제공 기간의 완료(completed) 주문을 기준으로
상품별 총 판매 수량과 총 주문 금액을 계산했을 때,
각 기준에서 상위 상품은 어떻게 다르게 나타나는가?
```

핵심은 **질문을 코드로 바꾸기 전에 측정 기준을 먼저 정하는 것**이다.

이번 실습에서는 다음 두 지표를 분리했다.

```text
1. 총 판매 수량
2. 총 주문 금액
```

주문 금액은 다음 기준으로 계산한다.

```text
주문 금액 = quantity × unit_price
```

또한 취소되거나 환불된 주문이 판매 실적에 섞이지 않도록 우선 `completed` 주문만 대상으로 정했다.

# 3. 여러 CSV는 키를 기준으로 연결한다

이번 데이터의 핵심 연결 관계는 다음과 같다.

```text
products.product_id
        ↓
order_items.product_id

orders.order_id
        ↓
order_items.order_id
```

즉 `order_items.csv`가 가운데에서 주문과 상품을 이어 주는 역할을 한다.

흐름으로 보면 다음과 같다.

```text
orders
  ↓ order_id
order_items
  ↓ product_id
products
```

하나의 CSV에 모든 정보가 들어 있지 않기 때문에 분석 전에 **어떤 파일을 어떤 키로 연결할 것인지** 확인해야 한다.

이 과정 없이 바로 코드를 작성하면 존재하지 않는 컬럼을 사용하거나 서로 다른 의미의 데이터를 잘못 연결할 수 있다.

# 4. LLM에게 분석 질문 후보 요청

오늘은 LLM에게 쇼핑몰 데이터로 가능한 분석 질문을 먼저 제안받았다.

대표적인 질문 후보는 다음과 같았다.

```text
1. 월별 완료 주문 금액은 어떻게 변하는가?
2. 어떤 상품이 많이 팔리고 어떤 상품이 높은 주문 금액을 만드는가?
3. 카테고리별 완료 주문 금액은 어떻게 다른가?
4. 고객별 구매 금액은 어떻게 다른가?
5. 완료·취소·환불 주문의 비율은 어떻게 되는가?
```

이 과정에서 느낀 점은 LLM이 **질문 후보를 빠르게 넓혀 주는 역할**에는 유용하다는 것이다.

하지만 LLM이 제안했다고 해서 바로 분석에 사용할 수 있는 것은 아니다.

반드시 확인해야 하는 내용은 다음과 같다.

```text
실제 파일이 존재하는가?
제안한 컬럼이 실제 데이터에 존재하는가?
계산 기준이 데이터 구조와 맞는가?
필요한 관계 키가 존재하는가?
데이터에 없는 원인을 임의로 추측하지 않았는가?
```

즉 LLM 답변은 **초안**이고 최종 판단은 사람이 해야 한다.

# 5. Notebook에서 실제 CSV 구조 검증

말로만 컬럼이 있다고 적는 대신 Jupyter Notebook에서 실제 파일을 읽어 확인했다.

사용한 코드는 다음과 같다.

```python
import pandas as pd
from pathlib import Path

DATA_DIR = Path("../data/raw")

products = pd.read_csv(DATA_DIR / "products.csv")
orders = pd.read_csv(DATA_DIR / "orders.csv")
order_items = pd.read_csv(DATA_DIR / "order_items.csv")

print("products.csv 컬럼")
print(products.columns.tolist())

print("\norders.csv 컬럼")
print(orders.columns.tolist())

print("\norder_items.csv 컬럼")
print(order_items.columns.tolist())

print("\norder_status 값")
print(orders["order_status"].value_counts())
```

실행 결과 실제 컬럼은 다음과 같았다.

```text
products.csv
['product_id', 'product_name', 'category', 'price']

orders.csv
['order_id', 'customer_id', 'order_date', 'payment_method', 'order_status']

order_items.csv
['order_item_id', 'order_id', 'product_id', 'quantity', 'unit_price']
```

`order_status` 값도 직접 확인했다.

```text
completed    184
cancelled     64
refunded      52
```

이 결과를 통해 LLM이 제안한 분석에서 필요한 컬럼이 실제 데이터에 존재하고, `completed` 주문만 구분할 수 있다는 점을 확인했다.

# 7. Evidence와 Prompt Log

Chapter 01 과제에서는 단순히 최종 답만 적는 것이 아니라 과정도 남겼다.

Evidence의 역할은 다음과 같았다.

```text
STEP 1
막연한 질문을 분석 가능한 질문으로 바꾼 과정

STEP 5

STEP 7
Notebook 실행 결과
```

Prompt Log에는 다음 내용을 남겼다.

```text
사용 목적
입력 Prompt 요약
LLM 답변 요약
실제 반영 여부
사람이 검증한 항목
사람이 수정한 내용
남은 확인 사항
```

이 기록이 중요한 이유는 나중에 결과가 달라졌을 때 **어떤 질문과 가정에서 분석을 시작했는지 다시 확인할 수 있기 때문**이다.

# 9. Chapter 02 — 데이터와 DBMS의 기본 개념

오늘 이어서 본 Chapter 02의 핵심은 데이터베이스 용어를 외우는 것이 아니라 **각 개념이 실제로 어디에 위치하고 어떤 역할을 하는지 연결하는 것**이었다.

기본 구조는 다음과 같다.

```text
사용자
  ↓
DBeaver / psql 같은 클라이언트
  ↓
PostgreSQL DBMS
  ↓
Database
  ↓
Schema
  ↓
Table
  ↓
Row / Column
```

이 구조를 한 번에 구분하는 것이 중요하다.

---

# 10. PostgreSQL과 DBeaver는 같은 것이 아니다

헷갈리기 쉬운 부분이다.

## PostgreSQL

```text
데이터베이스를 관리하는 DBMS
```

DBMS는 데이터를 저장하고 조회하고 수정하고 관계와 제약조건을 관리하는 소프트웨어다.

## DBeaver

```text
PostgreSQL 같은 DBMS에 접속해서 SQL을 실행할 수 있게 해 주는 클라이언트 도구
```

따라서 DBeaver를 종료한다고 PostgreSQL에 저장된 데이터가 사라지는 것은 아니다.

다음처럼 생각할 수 있다.

```text
DBeaver 종료
≠
PostgreSQL 데이터 삭제
```

DBeaver는 DB 자체가 아니라 DBMS에 접근하는 도구다.

# 11. DBMS, Database, Schema, Table 구분

## DBMS

```text
데이터베이스들을 관리하는 소프트웨어
```

예:

```text
PostgreSQL
```

## Database

```text
DBMS가 관리하는 하나의 논리적인 데이터 공간
```

한 PostgreSQL 서버 안에 여러 Database가 있을 수 있다.

## Schema

```text
Database 안에서 테이블 등의 객체를 묶어 관리하는 논리적인 구역
```

`public`도 PostgreSQL 제품 이름이 아니라 **스키마 이름**이다.

## Table

```text
행과 열 형태로 데이터를 저장하는 객체
```

예를 들어:

```text
public.students
```

은 다음처럼 읽는다.

```text
public   → 스키마
students → 테이블
```

즉 **public 스키마에 있는 students 테이블**이다.

# 12. 테이블은 먼저 '한 행의 의미'를 생각한다

Chapter 02에서 계속 강조되는 부분이다.

테이블을 볼 때 컬럼 이름부터 보기보다 먼저 다음 질문을 해야 한다.

```text
이 테이블의 한 행은 무엇을 의미하는가?
```

예:

```text
students 한 행
→ 학생 한 명

courses 한 행
→ 강의 한 개

enrollments 한 행
→ 특정 학생이 특정 강의를 신청한 사건 한 건
```

한 행의 의미가 불분명하면 테이블 설계 자체가 애매할 가능성이 있다.

# 13. 내부 식별자와 업무 식별자

학생 테이블 예시는 다음과 같다.

```sql
CREATE TEMP TABLE ch02_students (
    id INTEGER PRIMARY KEY,
    student_number TEXT UNIQUE NOT NULL,
    name TEXT NOT NULL,
    major TEXT
);
```

여기서 두 식별자를 구분할 수 있다.

```text
id
→ DB 내부에서 행을 안정적으로 구분하는 내부 식별자 후보

student_number
→ 학교 업무에서 사용하는 업무 식별자 후보
```

둘은 역할이 같지 않다.

특히 학번이 다음처럼 생겼다고 하자.

```text
00123456
```

이를 숫자로 저장하면 앞의 `00`이 사라질 수 있다.

```text
00123456 → 123456
```

따라서 숫자처럼 보인다고 해서 반드시 숫자 타입으로 저장해야 하는 것은 아니다.

계산에 사용하는 값인지, **식별을 위한 문자열인지 의미를 먼저 확인해야 한다.**

---

# 14. PK — Primary Key

PK는 테이블에서 각 행을 고유하게 구분하는 키다.

예:

```sql
id INTEGER PRIMARY KEY
```

이미 `id = 1`인 학생이 존재하는 상태에서 다시 다음 값을 넣으면 실패해야 한다.

```sql
INSERT INTO ch02_students (id, student_number, name, major)
VALUES (1, '20269999', '새학생', '경영학');
```

이유는 간단하다.

```text
PK는 한 테이블 안에서 같은 값을 중복해서 사용할 수 없다.
```

즉 PK는 **자기 테이블 안에서 자신의 행을 구분하는 역할**을 한다.

---

# 15. FK — Foreign Key

FK는 다른 테이블의 행을 참조하여 관계를 만드는 키다.

예:

```sql
student_id INTEGER NOT NULL REFERENCES ch02_students(id)
course_id INTEGER NOT NULL REFERENCES ch02_courses(id)
```

의미는 다음과 같다.

```text
student_id
→ ch02_students.id 참조

course_id
→ ch02_courses.id 참조
```

존재하지 않는 학생 ID를 참조하려 하면 DBMS가 막을 수 있다.

예:

```sql
INSERT INTO ch02_enrollments (id, student_id, course_id, status)
VALUES (1004, 999, 10, '신청');
```

현재 학생 테이블에 `id = 999`가 없다면 정상적인 FK 제약조건에서는 실패해야 한다.

이것이 DBMS가 관계의 무결성을 지키는 방법 중 하나다.

---

# 16. FK 값은 반복될 수 있다

PK와 FK를 처음 배울 때 헷갈릴 수 있는 부분이다.

PK는 같은 테이블에서 중복될 수 없지만 FK는 관계에 따라 반복될 수 있다.

예:

```text
학생 1 → 데이터베이스 입문 신청
학생 1 → 파이썬 기초 수강중
```

수강신청 테이블에서는 다음처럼 `student_id = 1`이 여러 번 나올 수 있다.

```text
1001 | student_id=1 | course_id=10
1002 | student_id=1 | course_id=20
```

이것은 오류가 아니다.

```text
학생 한 명이 여러 수강신청을 가질 수 있기 때문
```

즉 FK는 자동으로 UNIQUE가 되는 값이 아니다.

---

# 17. 1:N 관계

현재 예제를 기준으로 보면 다음 관계가 된다.

```text
students 1 ── N enrollments
courses  1 ── N enrollments
```

자연어로 읽으면:

```text
학생 한 명은 여러 수강신청을 가질 수 있다.
강의 한 개는 여러 수강신청을 가질 수 있다.
수강신청 한 건은 학생 한 명을 참조한다.
수강신청 한 건은 강의 한 개를 참조한다.
```

이 관계에서 학생 ID와 강의 ID가 여러 enrollment 행에서 반복되는 것은 정상이다.

---

# 18. N:M 관계와 연결 테이블

학생과 강의를 직접 보면 다음과 같은 관계가 가능하다.

```text
학생 한 명
→ 여러 강의를 신청할 수 있음

강의 한 개
→ 여러 학생이 신청할 수 있음
```

따라서 학생과 강의는 N:M 관계 후보가 된다.

이 관계를 `enrollments` 같은 연결 테이블로 풀면 다음과 같이 표현할 수 있다.

```text
students
   1
   |
   N

enrollments

   N
   |
   1
courses
```

즉 하나의 N:M 관계를 두 개의 1:N 관계로 표현할 수 있다.

---

# 19. TEMP TABLE

Chapter 02 실습에서는 기존 데이터에 영향을 주지 않기 위해 TEMP TABLE을 사용한다.

```sql
CREATE TEMP TABLE ...
```

TEMP TABLE의 특징은 다음과 같다.

```text
현재 연결 세션에서 사용하는 임시 테이블
세션이 끝나면 사라짐
개념 실험에 적합함
```

따라서 실습 중에는 같은 SQL Editor와 같은 연결 세션을 유지하는 것이 중요하다.

다른 연결을 새로 열면 방금 만든 TEMP TABLE이 보이지 않을 수 있다.

---

# 20. 테이블과 SELECT 결과는 다르다

중요한 개념이다.

```text
Table
≠
SELECT Result
```

예를 들어 원본 학생 테이블이 다음 네 컬럼을 가지고 있다고 하자.

```text
id
student_number
name
major
```

다음 SQL을 실행하면:

```sql
SELECT name, major
FROM ch02_students
ORDER BY id;
```

결과 화면에는 `name`, `major`만 보인다.

하지만 그렇다고 원본 테이블에서 `id`, `student_number`가 삭제된 것은 아니다.

SELECT는 **원본 테이블에서 조건에 맞는 데이터만 골라 만든 결과 집합**이다.

WHERE도 마찬가지다.

```sql
SELECT id, student_number, name, major
FROM ch02_students
WHERE major = '컴퓨터공학'
ORDER BY id;
```

결과가 두 행만 나와도 원본 테이블의 다른 학생 행이 삭제된 것이 아니다.

---

# 21. ORDER BY가 필요한 이유

조회 화면에서 어떤 순서로 보였다고 해서 테이블이 항상 그 순서를 보장하는 것은 아니다.

```text
현재 화면에서 이 순서로 보였다
≠
항상 그 순서로 조회된다
```

순서가 중요하면 명시해야 한다.

```sql
SELECT id, name
FROM ch02_students
ORDER BY name ASC;
```

또는:

```sql
SELECT id, name
FROM ch02_students
ORDER BY name DESC;
```

의미:

```text
ASC  → 오름차순
DESC → 내림차순
```

업무적으로 순서가 중요하다면 `ORDER BY`를 명시하는 습관이 필요하다.

# 22. AI가 만든 테이블도 사람이 먼저 검토해야 한다

Chapter 02에서는 다음과 같은 구조를 예시로 검토한다.

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),
    student_email VARCHAR(100),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50)
);
```

AI에게 바로 정답을 요청하기 전에 사람이 먼저 다음 질문을 던져야 한다.

```text
1. 이 테이블의 한 행은 무엇을 의미하는가?
2. 각 행을 안정적으로 구분하는 PK가 있는가?
3. 학생·강의·강사를 이름 문자열로만 연결해도 되는가?
4. 서로 다른 종류의 정보가 한 테이블에 섞여 있지 않은가?
5. 필수값·중복·참조 규칙은 무엇인가?
```

이 방식은 Chapter 01에서 배운 LLM 검증 과정과도 연결된다.

```text
사람이 먼저 문제 정의
    ↓
AI에게 검토 요청
    ↓
본문 또는 실제 DB 결과와 비교
    ↓
수용 / 수정 / 보류
```

AI가 설계를 대신 결정하도록 두기보다 **검토 도구로 사용하는 것**이 핵심이다.
