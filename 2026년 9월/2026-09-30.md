# 1. Chapter 09 — 트랜잭션을 하나의 업무 단위로 보기

Chapter 09에서는 트랜잭션을 단순히 `BEGIN`, `COMMIT`, `ROLLBACK` 문법으로만 보는 것이 아니라 여러 변경을 하나의 업무 단위로 묶는 방식으로 정리했다.

예를 들어 수강신청이라면 다음 작업이 서로 따로 움직이면 안 된다.

```text
좌석 1개 차감
→ 수강신청 생성
→ 결제 기록 생성
```

좌석만 줄고 신청이 생성되지 않거나, 신청은 있는데 결제가 없으면 데이터가 서로 맞지 않는다.

따라서 이런 변경은 하나의 트랜잭션 안에서 처리하고 최종 검증에 성공했을 때만 COMMIT해야 한다.

# 2. COMMIT과 ROLLBACK의 범위

ROLLBACK은 데이터베이스 전체를 과거 상태로 되돌리는 것이 아니다.

```text
현재 열려 있는 트랜잭션에서 발생한 변경
→ ROLLBACK 대상

이미 COMMIT된 이전 트랜잭션
→ 그대로 유지
```

이 점을 통해 트랜잭션 경계를 어디에서 잡는지가 중요하다는 것을 다시 확인했다.

또 SQL이 오류 없이 실행됐다는 사실만으로 업무가 정상 처리됐다고 볼 수는 없다.

예를 들어 UPDATE가 예상한 1행이 아니라 0행 또는 여러 행에 적용됐을 수도 있기 때문에 실제 업무에서는 영향 행 수와 최종 상태를 같이 확인해야 한다.

# 3. Chapter 10 — 인덱스 성능 실습 데이터

Chapter 10에서는 별도의 `performance_lab` 스키마에서 대량 데이터를 사용했다.

주요 데이터 규모는 다음과 같았다.

```text
students      10,003행
instructors        2행
courses         2,003행
enrollments    100,005행
```

인덱스를 만들기 전에 먼저 데이터 분포를 확인했다.

```text
student_id = 5000
→ 10행

course_id = 1500
→ 50행

course_id = 1500 AND status = '수강중'
→ 15행

status = '수강중'
→ 30,001행
```

100,005행 기준으로 보면 선택도 차이가 매우 크다.

```text
student_id = 5000
→ 약 0.01%

course_id = 1500
→ 약 0.05%

course_id + status
→ 약 0.015%

status = '수강중'
→ 약 30%
```

오늘 실습에서 가장 중요했던 것은 이 데이터 분포였다.

# 4. 인덱스를 만들기 전에 Baseline을 남겨야 하는 이유

처음에는 인덱스를 만들고 빨라졌는지만 보면 될 것 같지만, 비교 기준이 없으면 실제 효과를 판단할 수 없다.

그래서 후보 인덱스를 만들기 전에 같은 SQL을 먼저 실행했다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

확인한 주요 항목은 다음과 같다.

```text
Scan 방식
actual rows
Buffers
Execution Time
Filter
Index Cond
```

특히 실행 시간 하나만 보는 것이 아니라 계획 자체가 어떻게 바뀌었는지 확인하는 것이 중요했다.

# 5. 후보 인덱스

실습에서는 다음과 같은 조회 패턴을 기준으로 후보 인덱스를 만들었다.

```text
학생별 수강신청 조회
course_id 조건 조회
course_id + status 복합 조건 조회
강의 제목 검색 및 정렬
```

최종적으로 Chapter 10 후보 인덱스 3개를 포함해 `performance_lab`에서 전체 9개의 인덱스를 확인했다.

대표 후보는 다음과 같다.

```text
courses(title)

enrollments(student_id)

enrollments(course_id, status)
```

중요한 점은 인덱스 이름이나 개수보다 어떤 SQL을 빠르게 만들기 위해 존재하는지를 설명할 수 있어야 한다는 것이다.

# 6. 인덱스 전후 실제 계획 비교

`student_id = 5000`처럼 전체 데이터 중 극히 일부만 찾는 조건에서는 인덱스 효과가 컸다.

예를 들어 학생별 수강신청 조회에서는 버퍼 접근이 크게 감소했다.

```text
Before Buffers
769

After Buffers
36
```

`course_id = 1500` 조회도 Seq Scan에서 Bitmap Scan 계열로 바뀌면서 큰 차이가 나타났다.

```text
Before
Buffers = 736
Execution Time ≈ 3.944 ms

After
Buffers ≈ 52
Execution Time ≈ 0.106 ms
```

단순히 시간이 줄었다는 것보다 접근해야 하는 페이지 수 자체가 크게 줄었다는 점이 더 의미 있었다.

# 7. Seq Scan이 항상 나쁜 것은 아니다

오늘 가장 기억에 남은 부분이다.

`status = '수강중'` 조건은 전체 약 30%인 30,001행을 반환한다.

인덱스를 만든 후에도 PostgreSQL은 이 SQL에서 계속 Seq Scan을 선택했다.

```text
Before
Seq Scan
Buffers = 736
Execution Time ≈ 9.000 ms

After
Seq Scan
Buffers = 736
Execution Time ≈ 9.191 ms
```

처음에는 인덱스를 만들었는데 Seq Scan이 나오면 인덱스가 실패한 것처럼 생각할 수 있다.

하지만 실제로는 그렇지 않았다.

30% 정도의 많은 행을 가져와야 한다면 인덱스를 통해 여러 위치를 찾아다니는 것보다 테이블을 순서대로 한 번 읽는 것이 더 저렴할 수 있다.

즉,

```text
Seq Scan
≠ 무조건 나쁜 실행 계획

Index Scan
≠ 무조건 좋은 실행 계획
```

옵티마이저는 현재 데이터 분포와 비용을 기준으로 계획을 선택한다.

# 8. 복합 인덱스의 컬럼 순서

```text
(course_id, status)
```

형태의 복합 인덱스를 사용했다.

이 인덱스는 다음 조회에는 효과가 있었다.

```text
WHERE course_id = ...
WHERE course_id = ... AND status = ...
```

하지만 다음 조회에서는 효과가 없었다.

```text
WHERE status = ...
```

선두 컬럼인 `course_id` 조건이 없기 때문이다.

PostgreSQL 버전에 따라 복합 B-tree 후행 컬럼을 활용하는 방식이 달라질 수 있지만, 이번 실제 실행에서는 `status` 단독 조건이 계속 Seq Scan으로 나왔다.

결국 인덱스는 컬럼이 들어 있기만 하면 모든 조건에 동일하게 쓰이는 것이 아니며 컬럼 순서가 중요하다.

# 9. ORDER BY와 LIMIT

강의 제목 정렬에서도 인덱스 효과를 확인했다.

```text
ORDER BY title
```

인덱스 생성 전에는 전체 데이터를 읽고 Sort 노드에서 정렬했다.

인덱스 생성 후에는 `title` 순서로 만들어진 인덱스를 그대로 읽으면서 Sort 노드가 사라졌다.

특히 다음처럼 LIMIT이 붙었을 때 효과가 더 컸다.

```sql
ORDER BY title
LIMIT 20
```

실행 결과:

```text
Before
Seq Scan + Sort
Buffers = 34
Execution Time ≈ 1.045 ms

After
Index Scan
Buffers = 3
Execution Time ≈ 0.026 ms
```

이미 정렬된 인덱스에서 앞쪽 20개만 읽고 바로 멈출 수 있기 때문에 전체 데이터를 읽고 정렬하는 것보다 효율적이었다.

# 10. 실행 시간 한 번만 믿으면 안 되는 이유

실행 시간은 캐시 상태나 PC 부하에 따라 달라질 수 있다.

그래서 오늘 실습에서는 다음을 함께 비교했다.

```text
1. actual rows가 같은가?
2. Scan 방식이 바뀌었는가?
3. Buffers가 감소했는가?
4. Index Cond가 실제로 사용됐는가?
5. Execution Time이 개선됐는가?
```

특히 결과 행 수가 Before와 After에서 같아야 한다.

```text
더 빠른데 결과가 다름
=
성능 개선이 아니라 잘못된 결과
```

이 기준이 생각보다 중요했다.

# 12. 인덱스를 많이 만들면 생기는 비용

인덱스는 조회 성능만 생각하면 계속 추가하고 싶어진다.

하지만 인덱스가 늘어날수록 다음 비용도 같이 증가한다.

```text
INSERT
→ 테이블 + 인덱스 갱신

UPDATE
→ 인덱스 대상 컬럼 변경 시 인덱스도 수정

DELETE
→ 인덱스 항목도 정리

Storage
→ 인덱스 자체 디스크 공간 필요
```

따라서 실제로 자주 사용하는 조회인지 확인하지 않고 인덱스를 계속 추가하는 것은 좋은 방법이 아니다.

# 13. AI의 인덱스 제안을 그대로 믿으면 안 되는 이유

AI에게 컬럼 이름과 SQL만 보여주면 그럴듯한 인덱스를 쉽게 추천할 수 있다.

하지만 실제 데이터 분포를 모르면 잘못된 판단을 할 수 있다.

오늘 실습에서도 `status` 단독 조회를 위한 인덱스가 도움이 될 것처럼 생각할 수 있었지만 실제 데이터에서는 약 30%를 반환했고 PostgreSQL은 계속 Seq Scan을 선택했다.

그래서 AI에게 인덱스를 추천받을 때도 최소한 다음 정보를 같이 줘야 한다.

```text
테이블 행 수
조건별 실제 행 수
선택도
현재 인덱스
PostgreSQL 버전
EXPLAIN (ANALYZE, BUFFERS) 결과
```

결국 AI의 제안도 실제 실행 계획으로 검증해야 한다.

# 16. 오늘의 회고

오늘은 단순히 `CREATE INDEX` 문법을 배우는 것보다 PostgreSQL이 왜 어떤 상황에서는 인덱스를 선택하고 어떤 상황에서는 Seq Scan을 선택하는지를 직접 비교해 본 것이 가장 의미 있었다.

특히 이전에는 인덱스가 있으면 당연히 사용하는 것이 좋은 것이라고 생각하기 쉬웠는데, 실제로는 반환해야 하는 행이 많으면 Seq Scan이 더 합리적인 선택이 될 수 있었다.

앞으로 SQL 성능 문제를 볼 때는 다음 순서로 접근해야겠다.

```text
조회 패턴 확인
→ 데이터 규모와 분포 확인
→ Baseline EXPLAIN
→ 인덱스 후보 설계
→ 동일 SQL 재실행
→ 계획 / Buffers / 시간 비교
→ 결과 행 동일성 검증
→ 유지 여부 판단
```

오늘 실습을 통해 인덱스는 많이 만드는 것이 목표가 아니라 실제 조회 패턴에 맞는 최소한의 인덱스를 근거를 가지고 선택하는 것이 중요하다는 점을 정리했다.
