# 1. 오늘의 핵심 — AI를 '작업자'로 쓰기

오늘 가장 크게 느낀 점은 AI를 그냥 코드 질문용으로 쓰는 것과, 실제 프로젝트 파일을 읽고 수정하게 하는 것은 완전히 다르다는 것이다.

단순 질문:

```text

```

자동화 작업:

```text
현재 저장소 상태 확인
↓

↓
다음 STEP 판단
↓
실제 파일 수정
↓
실행/검증
↓
진행 상황 기록
↓
Git 반영
```

오늘은 후자에 더 가까운 작업을 많이 했다.

# 7. 자동 윤문에서 가장 중요한 조건

책 전체를 AI가 마음대로 다시 쓰게 하면 안 된다.

그래서 다음 조건을 명확하게 잡았다.

```text
의미 보존
고유명사 보존
책별 문체 보존
Markdown 구조 보존
reading-nav 보존
번역체만 자연스럽게 수정
과도한 의역 금지
내용 추가 금지
내용 삭제 금지
```

핵심은 '재창작'이 아니라 **보수적 교정**이다.

# 8. 책마다 문체가 다르다

도서관 프로젝트에는 소설, 역사서, 정치·사회서, 경제서 등 여러 책이 섞여 있다.

따라서 하나의 문체로 평준화하면 안 된다.

예를 들어:

```text
소설
→ 대사와 서술 리듬 보존

역사서
→ 건조한 설명체와 고유명사 보존

사회과학
→ 논리 구조와 개념어 유지

고전 번역
→ 지나치게 현대식으로 바꾸지 않기
```

그래서 범용 프롬프트 안에서도 원문의 장르와 문체를 먼저 추론하고 그 스타일을 유지하도록 설계했다.

# 9. Markdown 구조 보존

자동 윤문에서 텍스트만 보면 안 된다.

Markdown에는 다음 요소가 있을 수 있다.

```text
# 제목
## 소제목
링크
이미지
인용문
목록
코드 블록
reading-nav
내부 링크
```

이 구조가 깨지면 책 탐색 기능이나 렌더링이 망가질 수 있다.

따라서 수정 대상은 본문 문장이고, 구조 요소는 최대한 그대로 유지해야 한다.

# 10. 제외 대상 정리

모든 파일을 자동으로 돌리면 안 된다.

오늘 정한 제외 대상:

```text
.git
node_modules
tools
ux library
README.md
```

이런 폴더나 파일은 본문 책 데이터가 아니거나 자동 윤문 대상이 아니기 때문이다.

# 11. 진행 로그 남기기

책이 많기 때문에 어디까지 처리했는지 기록해야 한다.

진행 로그 예:

```text
auto_rewrite_progress.log
```

로그에는 다음 정도를 남기는 방식이 적절하다.

```text
처리 시작 파일
처리 완료 파일
실패 파일
재시도 여부
처리 시간
변경 여부
```

이렇게 하면 중간에 작업이 멈춰도 처음부터 다시 돌릴 필요가 없다.

# 12. diff 검증이 필요한 이유

AI가 수정한 결과는 무조건 믿으면 안 된다.

특히 책 전체 자동화에서는 다음을 확인해야 한다.

```text
문단이 사라지지 않았는가?
제목이 바뀌지 않았는가?
Markdown 링크가 깨지지 않았는가?
고유명사가 잘못 바뀌지 않았는가?
navigation이 유지되었는가?
문장 의미가 달라지지 않았는가?
```

그래서 원본과 결과의 diff를 검토하는 과정이 필요하다.

# 13. 자동 윤문 파이프라인 구상

오늘 정리한 전체 흐름은 대략 다음과 같다.

```text
Markdown 파일 탐색
↓
제외 경로 필터링
↓
파일 읽기
↓
문단 단위 분할
↓
OpenAI API 호출
↓
윤문 결과 수신
↓
Markdown 구조 검증
↓
누락 / 길이 / diff 확인
↓
원본 파일 반영
↓
진행 로그 기록
↓
다음 파일 처리
```

문단 단위로 나누는 이유는 책 전체를 한 번에 보내면 토큰 제한과 오류 가능성이 커지기 때문이다.

# 14. 프롬프트가 코드만큼 중요한 이유

오늘 도서관 프로젝트에서 느낀 것은 자동화에서는 코드만 잘 짜는 것으로 끝나지 않는다는 점이다.

API에 어떤 지시를 보내느냐가 결과 품질을 결정한다.

좋은 프롬프트는 다음을 포함해야 한다.

```text
역할
작업 목적
수정 허용 범위
금지 사항
보존 대상
출력 형식
검증 기준
```

특히 여러 책에 공통 적용하려면 너무 특정 장르에 맞춘 프롬프트가 아니라 범용 규칙이 필요하다.

# 15. API 키와 보안

API를 프로젝트에 붙일 때는 키를 코드에 직접 넣으면 안 된다.

예:

```text
.env
```

파일에 저장하고 Python에서는 환경변수로 읽는 방식이 일반적이다.

예:

```python
from dotenv import load_dotenv
import os

load_dotenv()

api_key = os.getenv("OPENAI_API_KEY")
```

그리고 `.env`는 GitHub에 올리지 않도록 `.gitignore`에 포함해야 한다.
