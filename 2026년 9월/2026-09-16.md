# 1. 기존 프로젝트는 먼저 상태부터 확인한다

새 작업을 시작할 때 가장 먼저 할 일은 코드를 쓰는 것이 아니라 현재 저장소가 어디까지 진행되었는지 확인하는 것이다.

특히 장기 프로젝트는 다음 내용을 먼저 확인해야 한다.

```text
어떤 폴더가 이미 존재하는가?
어떤 파일이 완료되었는가?
어떤 작업이 진행 중인가?
다음 작업 대상은 무엇인가?
```

이 과정을 건너뛰면 이미 끝난 작업을 다시 만들거나 파일을 덮어쓸 수 있다.

# 2. 프로젝트 진행 상태를 구조로 표현하기

폴더 이름과 파일 이름을 일정하게 정해 두면 진행 상황을 파악하기 쉬워진다.

예를 들어 시리즈형 프로젝트라면 다음처럼 관리할 수 있다.

```text
project/
├─ 01_part/
├─ 02_part/
├─ 03_part/
├─ 04_part/
└─ README.md
```

각 폴더 안에서 다시 세부 작업을 번호로 나누면 현재 위치를 빠르게 찾을 수 있다.

```text
03_part/
├─ 001.md
├─ 002.md
├─ 003.md
└─ ...
```

이런 방식은 번역, 문서화, 데이터 정리, 코딩 과제처럼 파일이 계속 늘어나는 프로젝트에서 특히 유용하다.

# 3. 완료된 작업은 다시 건드리지 않는다

오늘 프로젝트를 이어갈 때 중요했던 원칙이다.

```text
완료된 작업
→ 수정 이유가 없으면 그대로 유지

진행 중 작업
→ 현재 상태 확인 후 이어서 작업

미시작 작업
→ 다음 순서로 진행
```

장기 프로젝트에서는 '새로 만드는 능력'보다 '기존 상태를 안전하게 이어가는 능력'도 중요하다.

# 4. 진행률을 숫자로 남기기

작업량이 많을수록 감으로 관리하면 헷갈리기 쉽다.

예를 들어 다음처럼 적어 두면 명확하다.

```text
완료: 73 / 73
완료: 70 / 70
진행 예정: 0 / 82
```

이렇게 하면 다음 작업이 어디인지 바로 알 수 있다.

프로젝트 README에는 최소한 다음 내용을 남겨두는 것이 좋다.

```text
현재 완료 범위
현재 진행 중인 범위
다음 작업
예외 또는 주의 사항
```

# 5. GitHub 저장소를 작업 기록으로 사용하기

GitHub는 코드만 올리는 곳이 아니라 작업 상태를 남기는 데도 사용할 수 있다.

```text
폴더 구조
+ 파일 이름
+ README
+ commit 기록
```

이 네 가지를 잘 사용하면 나중에 다시 프로젝트를 열었을 때도 빠르게 상황을 복구할 수 있다.

특히 작업 기간이 길어질수록 commit 메시지가 중요하다.

좋은 예:

```text
docs: complete part 2

docs: start part 3

fix: correct chapter numbering
```

나쁜 예:

```text
수정

ㅇㅇ

asdf
```

나중에 어떤 작업을 했는지 확인하기 어렵기 때문이다.

# 6. 새로 시작하지 말고 이어서 작업하는 기본 순서

앞으로 장기 프로젝트를 다시 열었을 때 다음 순서로 확인하면 된다.

```text
1. 저장소 구조 확인
2. README 확인
3. 최근 commit 확인
4. 완료 범위 확인
5. 다음 작업 파일 확인
6. 기존 파일을 덮어쓰지 않는지 확인
7. 작업 진행
8. commit으로 상태 기록
```

이 순서만 지켜도 중복 작업이나 잘못된 덮어쓰기를 많이 줄일 수 있다.

# 7. 파일 이름 규칙의 중요성

파일 이름이 제각각이면 정렬했을 때 순서가 뒤섞인다.

예:

```text
1.md
2.md
10.md
```

환경에 따라 문자열 기준 정렬에서는 다음처럼 보일 수 있다.

```text
1.md
10.md
2.md
```

그래서 규모가 큰 프로젝트에서는 처음부터 자릿수를 맞추는 방식이 편하다.

```text
001.md
002.md
003.md
...
010.md
```

폴더도 같은 원리다.

```text
01_part
02_part
03_part
```

# 8. README는 프로젝트 안내판이다

README에는 프로젝트 설명만 적는 것이 아니라 현재 작업 상태도 적어두면 좋다.

예:

```markdown
## Progress

- Part 1: Complete
- Part 2: Complete
- Part 3: In progress
- Part 4: Ready
```

이렇게 하면 저장소를 열자마자 현재 상태를 알 수 있다.

혼자 작업하더라도 README를 잘 적어두면 며칠 뒤의 나 자신에게 설명하는 문서가 된다.

# 9. 오늘 배운 핵심

```text
장기 프로젝트에서는 현재 상태 확인이 작업 시작보다 먼저다.
```

```text
완료된 작업을 다시 만드는 것은 진행이 아니라 중복이다.
```

```text
폴더 구조와 파일 이름도 프로젝트 관리의 일부다.
```

```text
README와 commit 기록은 미래의 나를 위한 작업 로그다.
```

# 10. 오늘의 회고

오늘은 코드를 새로 작성하는 것보다 이미 존재하는 프로젝트를 어떻게 안전하게 이어갈 것인지에 초점을 맞췄다.

프로젝트가 커질수록 머릿속으로 모든 진행 상황을 기억하기 어렵기 때문에, 폴더 구조와 README, commit 기록 자체가 중요한 도구가 된다는 점을 다시 확인했다.

앞으로는 장기 프로젝트를 시작하거나 다시 열 때 무작정 파일부터 수정하지 않고 `현재 상태 확인 → 다음 작업 결정 → 작업 → 기록` 순서로 진행해야겠다.
