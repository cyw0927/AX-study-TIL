# 1. 모델 코드보다 먼저 문제 정의

문제는 고객 문의 텍스트를 분석해서 담당자를 자동 배정하는 시스템이다.

현재 가진 데이터:

```text
고객 문의 텍스트
담당자 이름
최종 처리 결과
처리 시간
고객 만족도
```

처음 보면 바로 텍스트 분류 모델을 만들 수 있을 것처럼 보이지만, 먼저 무엇을 예측하려는지 명확히 해야 한다.

과거 담당자 이름을 맞히는 것과 '가장 적절한 담당자'를 배정하는 것은 같은 문제가 아니다.

# 2. 목표 변수 정의

가장 단순한 Target은 과거 담당자 이름이다.

```text
문의 텍스트 → 담당자 이름
```

하지만 과거 담당자 배정이 항상 최선이었다고 보장할 수 없다. 과거 배정에는 당시 근무 여부, 업무량, 수동 배정 습관, 조직 규칙 같은 요소가 섞여 있을 수 있다.

따라서 담당자 이름을 그대로 정답으로 쓰면 모델은 최적 담당자가 아니라 과거 배정 패턴을 학습할 수 있다.

# 3. 데이터 누수

데이터 누수는 실제 예측 시점에는 알 수 없는 정보를 학습에 사용하는 문제다.

오늘 데이터에서 특히 위험한 컬럼:

```text
최종 처리 결과
처리 시간
고객 만족도
```

이 값들은 대부분 문의가 담당자에게 배정된 뒤에 생긴다.

```text
문의 접수
↓
담당자 배정
↓
처리
↓
처리 시간 확정
↓
최종 결과 확정
↓
고객 만족도 수집
```

따라서 담당자를 배정하는 순간에는 사용할 수 없는 정보이므로 모델 입력 Feature로 쓰면 안 된다.

# 4. 사용할 수 있는 Feature

가장 기본적으로 사용할 수 있는 Feature는 고객 문의 텍스트다.

추가 Feature를 쓸 때는 항상 다음 질문을 해야 한다.

```text
이 정보는 담당자를 배정하는 순간에도 알고 있는가?
```

YES라고 답할 수 있는 정보만 입력 Feature 후보가 된다.

# 5. 운영 시점과 학습 시점 일치

머신러닝에서 중요한 원칙:

```text
학습할 때 사용할 수 있는 정보
=
실제 예측할 때 사용할 수 있는 정보
```

이 조건이 깨지면 오프라인에서는 성능이 좋아 보여도 실제 서비스에서는 사용할 수 없다.

# 6. 데이터 구조

모델링 전에는 한 행의 의미를 명확하게 해야 한다.

권장 구조:

```text
한 행 = 한 건의 고객 문의

inquiry_id
inquiry_text
created_at
assigned_agent
...
```

배정 당시 존재했던 정보만 Feature로 사용하고, 배정 이후 생긴 정보는 평가나 사후 분석용으로 분리하는 편이 안전하다.

# 7. 평가 방식

실제 운영은 시간 순서대로 진행되므로 랜덤 분할만으로는 충분하지 않을 수 있다.

예:

```text
1~8월 데이터 → Train
9월 데이터 → Test
```

이렇게 하면 과거 데이터로 미래 문의를 얼마나 잘 처리하는지 확인할 수 있다.

# 8. 첫 번째 Baseline

처음부터 복잡한 모델을 쓸 필요는 없다.

텍스트 분류의 첫 번째 Baseline 후보:

```text
TF-IDF
+
Logistic Regression
```

구현이 단순하고 빠르며, 이후 더 복잡한 모델이 실제로 얼마나 개선되는지 비교하기 좋다.

# 9. 평가 지표

담당자 분류는 다중 분류 문제가 될 가능성이 높다. Accuracy만 보면 담당자 분포가 불균형할 때 왜곡될 수 있다.

같이 확인할 지표:

```text
Accuracy
Precision
Recall
F1-score
Confusion Matrix
```

특히 담당자별 성능을 확인해야 한다.

# 10. 가장 큰 실패 원인

가장 위험한 것은 모델보다 잘못된 문제 정의다.

```text
과거 담당자를 그대로 정답으로 사용
+
배정 이후 정보를 Feature에 포함
+
랜덤 분할만으로 성능 평가
```

이렇게 하면 실제 운영과 동떨어진 높은 성능이 나올 수 있다.

# 11. 외래키(FK) 복습

Foreign Key는 다른 테이블의 Primary Key를 참조하는 컬럼이다.

예:

```text
customers
customer_id  PK

orders
order_id     PK
customer_id  FK
```

관계:

```text
orders.customer_id
→ customers.customer_id
```

# 12. PK와 FK 차이

```text
PK
= 자기 테이블에서 행을 유일하게 식별

FK
= 다른 테이블의 PK를 참조
```

PK는 일반적으로 중복되면 안 되지만, FK는 1:N 관계에서는 반복될 수 있다.

예:

```text
고객 1명
→ 주문 여러 건
```

# 14. 오늘의 회고

오늘은 데이터가 있다고 바로 모델을 학습시키는 것이 아니라, 먼저 Target이 무엇인지, 어떤 Feature가 실제 예측 시점에 존재하는지, 운영 환경과 학습 환경이 같은지 확인해야 한다는 점을 정리했다.

특히 최종 처리 결과, 처리 시간, 고객 만족도처럼 결과가 나온 뒤 생기는 정보는 분석에서는 유용하지만 담당자 배정 모델의 입력값으로는 사용할 수 없다.

앞으로 머신러닝 프로젝트에서는 다음 순서로 진행해야겠다.

```text

→ 평가 설계
→ Baseline
→ 모델 개선
```
