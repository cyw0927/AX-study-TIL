# 1. GitHub 협업에서 다시 헷갈렸던 부분

GitHub 협업을 할 때 가장 헷갈리는 부분은 **내 컴퓨터, 내 브랜치, 원격 저장소, 메인 브랜치가 각각 어디인지** 구분하는 것이다.

가장 단순하게 보면 다음과 같다.

```text
내 컴퓨터(Local)
    ↓ push
GitHub 원격 저장소(Remote)
    ↓ Pull Request
공용 main 브랜치
```

반대로 원격 저장소의 변경 내용을 내 컴퓨터로 가져오는 흐름은 다음과 같다.

```text
GitHub 원격 저장소
    ↓ fetch / pull
내 컴퓨터(Local)
```

`push`는 **내 변경 내용을 GitHub로 올리는 것**이고,
`pull`은 **GitHub의 변경 내용을 내 로컬 브랜치로 가져와 합치는 것**이다.

---

# 2. fetch와 pull의 차이

`git fetch`는 원격 저장소의 변경 내용을 확인용으로 가져온다.

```bash
git fetch
```

이 명령은 원격 브랜치의 최신 상태를 가져오지만 현재 작업 중인 파일에 바로 합치지는 않는다.

반면 `git pull`은 보통 다음 두 작업을 한 번에 한다.

```text
fetch
+
merge
```

즉,

```bash
git pull
```

은 원격 저장소의 최신 내용을 가져오고 현재 브랜치에 반영한다.

초보자 입장에서는 다음처럼 기억하면 편하다.

```text
fetch = 일단 새 소식 가져오기
pull  = 새 소식 가져와서 내 작업에 합치기
push  = 내 작업 GitHub에 올리기
```

# 3. Pull Request는 무엇인가

Pull Request는 다른 브랜치의 변경 내용을 `main` 같은 기준 브랜치에 합쳐 달라고 요청하는 과정이다.

예를 들어 다음 구조라고 생각할 수 있다.

```text
feature/user-a
      ↓
Pull Request
      ↓
main
```

즉 PR은 단순히 파일을 보내는 것이 아니라,

> "내가 이 브랜치에서 이런 변경을 했으니 main에 합쳐도 되는지 확인해 주세요."

라는 요청이다.

PR 화면에서는 보통 다음을 확인한다.

- 어떤 브랜치에서 어떤 브랜치로 합치는가
- 어떤 파일이 변경되었는가
- 어떤 코드가 추가/삭제되었는가
- 충돌은 없는가
- 리뷰가 필요한가

PR 내용이 이상하거나 아직 합치고 싶지 않다면 **Merge 버튼을 누르지 않으면 된다.** 필요하면 PR을 닫을 수도 있다.

# 4. API란 무엇인가

API는 프로그램과 프로그램이 서로 기능이나 데이터를 주고받기 위한 약속이다.

처음에는 API를 어렵게 생각하기 쉬운데, 식당으로 비유하면 이해하기 쉽다.

```text
사용자
  ↓ 주문
메뉴판/API
  ↓ 요청
주방/서버
  ↓ 결과
사용자
```

사용자는 서버 내부의 모든 코드를 알 필요가 없다.

정해진 방식으로 요청하면 서버가 결과를 돌려준다.

예를 들어 웹 서비스에서 다음과 같은 API가 있을 수 있다.

```text
GET /expenses
```

의미:

```text
저장된 지출 목록을 주세요.
```

또는

```text
POST /expenses
```

의미:

```text
새로운 지출 데이터를 저장해 주세요.
```

즉 API를 아주 간단히 정리하면 다음과 같다.

> 프로그램끼리 대화하기 위해 미리 정해 둔 요청과 응답 규칙

# 9. 지출 데이터는 딕셔너리 하나로 표현

지출 한 건에는 여러 정보가 있다.

```python
expense = {
    "date": "2026-09-01",
    "category": "식비",
    "description": "점심",
    "amount": 12000
}
```

각 항목의 의미는 다음과 같다.

```text
date        → 언제 사용했는가
category    → 어디에 사용했는가
description → 무엇을 샀는가
amount      → 얼마를 사용했는가
```

여러 건을 저장하려면 리스트에 넣을 수 있다.

```python
expenses = [
    {
        "date": "2026-09-01",
        "category": "식비",
        "description": "점심",
        "amount": 12000
    },
    {
        "date": "2026-09-01",
        "category": "교통",
        "description": "버스",
        "amount": 1500
    }
]
```

즉 구조는 다음과 같다.

```text
expenses 리스트
    ↓
지출 딕셔너리
    ↓
date / category / description / amount
```

# 10. 함수를 왜 나눠야 하는가

프로그램 전체를 하나의 긴 코드로 작성하면 수정하기 어려워진다.

따라서 기능별로 함수를 나눈다.

예상 함수는 다음과 같다.

```text
add_expense()              지출 추가
show_expenses()            목록 확인
calculate_total()          전체 합계
calculate_by_category()    카테고리별 합계
save_expenses()            CSV 저장
load_expenses()            CSV 불러오기
```

중요한 원칙은 다음과 같다.

> 함수 하나가 너무 많은 일을 하지 않게 한다.

예를 들어 `calculate_total()`은 합계 계산만 한다.

```python
def calculate_total(expenses):
    total = 0

    for expense in expenses:
        total += expense["amount"]

    return total
```

이렇게 나누면 특정 기능에서 오류가 났을 때 어디를 확인해야 하는지 찾기 쉬워진다.

# 11. 입력 검증과 예외 처리는 다른 문제

사용자가 금액을 입력할 때 모든 입력이 정상적인 것은 아니다.

예를 들어 다음 입력을 생각해 볼 수 있다.

```text
12000
만원
0
-3000
빈 문자열
```

여기서 문제의 종류가 서로 다르다.

## `만원`

```python
int("만원")
```

정수로 변환 자체가 불가능하다.

따라서 `ValueError` 예외가 발생한다.

```python
try:
    amount = int(value)
except ValueError:
    print("금액은 숫자로 입력해 주세요.")
```

## `0`, `-3000`

정수 변환은 가능하다.

하지만 지출 금액이라는 요구사항에는 맞지 않는다.

따라서 조건문으로 검증한다.

```python
if amount <= 0:
    print("금액은 0보다 큰 값이어야 합니다.")
```

정리하면 다음과 같다.

```text
문자로 인해 변환 불가능
→ 예외 처리

숫자이지만 허용하면 안 되는 값
→ 조건문으로 검증
```

# 12. CSV 저장과 불러오기

프로그램 실행 중 리스트에 저장된 데이터는 프로그램을 종료하면 사라진다.

그래서 파일에 저장해야 한다.

이번 프로젝트에서는 CSV를 사용한다.

흐름은 다음과 같다.

```text
Python 리스트
    ↓
CSV 저장
    ↓
expenses.csv
    ↓
프로그램 다시 실행
    ↓
CSV 읽기
    ↓
Python 리스트 복원
```

CSV에 저장된 값은 다시 읽었을 때 문자열로 처리되는 경우가 많다.

특히 `amount`는 계산에 사용해야 하기 때문에 다시 정수로 바꿔야 한다.

```python
row["amount"] = int(row["amount"])
```

이 과정을 하지 않으면 숫자 계산에서 문제가 생길 수 있다.

# 13. FileNotFoundError는 항상 큰 오류가 아니다

프로그램을 처음 실행하면 아직 `expenses.csv`가 없을 수 있다.

이때 파일이 없다고 프로그램이 바로 종료될 필요는 없다.

```text
첫 실행
→ CSV 없음
→ 빈 지출 목록으로 시작
```

즉 파일이 없는 것이 프로그램 요구사항상 정상적인 상황일 수 있다.

이처럼 오류 메시지를 볼 때도 단순히 "오류가 났다"고 판단하기보다 **현재 상황에서 정말 비정상인지** 생각해야 한다.

# 14. 카테고리별 합계 계산

카테고리별 합계는 딕셔너리를 이용해 누적할 수 있다.

예를 들어 다음 지출이 있다고 생각한다.

```text
식비 12,000원
교통 1,500원
식비 8,000원
카페 4,000원
```

결과는 다음이 되어야 한다.

```text
식비 20,000원
교통 1,500원
카페 4,000원
```

중요한 검증 조건도 있다.

```text
전체 지출 합계
=
카테고리별 합계를 모두 더한 값
```

두 값이 다르면 계산이나 저장 과정에 문제가 있다는 뜻이다.

# 15. 웹으로 바꾸어도 Python 로직은 그대로 사용할 수 있다

콘솔 프로그램에서는 사용자가 `input()`으로 값을 입력한다.

웹에서는 HTML 폼에서 값을 입력한다.

하지만 실제 Python의 핵심 로직은 크게 달라지지 않는다.

```text
콘솔
input()
    ↓
Python 함수

웹
HTML form
    ↓
Flask
    ↓
Python 함수
```

즉 웹 프로젝트라고 해서 모든 것을 새로 만드는 것은 아니다.

기존 Python 로직 위에 **웹 입력과 화면 출력 기능을 추가하는 것**에 가깝다.

# 18. AI를 어떻게 사용해야 하는가

이번 과제에서 가장 중요한 부분 중 하나다.

기술적으로는 AI에게 다음처럼 요청하면 전체 프로그램을 만들어 줄 수 있다.

```text
Flask로 개인 지출 관리 프로그램 전체를 만들어 줘.
CSV 저장과 웹페이지 4개까지 전부 구현해 줘.
```

하지만 이렇게 하면 내가 실제 구조를 이해하기 어렵다.

이번 과제에서는 AI를 **전체 코드 생성기보다 튜터와 리뷰어**로 사용하는 것이 적절하다.

좋은 사용 방법의 예시는 다음과 같다.

```text
Flask에서 / 주소로 index.html을 보여 주고 싶다.
전체 프로젝트를 작성하지 말고 필요한 구조와 개념만 설명해 줘.
```

또는 오류가 발생했을 때 다음처럼 물어볼 수 있다.

```text
TemplateNotFound 오류가 발생했다.
전체 코드를 다시 작성하지 말고,
왜 발생했는지와 내가 확인할 위치를 순서대로 알려 줘.
```

코드를 작성한 뒤에는 다음처럼 리뷰를 요청할 수 있다.

```text
내 코드가 아래 요구사항을 만족하는지 확인해 줘.

1. 빠진 요구사항
2. 잘못된 입력 처리 문제
3. CSV 저장/불러오기 문제
4. 부족한 테스트

전체 코드를 다시 작성하지 말고 문제점만 설명해 줘.
```

# 19. AI가 수정 코드를 주더라도 바로 복사하지 않기

AI가 코드를 제안했다고 해서 무조건 맞는 것은 아니다.

다음 순서가 중요하다.

```text
AI 제안 확인
    ↓
왜 바꾸는지 이해
    ↓
한 부분만 수정
    ↓
실행
    ↓
기존 테스트 다시 실행
```

특히 한 기능을 추가한 뒤 기존 기능도 다시 확인해야 한다.

새 기능 때문에 이전에 잘 되던 코드가 깨질 수도 있기 때문이다.

# 20. 테스트할 항목

프로그램이 한 번 실행된다고 완성된 것은 아니다.

최소한 다음 경우를 직접 확인해야 한다.

```text
정상적인 지출 입력
문자 금액 입력
0원 입력
음수 입력
빈 날짜
빈 카테고리
빈 내용
지출 목록이 비어 있는 경우
여러 건의 지출 목록
전체 합계
카테고리별 합계
CSV 저장
프로그램 재실행 후 불러오기
CSV 파일이 없는 첫 실행
잘못된 amount 데이터가 있는 CSV
```

테스트할 때는 먼저 예상 결과를 적는 것이 좋다.

예:

| 입력 | 예상 결과 |
|---|---|
| 12000 | 정상 저장 |
| 만원 | 숫자 입력 안내 |
| 0 | 0보다 큰 값 입력 안내 |
| -3000 | 0보다 큰 값 입력 안내 |
| 빈 카테고리 | 빈 값 입력 안내 |

# 21. 오늘 배운 핵심

오늘 가장 중요했던 내용을 정리하면 다음과 같다.

### 1. GitHub에서는 방향을 먼저 생각한다.

```text
내 컴퓨터 → GitHub = push
GitHub → 내 컴퓨터 = pull
브랜치 → main 합치기 요청 = Pull Request
```

### 2. API는 프로그램끼리 대화하는 규칙이다.

```text
요청
→ API
→ 서버 처리
→ 응답
```

### 3. 프로젝트는 코드보다 요구사항부터 정한다.

```text
요구사항
→ 데이터 구조
→ 함수
→ 화면
→ 테스트
```

### 4. 데이터는 리스트와 딕셔너리로 구조화할 수 있다.

```text
리스트
└─ 지출 딕셔너리
   ├─ date
   ├─ category
   ├─ description
   └─ amount
```

### 5. 입력 검증과 예외 처리를 구분한다.

```text
만원 → ValueError
0원 → 조건식 검증
-3000원 → 조건식 검증
```

### 6. CSV는 프로그램을 종료해도 데이터를 남기기 위해 사용한다.

```text
리스트 → CSV → 다시 리스트
```

### 7. AI는 전체 프로젝트를 대신 만드는 용도보다 리뷰와 디버깅에 활용한다.

```text
내가 작성
→ AI 리뷰
→ 이유 확인
→ 한 부분 수정
→ 다시 테스트
```

## 오늘의 결론

오늘은 새로운 코드를 많이 작성하기보다 **프로젝트를 어떤 순서로 만들 것인지 구조를 잡는 과정**이 중심이었다.

GitHub 협업에서는 `push`, `pull`, `fetch`, Pull Request의 방향을 다시 정리했고, API는 프로그램끼리 통신하는 약속이라는 점을 복습했다.

개인 지출 관리 프로젝트에서는 요구사항을 먼저 정하고, 지출 데이터를 리스트와 딕셔너리로 표현하며, 기능을 함수별로 나누고, CSV에 저장한 뒤 Flask를 통해 웹 화면을 붙이는 방향으로 설계했다.

특히 이번 프로젝트에서는 AI에게 전체 결과물을 한 번에 맡기기보다 **내가 직접 코드를 작성하고 AI는 설명, 오류 분석, 코드 리뷰, 테스트 보조 역할로 사용하는 것이 핵심**이다.
