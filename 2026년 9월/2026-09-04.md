# 1. PostgreSQL과 DBeaver는 같은 프로그램이 아니다

오늘 실습하면서 가장 먼저 다시 잡은 개념은 PostgreSQL과 DBeaver의 역할 차이다.

```text
PostgreSQL
→ 데이터를 실제로 저장하고 SQL을 실행하는 DBMS

DBeaver
→ PostgreSQL에 연결해 SQL을 작성하고 결과를 보여 주는 클라이언트
```

즉 DBeaver는 데이터베이스 자체가 아니다.

흐름으로 보면 다음과 같다.

```text
사용자
  ↓
DBeaver에서 SQL 작성
  ↓
PostgreSQL에 SQL 전달
  ↓
PostgreSQL이 SQL 실행
  ↓
DBeaver가 결과 또는 오류 표시
```

DBeaver를 종료해도 PostgreSQL 서버와 저장된 데이터가 사라지는 것은 아니다.

# 2. 현재 내가 어디에 연결되어 있는지 SQL로 확인

오늘 다음 SQL을 직접 실행했다.

```sql
SELECT version();
SELECT current_database();
SELECT current_user;
SELECT current_schema();
SHOW search_path;
```

확인한 값은 다음과 같았다.

```text
PostgreSQL 버전: PostgreSQL 18.4
현재 데이터베이스: postgres
현재 사용자: postgres
현재 스키마: public
search_path: public, "$user"
```

여기서 다시 정리한 구조는 다음과 같다.

```text
PostgreSQL DBMS
  ↓
Database
  ↓
Schema
  ↓
Table
  ↓
Row / Column
```

`public`은 데이터베이스 그 자체가 아니라 **데이터베이스 안에 존재하는 스키마**다.

`search_path`는 스키마 이름을 생략했을 때 PostgreSQL이 객체를 찾는 순서를 의미한다.

# 3. TEMP TABLE로 테이블의 의미 직접 확인

오늘은 다음 세 개의 임시 테이블을 만들었다.

```text
ch02_students
ch02_courses
ch02_enrollments
```

각 테이블의 한 행 의미는 다음처럼 정리했다.

```text

```

테이블을 볼 때 단순히 컬럼 이름만 보는 것이 아니라 **한 행이 무엇을 의미하는지 먼저 정하는 것**이 중요하다는 점을 다시 확인했다.

# 4. 내부 식별자와 업무 식별자는 다르다

`ch02_students`에서는 다음 두 값을 구분했다.

```text
id
→ DB 내부에서 학생 행을 구분하는 내부 식별자

student_number
→ 학교 업무에서 실제로 사용하는 학번
```

두 값이 모두 학생을 구분하는 데 쓰일 수 있지만 목적은 다르다.

학번은 실제 업무 규칙에 따라 형식이 바뀔 수 있고, 앞자리 `0`이 포함될 수도 있다.

그래서 학번을 숫자로 계산할 이유가 없다면 문자열로 저장하는 것이 자연스럽다.

예를 들어:

```text
00123456
```

이 값을 숫자로 처리하면 앞의 0이 사라질 수 있다.

# 5. 테이블과 SELECT 결과는 같은 것이 아니다

오늘 `ch02_students`에는 총 3명의 학생이 있었다.

하지만 다음처럼 조건을 걸었다.

```sql
SELECT id, student_number, name, major
FROM ch02_students
WHERE major = '컴퓨터공학'
ORDER BY id;
```

결과는 2행만 나왔다.

중요한 점은 **조회 결과가 2행이라고 해서 원본 테이블에서 1행이 삭제된 것이 아니라는 것**이다.

```text
원본 테이블
→ 3행

WHERE 조건을 적용한 Result Set
→ 2행
```

SELECT는 원본 데이터를 바꾸는 것이 아니라 필요한 행과 열을 골라 결과 집합으로 보여 준다.

---

# 6. ORDER BY를 사용하지 않으면 현재 순서를 믿으면 안 된다

이름을 오름차순과 내림차순으로 정렬해 보았다.

```sql
SELECT id, name
FROM ch02_students
ORDER BY name ASC;

SELECT id, name
FROM ch02_students
ORDER BY name DESC;
```

직접 결과를 비교하면서 확인한 점은 다음과 같다.

```text
정렬 기준이 필요한 경우 반드시 ORDER BY를 적는다.

현재 화면에 보이는 행 순서를 원래 테이블 순서라고 가정하면 안 된다.
```

특히 실제 서비스나 분석에서는 ‘최근 주문’, ‘금액이 큰 순’, ‘이름순’처럼 순서 자체가 업무 의미가 될 수 있기 때문에 정렬 기준을 명시하는 것이 중요하다.

# 7. PK 중복 오류를 직접 확인

다음 INSERT를 실행해 이미 존재하는 `id=1`을 다시 넣어 보았다.

```sql
INSERT INTO ch02_students (id, student_number, name, major)
VALUES (1, '20269999', '새학생', '경영학');
```

실행 결과는 실패였다.

확인한 오류의 핵심은 다음과 같다.

```text
SQL Error [23505]
ch02_students_pkey
중복된 키 값
(id)=(1) 키가 이미 있음
```

여기서 확인한 점:

```text
PK는 같은 테이블 안에서 각 행을 고유하게 구분한다.

따라서 같은 PK 값을 두 행에서 동시에 사용할 수 없다.
```

오류 메시지를 직접 보고 나니 PK의 ‘고유성’이 단순한 정의가 아니라 실제 DBMS가 강제로 지키는 규칙이라는 점이 확실해졌다.

# 8. FK 참조 오류도 직접 확인

이번에는 존재하지 않는 학생을 수강신청에서 참조하도록 했다.

```sql
INSERT INTO ch02_enrollments (id, student_id, course_id, status)
VALUES (1004, 999, 10, '신청');
```

하지만 `ch02_students`에는 `id=999`인 학생이 없었다.

실행 결과:

```text
SQL Error [23503]
ch02_enrollments_student_id_fkey
foreign key 제약조건 위반
(student_id)=(999) 키가 ch02_students에 없음
```

여기서 FK의 의미를 다시 정리했다.

```text
PK
→ 자기 테이블의 행을 고유하게 구분

FK
→ 다른 테이블의 행을 참조해서 관계를 연결
```

FK는 부모 테이블에 실제 존재하는 값을 참조해야 한다.

---

# 9. FK는 중복될 수 있다

처음 배우면 PK와 FK가 모두 ‘키’라서 둘 다 중복되면 안 된다고 착각하기 쉽다.

하지만 오늘 실습에서 다음 구조를 확인했다.

```text
students 1 ── N enrollments N ── 1 courses
```

학생 한 명이 여러 강의를 신청할 수 있기 때문에 `enrollments.student_id`는 반복될 수 있다.

강의 하나를 여러 학생이 신청할 수 있기 때문에 `enrollments.course_id`도 반복될 수 있다.

따라서 다음과 같은 반복은 정상이다.

```text
student_id = 1
student_id = 1
student_id = 2
```

FK의 반복 여부는 관계의 구조를 봐야 한다.

# 10. 1:N과 N:M 관계

학생과 수강신청 관계:

```text
학생 한 명
→ 여러 수강신청 가능

students 1 : N enrollments
```

강의와 수강신청 관계:

```text
강의 한 개
→ 여러 수강신청 가능

courses 1 : N enrollments
```

학생과 강의를 바로 보면:

```text
학생 한 명은 여러 강의를 들을 수 있음
강의 한 개에는 여러 학생이 참여할 수 있음
```

그래서 학생과 강의는 N:M 관계로 볼 수 있다.

이를 `enrollments`가 중간에서 연결하면서 두 개의 1:N 관계로 풀어 주는 구조가 된다.

# 11. AI가 만든 테이블 구조도 그대로 믿으면 안 된다

오늘 다음과 같은 테이블을 AI에게 검토시켰다.

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),
    student_email VARCHAR(100),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50)
);
```

검토하면서 먼저 직접 찾은 문제는 다음과 같았다.

```text
1. 각 행을 고유하게 구분할 PK가 없음
2. 학생 이름만으로 학생을 안정적으로 구분하기 어려움
3. 강의 제목만으로 강의를 안정적으로 구분하기 어려움
4. 학생·강의·강사 정보가 한 테이블에 섞여 반복 저장될 가능성이 큼
```

AI에게도 다음 관점으로 검토를 요청했다.

```text
한 행의 의미가 명확한가?
PK가 필요한가?
내부 식별자와 업무 식별자를 구분해야 하는가?
FK 후보는 무엇인가?
중복 저장 위험이 있는가?
현재 요구사항만으로 결정할 수 없는 정책은 무엇인가?
```

AI 답변은 참고용으로 사용하고, 실제로 내가 판단해야 하는 부분은 따로 남겼다.

특히 이메일 고유 여부, 재수강 가능 여부, 강의당 강사 수, 삭제 정책 같은 내용은 요구사항이 없는데 임의로 확정하면 안 된다.

# 15. 행, 열, 값, 인덱스

DataFrame에서 각 요소의 의미를 다시 정리했다.

```text
행(row)
→ 하나의 관측 대상 또는 사건 한 건

열(column)
→ 대상의 속성

값(value)
→ 특정 행과 열이 만나는 실제 데이터

인덱스(index)
→ DataFrame 내부에서 행 위치를 구분하는 표지
```

예를 들어 고객 데이터라면:

```text
한 행 = 고객 한 명
customer_id = 고객 식별 번호
age = 나이
city = 거주 도시
```

# 16. DataFrame index와 업무용 ID는 다르다

이 부분은 오늘 DB에서 배운 ‘내부 식별자와 업무 식별자’와도 연결됐다.

```text
DataFrame index
→ pandas가 자동 생성할 수 있음
→ 현재 DataFrame에서 행 위치를 표현
→ reset_index() 등으로 변경 가능

customer_id 같은 업무용 ID
→ 실제 고객을 식별
→ 다른 파일과 연결하는 키가 될 수 있음
→ 고유성과 결측 여부를 따로 점검해야 함
```

따라서:

```text
DataFrame index가 고유하다
≠
customer_id가 고유하다
```

이 차이를 꼭 구분해야 한다.

# 18. 보이는 값과 실제 dtype은 다를 수 있다

화면에 다음 값이 보인다고 가정한다.

```text
2026-08-05
```

사람 눈에는 날짜처럼 보이지만 pandas에서는 다음처럼 읽힐 수 있다.

```text
object
```

문자열 상태에서는 날짜 차이 계산이나 월별 집계가 제한될 수 있다.

또 다음 값들도 겉보기에는 숫자처럼 보이지만 바로 계산하지 못할 수 있다.

```text
"12,000"
" 35 "
"unknown"
"₩5000"
```

변환 전에는 쉼표, 통화 기호, 공백, 오류 코드, 빈 문자열 등을 먼저 확인해야 한다.

# 19. 결측치와 중복은 발견 즉시 삭제하지 않는다

Chapter 03에서 특히 중요한 원칙은 다음과 같았다.

```text
결측치를 발견했다고 즉시 삭제하지 않는다.

중복을 발견했다고 모든 행을 제거하지 않는다.
```

먼저 다음을 확인해야 한다.

```text
어느 파일인가?
어느 컬럼인가?
몇 건인가?
업무적으로 정상일 수 있는가?
```

예를 들어 `order_items.order_id`가 반복된다고 해서 오류는 아니다.

주문 한 건에 여러 상품이 들어갈 수 있기 때문에 같은 `order_id`가 여러 주문상세 행에 반복되는 것이 정상일 수 있다.

이 부분은 오늘 DB에서 확인한 **FK는 1:N 관계에서 반복될 수 있다**는 내용과 정확히 연결된다.

# 20. 쇼핑몰 데이터 4개 파일의 역할

Chapter 03에서는 다음 네 개의 CSV를 기준으로 설명했다.

```text
customers.csv
→ 고객 한 명

products.csv
→ 상품 한 개

orders.csv
→ 주문 한 건

order_items.csv
→ 주문에 포함된 상품 한 항목
```

연결 관계는 다음과 같다.

```text
customers.customer_id
        ↓
orders.customer_id

orders.order_id
        ↓
order_items.order_id

products.product_id
        ↓
order_items.product_id
```

여기에서도 부모 데이터의 주요 ID는 보통 고유해야 하고, 자식 데이터의 FK는 반복될 수 있다.

# 21. 분석 질문에 따라 필요한 파일이 달라진다

모든 분석에서 모든 CSV를 사용할 필요는 없다.

예를 들어:

```text
고객 수
→ customers

상품 카테고리 수
→ products

주문 상태별 주문 수
→ orders

상품별 판매 수량
→ order_items + products

고객별 구매 금액
→ customers + orders + order_items

지역별 카테고리 매출
→ 네 파일 모두
```

즉 분석 질문을 먼저 정하면 필요한 파일과 연결 키가 결정된다.

# 22. 오늘 DB 실습과 데이터 분석 수업이 연결된 부분

오늘 가장 크게 느낀 점은 DB 수업과 pandas 데이터 분석 수업이 서로 따로 노는 내용이 아니라는 것이다.

DB에서는:

```text
PK
FK
1:N
N:M
테이블의 한 행 의미
내부 식별자와 업무 식별자
```

를 배웠다.

데이터 분석에서는:

```text
업무용 ID 고유성 점검
부모-자식 파일 관계
중복 ID가 정상인지 판단
파일 간 연결 키 확인
한 행의 의미 확인
```

를 배웠다.

결국 둘 다 핵심은 같다.

```text
데이터가 무엇을 의미하는지 먼저 이해하고
그다음 연결·조회·분석을 해야 한다.
```

# 23. 오늘 다시 확인한 실습 원칙

```text
1. SQL 실행 전 현재 Database와 Schema를 확인한다.
2. SQL 오류 메시지는 생략하지 않고 읽는다.
3. PK와 FK를 이름만 외우지 말고 실제 오류로 확인한다.
4. FK가 반복된다고 바로 오류라고 판단하지 않는다.
5. 한 행의 의미를 먼저 정의한다.
6. AI가 제안한 구조는 실제 요구사항과 데이터 기준으로 검토한다.
7. CSV가 열렸다고 바로 분석하지 않는다.
8. shape → head/tail → columns → info/dtypes 순서로 구조를 먼저 본다.
9. 결측과 중복은 발견 단계와 처리 단계를 구분한다.
10. LLM 설명도 실제 SQL과 데이터 실행 결과로 검증한다.
```

# 오늘의 정리

오늘은 단순히 SQL 문법 몇 개를 실행한 것이 아니라 **데이터를 구조적으로 보는 법**을 조금 더 익혔다.

가장 기억에 남는 내용은 다음 세 가지다.

```text
첫째,
PK는 자기 테이블의 행을 고유하게 구분하고
FK는 다른 테이블의 행과 관계를 연결한다.

둘째,
FK나 업무용 ID의 중복은 무조건 오류가 아니라
데이터 관계와 한 행의 의미를 기준으로 판단해야 한다.

셋째,
CSV나 테이블을 불러오는 데 성공했다고 분석 준비가 끝난 것이 아니라
구조, 타입, 결측, 중복, 키, 관계를 먼저 점검해야 한다.
```

오늘 실습을 통해 PostgreSQL의 관계 개념과 pandas의 데이터 점검 개념이 서로 이어져 있다는 점을 이해했다.
