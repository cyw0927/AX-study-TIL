# 1. 데이터 전처리의 목표

오늘 수업에서 가장 중요했던 내용은 전처리를 단순한 데이터 정리 작업으로 보면 안 된다는 점이었다.

전처리 과정은 다음 흐름으로 진행한다.

```text
원본 확인
↓
전처리 전 상태 기록
↓
문자열 정리
↓
숫자·날짜 변환
↓
변환 실패 확인
↓
결측 처리 기준 결정
↓
중복·범주·이상값 확인
↓
파생 컬럼 생성
↓
PK/FK 관계 재검증
↓
processed 데이터 저장
↓
같은 과정을 다시 실행해 재현성 확인
```

핵심은 **왜 이 데이터를 바꿨는지 설명할 수 있어야 하고, 바꾼 뒤 무엇이 달라졌는지 확인할 수 있어야 한다는 것**이다.

# 2. 원본은 직접 수정하지 않는다

전처리 전에 원본 상태를 먼저 확인한다.

```python
raw_data = {
    "customers": customers,
    "products": products,
    "orders": orders,
    "order_items": order_items,
}

for name, df in raw_data.items():
    print(name)
    print("shape:", df.shape)
    print("missing:", int(df.isna().sum().sum()))
    print("duplicated rows:", int(df.duplicated().sum()))
```

이후 실제 전처리는 복사본에서 진행한다.

```python
customers_clean = customers.copy()
products_clean = products.copy()
orders_clean = orders.copy()
order_items_clean = order_items.copy()
```

즉 원칙은 다음과 같다.

```text
raw 원본 덮어쓰기 X
clean 복사본에서 처리 O
```

원본을 남겨두면 전처리 전후를 비교할 수 있고, 문제가 생겼을 때 다시 시작할 수도 있다.

# 3. 문자열 공백과 빈 문자열 처리

문자열 데이터는 눈으로 보기에는 같아 보여도 앞뒤 공백 때문에 다른 값으로 처리될 수 있다.

예를 들어 다음 값들은 실제로는 서로 다른 문자열이다.

```text
"서울"
" 서울"
"서울 "
```

그래서 `.str.strip()`을 사용해 앞뒤 공백을 제거한다.

```python
result[column] = result[column].where(
    result[column].isna(),
    result[column].astype(str).str.strip(),
)
```

그리고 공백 제거 후 빈 문자열은 실제 결측치로 바꿀 수 있다.

```python
result[column] = result[column].replace("", pd.NA)
```

중요한 점은 문자열을 정리한 뒤 반드시 다시 결측치를 확인해야 한다는 것이다.

```python
customers_clean.isna().sum()
```

공백만 있던 값이 `pd.NA`로 바뀌면서 새로운 결측으로 드러날 수 있기 때문이다.

# 4. 숫자와 날짜는 변환 후 실패 건수를 확인한다

숫자형 변환:

```python
products_clean["price"] = pd.to_numeric(
    products_clean["price"],
    errors="coerce",
)
```

날짜형 변환:

```python
orders_clean["order_date"] = pd.to_datetime(
    orders_clean["order_date"],
    errors="coerce",
)
```

여기서 `errors="coerce"`를 사용하면 변환할 수 없는 값이 `NaN` 또는 `NaT`로 바뀐다.

따라서 코드가 오류 없이 실행됐다고 해서 모든 값이 정상 변환됐다고 생각하면 안 된다.

반드시 다음처럼 실패 건수를 확인해야 한다.

```python
print(products_clean["price"].isna().sum())
print(orders_clean["order_date"].isna().sum())
```

즉:

```text
코드 실행 성공
≠
데이터 변환 성공
```

# 5. 결측치는 무조건 삭제하거나 채우는 것이 아니다

결측치가 있다고 해서 무조건 삭제하거나 평균값으로 채우면 안 된다.

예를 들어 나이 결측치는 중앙값 대체를 검토할 수 있다.

```python
age_median = customers_clean["age"].median()
customers_clean["age"] = customers_clean["age"].fillna(age_median)
```

도시는 별도 범주로 처리할 수도 있다.

```python
customers_clean["city"] = customers_clean["city"].fillna("Unknown")
```

하지만 다음처럼 업무적으로 중요한 값들은 함부로 대표값으로 채우면 안 된다.

```text
고유 ID
핵심 날짜
금액
업무 상태
```

결측치를 처리할 때는 항상 다음 질문을 같이 생각해야 한다.

```text
왜 삭제하지 않았는가?
왜 이 값으로 대체했는가?
대체로 인해 데이터가 왜곡될 가능성은 없는가?
```

# 6. 전체 행 중복과 키 중복은 다르다

전체 중복은 다음처럼 확인한다.

```python
df.duplicated().sum()
```

하지만 이것만 확인해서는 부족하다.

각 테이블의 고유 ID 중복도 별도로 확인해야 한다.

```text
customers → customer_id
products → product_id
orders → order_id
order_items → order_item_id
```

중요한 차이는 다음과 같다.

```text
완전히 같은 행 반복
≠
고유 ID 중복
≠
1:N 관계에서 정상적으로 반복되는 FK
```

예를 들어 `order_items.order_id`는 한 주문에 상품이 여러 개 들어갈 수 있기 때문에 반복되는 것이 정상이다.

# 7. 범주값 표준화

주문 상태처럼 같은 의미를 여러 표현으로 입력할 수 있는 데이터는 표준화가 필요하다.

먼저 현재 값 분포를 확인한다.

```python
orders_clean["order_status"].value_counts(dropna=False)
```

업무적으로 같은 의미라는 것이 확인된 경우에만 매핑한다.

```python
status_map = {
    "complete": "completed",
    "완료": "completed",
    "cancel": "cancelled",
    "취소": "cancelled",
    "refund": "refunded",
    "환불": "refunded",
}
```

중요한 점은 비슷해 보인다고 임의로 합치는 것이 아니라 **실제 업무 의미가 같은 경우에만 표준화**해야 한다는 것이다.

# 8. 이상값 후보는 자동 삭제 대상이 아니다

다음과 같은 값들을 이상값 후보로 확인할 수 있다.

```python
customers_clean.loc[
    (customers_clean["age"] < 0)
    | (customers_clean["age"] > 120)
]

products_clean.loc[products_clean["price"] <= 0]
order_items_clean.loc[order_items_clean["quantity"] <= 0]
order_items_clean.loc[order_items_clean["unit_price"] <= 0]
```

하지만 이상해 보이는 값이 반드시 오류라는 뜻은 아니다.

```text
0원 상품 → 증정품일 수 있음
음수 수량 → 반품일 수 있음
0원 단가 → 프로모션일 수 있음
```

따라서:

```text
이상값 후보
≠
자동 삭제 대상
```

업무 의미를 확인한 뒤 처리해야 한다.

# 9. 파생 컬럼 생성

날짜 데이터를 활용해 주문 월과 요일을 만들 수 있다.

```python
orders_clean["order_month"] = (
    orders_clean["order_date"]
    .dt.to_period("M")
    .astype(str)
)
```

```python
orders_clean["order_dayofweek"] = (
    orders_clean["order_date"].dt.day_name()
)
```

주문상세에서는 금액을 계산한다.

```python
order_items_clean["line_total"] = (
    order_items_clean["quantity"]
    * order_items_clean["unit_price"]
)
```

여기서 `line_total`은 주문 전체 금액이 아니라 **주문상세 한 행의 금액**이다.

전체 합계를 바로 회계상 매출로 해석하면 안 된다.

# 10. 전처리 후 PK/FK를 다시 확인해야 한다

전처리를 하기 전에는 관계가 정상이었더라도 데이터 수정 과정에서 관계가 깨질 수 있다.

확인할 관계는 다음과 같다.

```text
orders.customer_id → customers.customer_id
order_items.order_id → orders.order_id
order_items.product_id → products.product_id
```

즉 전처리 후에는 다음을 다시 확인해야 한다.

```text
존재하지 않는 customer_id가 생겼는가?
존재하지 않는 order_id가 생겼는가?
존재하지 않는 product_id가 생겼는가?
```

데이터 각각이 깨끗해 보여도 테이블끼리 연결이 깨져 있으면 이후 분석에서 문제가 발생한다.

# 14. LLM의 전처리 제안도 검증해야 한다

LLM에게 실제 고객 원본 데이터를 모두 넘기지 않고 구조와 품질 요약만 제공한다.

예를 들어:

```text
customers 데이터 품질 요약
- rows: 150
- customer_id missing/duplicate: 0 / 0
- age missing: 3
- city missing: 2
```

LLM이 처리 방법을 제안하더라도 다음을 사람이 확인해야 한다.

```text
raw 데이터를 덮어쓰지 않는가?
변환 실패를 확인하는가?
결측 처리 근거가 있는가?
키 중복을 자동 삭제하지 않는가?
이상값을 자동 삭제하지 않는가?
처리 후 관계를 다시 검증하는가?
전후 변화를 기록하는가?
```

LLM의 답은 참고 의견이고 최종 전처리 기준은 사람이 결정한다.

# 15. 코드만 실행되는 Notebook은 완성된 분석이 아니다

Chapter 05 과제에서는 코드와 결과뿐 아니라 다음 내용도 함께 작성해야 한다.

```text
결과 관찰
→ 실제로 무엇이 나왔는가?

나의 해석과 판단
→ 왜 이 처리 기준을 선택했는가?

업무·분석적 의미
→ 이후 분석에 어떤 영향을 주는가?

한계와 추가 확인 사항
→ 현재 데이터만으로 확신할 수 없는 부분은 무엇인가?
```

예를 들어 단순히:

```text
결측치를 처리했다.
```

라고 쓰는 것보다:

```text
age 결측치가 존재했고, 행 삭제 시 표본 감소가 발생할 수 있어 중앙값 대체를 선택했다.
다만 연령 분포가 중앙에 몰릴 수 있어 실제 업무에서는 결측 원인을 추가 확인해야 한다.
```

처럼 처리 이유와 한계를 같이 설명하는 것이 더 중요하다.

# 오늘 배운 점

오늘 가장 크게 느낀 점은 **전처리는 데이터를 깨끗하게 만드는 작업이 아니라 분석 결과를 믿을 수 있게 만드는 작업**이라는 것이다.

전처리에서 중요한 것은 다음 세 가지다.

```text
1. 원본을 보존할 것
2. 처리 기준과 이유를 기록할 것
3. 처리 전후와 재실행 결과를 검증할 것
```

또 결측치, 중복, 이상값처럼 겉으로 문제가 있어 보이는 데이터도 업무 의미를 모르면 함부로 삭제하거나 수정하면 안 된다.

앞으로 pandas 분석을 할 때도 단순히 코드가 실행됐다는 것보다 **내가 무엇을 바꿨고, 왜 바꿨고, 그 결과가 다시 재현되는지**를 확인하는 습관이 중요할 것 같다.
