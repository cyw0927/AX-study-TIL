## 1. GET과 POST는 데이터 전달 위치가 다르다

일반적인 API 설계에서 GET은 정보를 조회할 때, POST는 서버에 데이터를 보내 특정 작업을 처리하도록 요청할 때 자주 사용한다.

| 구분 | GET의 일반적 사용 | POST의 일반적 사용 |
| --- | --- | --- |
| 주요 용도 | 목록·상세 조회, 검색 | 생성·제출·처리 요청 |
| 입력 위치 | URL의 Path·Query Parameter | 주로 Request Body |
| 예시 | `GET /members?name=kim` | `POST /members`와 JSON Body |
| 주소에 보이는 정보 | Query 문자열이 URL에 포함됨 | Body는 일반적으로 URL에 직접 표시되지 않음 |
| 데이터베이스 저장 | Method 자체가 저장을 결정하지 않음 | Method 자체가 저장을 보장하지 않음 |

중요한 점은 **GET도 요청에 정보를 전달할 수 있고 POST에도 URL Query가 포함될 수 있다**는 것이다. Method와 데이터 전달 위치가 일대일로 고정되는 것은 아니다.

## 2. Query Parameter와 Request Body 비교

GET 검색 요청 예:

```http
GET /members?name=kim&min_age=20 HTTP/1.1
Host: example.com
```

위 요청의 Query Parameter는 다음 두 개다.

```text
name = kim
min_age = 20
```

POST 회원 생성 요청 예:

```http
POST /members HTTP/1.1
Host: example.com
Content-Type: application/json

{"name":"Kim","email":"kim@example.com","age":25}
```

여기서는 Body에 JSON 데이터가 들어간다.

기존 FastAPI 수업에서 배운 `GET /members?name=kim`과 `POST /members`의 차이를 다시 이해할 수 있었다.

## 3. GET 요청에는 몇 글자까지 담을 수 있을까?

**HTTP 표준이 모든 서비스에 공통으로 적용되는 GET URL 최대 글자 수 하나를 정해 놓지는 않는다.**

실제로는 다음 요소들이 각자의 제한을 설정할 수 있다.

- 브라우저와 HTTP 클라이언트
- 웹 서버
- 리버스 프록시
- API Gateway와 CDN
- 애플리케이션 프레임워크 및 서버 설정

RFC 9110·9112에서는 상호운용성을 위해 **최소 8,000옥텟 정도의 URI 또는 요청줄 지원을 권고**하지만, 이것이 GET의 무조건적인 최대 용량이나 모든 서버의 보장값이라는 의미는 아니다.

URL이 서버가 받아들일 수 있는 길이를 넘어가면 일반적으로 다음 상태를 반환할 수 있다.

```http
414 URI Too Long
```

문자 수와 전송 바이트 수는 같지 않을 수 있다. 특히 한글 등은 URL 인코딩을 거치면서 더 많은 바이트를 사용할 수 있다.

## 4. POST Request Body의 최대 크기

POST 역시 **HTTP Method 자체에 고정된 전 세계 공통 최대 크기가 있는 것은 아니다.**

실제 한도는 서버·프록시·애플리케이션 설정, 업로드 정책, 서비스 요금제 등 구현 환경에 달려 있다.

예를 들어 파일 업로드 API가 10MB까지만 허용하도록 설정됐다면 그 제한은 서비스의 설정이며 POST라는 Method의 본질적인 상한이 아니다.

Body가 허용 크기를 초과하면 서버는 다음 상태를 반환할 수 있다.

```http
413 Content Too Large
```

이전 자료에서는 `413 Payload Too Large`라는 이름도 사용한다.

**정리:** GET은 URL 길이 문제가 먼저 나타나기 쉽고, POST는 서버가 정한 Body 크기·업로드 한도를 따져야 한다.

## 5. 요청을 많이 보내면 Query Parameter가 계속 생길까?

오늘 궁금했던 핵심은 **질문을 많이 하면 GET Parameter 조합이 무한히 생기고, 한 번 생성한 조합은 사라지지 않는지**였다.

정답은 **그렇지 않다**이다.

- Query Parameter는 요청 URL에 그때그때 포함되는 값이다.
- 요청이 100번 발생했다고 서버 내부에 Query Parameter 정의가 100개씩 영구 추가되는 것은 아니다.
- 같은 Endpoint에서 다양한 검색값을 받을 수 있으므로 조합 가능한 값은 많을 수 있지만, **가능한 조합의 수와 실제 저장된 데이터의 수는 다른 문제**다.
- API가 처리한 요청 URL을 로그·분석·캐시에 기록할 수는 있으나, 이것은 서버의 별도 저장 정책에 따른다.
- 로그 보존 기간, 캐시 만료, DB 저장, 브라우저 방문 기록은 각기 다른 동작이다.

즉 다음을 구분해야 한다.

```text
Query Parameter = 이번 HTTP 요청에 붙은 값
Server Log      = 서버가 요청 이력을 따로 남기는 기록
Cache           = 일정 조건에서 응답을 재사용하기 위한 보관
Database        = 프로그램이 명시적으로 저장한 데이터
```

또한 **채팅에 질문을 입력한다고 그 입력이 전부 GET Query Parameter로 바뀌는 것도 아니다.** 실제 요청 구조는 해당 서비스의 API와 클라이언트 구현에 따라 달라진다.

## 6. GET과 POST를 데이터 보안 관점에서 생각하기

GET Query는 URL에 표시되므로 브라우저 기록, 로그, 일부 분석 시스템 등에 남을 수 있다. 따라서 비밀번호·API Key처럼 민감한 값을 일반적인 Query 문자열에 넣는 설계는 피해야 한다.

POST Body는 주소창에 직접 드러나지 않지만, **POST라고 해서 자동 암호화·비공개·영구 보존이 보장되는 것도 아니다.**

- 네트워크 구간 보호에는 HTTPS가 중요하다.
- 서버가 Body를 기록하는지 여부는 별도의 로깅 정책에 달려 있다.
- 서버가 DB에 저장하는지 여부는 Endpoint 구현에 달려 있다.

## 7. 기존 FastAPI 수업과 연결

이미 학습한 API 설계의 세 입력 위치:

```text
Path Parameter
  /members/3
  → 특정 자원 식별

Query Parameter
  /members?name=kim
  → 검색·필터 조건

Request Body
  POST /members + JSON
  → 여러 필드를 구조적으로 전달
```

앞선 백엔드 Chapter 02·03에서 사용했던 패턴을 다시 비교한 것이다.

아래는 **이해를 돕기 위한 예시 코드**이며, 오늘 새로 작성·실행·테스트했다고 주장하지 않는다.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class MemberCreate(BaseModel):
    name: str
    age: int

@app.get("/members")
def search_members(name: str | None = None):
    return {"search_name": name}

@app.post("/members")
def create_member(member: MemberCreate):
    return {"received": member.model_dump()}
```
