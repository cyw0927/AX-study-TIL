## 2. T23 — 직무·기술 탐색 화면

오늘 병합한 PR: [#148 — 직무·기술 탐색 화면](https://github.com/ai-career-platform/ai-career-platform/pull/148)

화면 경로는 `/job-roles`다.

구현한 기능:

- 직무 이름 검색, `?q=` 검색어 URL 유지
- 커서 기반 페이지 이동
- 직무 상세 및 요구 기술 목록
- 요구 기술의 수준(1~5단계) 표시
- 로그인했을 때 `GET /v1/me/skills`로 내 보유 기술 조회
- 요구 수준과 보유 수준의 **단순 수치 비교**
- 검색 중 로딩, 결과 없음, 오류 재시도 표시
- 늦게 도착한 이전 API 응답 무시
- 검색어를 바꿀 때 첫 페이지로 복귀
- 모바일 너비 375px에서 가로 넘침 점검

보유 기술 비교 상태를 다음처럼 나눴다.

| 비교 결과 | 의미 |
| --- | --- |
| 충족 | 내 숙련도가 요구 수준 이상 |
| 부족(N단계) | 요구 수준보다 N단계 낮음 |
| 숙련도 미입력 | 기술은 있으나 `proficiency`가 비어 있음 |
| 보유 기술에 없음 | 내 기술 목록에 해당 항목 자체가 없음 |

**숙련도 미입력을 0으로 임의 변환하거나, 보유하지 않은 기술과 같은 의미로 처리하지 않았다.** 또 이 화면은 T26 AI Skill Gap 계산 결과가 아니라 단순 요구 수준 비교라는 사실을 명시했다.

### 백엔드 API가 지원하지 않는 기능은 꾸며내지 않기

T17 직무 목록 API는 현재 `q`, `limit`, `cursor`를 지원하고, 목록 항목에 제한된 필드만 제공한다.

따라서 다음 기능은 실제 API 계약 없이 임의 구현하지 않았다.

- 분야별 전체 직무 필터
- 전체 검색 결과 정렬
- 기술 이름으로 직무 찾기
- 목록 카드에 없는 설명·기술 칩을 임의 생성하기

현재 받아 온 한 페이지에서만 필터링하면 전체 검색 결과를 보여 주는 것처럼 오해를 줄 수 있기 때문이다.

## 3. T24 — 기업·채용공고 탐색 화면

오늘 병합한 PR: [#150 — 기업·채용공고 탐색 화면](https://github.com/ai-career-platform/ai-career-platform/pull/150)

화면 경로는 `/job-postings`다.

주요 구현:

- 모집 중만 보기 / 마감 공고 포함
- 최신 등록순 / 마감 임박순
- 커서 기반 다음·이전 페이지 이동
- URL에 검색·필터·정렬 상태 보존
- 기업 둘러보기 카드(8개와 전체 보기)
- 채용공고 상세의 필수·우대 기술 및 요구 수준
- 기업 소개, 진행 중 공고 수, 웹사이트 표시
- 목록·상세·기업 각각 로딩·빈 결과·오류 재시도
- 요청 순서가 바뀌었을 때 오래된 응답 무시

대표 URL 상태:

```text
q       = 검색어
company = 기업 조건
role    = 직무 조건
closed  = 마감 공고 포함 여부
order   = 정렬 기준
```

검색 조건을 URL에 유지하면 새로고침하거나 주소를 공유해도 조건을 복원할 수 있다.

### 데이터 출처를 표시할 때 지킨 원칙

- API에 게시일·마감일이 없으면 임의 날짜를 만들지 않고 **미등록/미정**으로 표시
- 기업·공고의 외부 주소는 유효한 HTTP(S) 링크만 허용
- 원문 링크가 없으면 있다고 꾸미지 않음
- `source=synthetic_seed`인 기업·공고에는 **합성 테스트 데이터**임을 표시
- 실제 공고 수집 저장소의 내용을 승인 없이 정식 공고 DB 목록에 섞지 않음

특히 현재 Staging 정식 공고는 **합성 Seed 데이터**이므로, 화면에서 공고가 조회된다고 실제 채용공고 수집과 서비스 표시가 완료된 것은 아니다.

## 6. T26 — Skill Gap 계산 기준선

오늘 병합된 PR: [#27 — Skill Gap 계산 기준선](https://github.com/ai-career-platform/ai-career-platform/pull/27)

직무에서 요구하는 기술 수준과 사용자의 관측된 기술 수준 사이 차이를 계산한다.

기본 공식:

```python
gap = max(required_level - observed_level, 0)
```

예를 들어 요구 수준이 4이고 보유 수준이 2이면 `gap=2`다. 보유 수준이 더 높더라도 부족분은 음수가 되지 않고 0이다.

구현·검증한 부분:

- 요구·관측 수준의 범위 검사
- 중복 기술 항목 검사
- 일관된 정렬 규칙
- 원본 NULL을 변경하지 않는 계산 전용 스냅샷
- 실제 UUID/API DTO가 아닌 합성 `skill_code` 기준선

검증 기록:

- 전용 테스트 **10 passed**
- 로컬 전체 테스트 **270 passed / 94 skipped**
- Backend CI **337 passed / 27 skipped**, 다른 관련 CI 성공

**주의:** 건너뛴 DB 연계 테스트는 통과한 것이 아니며, 실제 PostgreSQL·Migration·API·인증·Staging에는 연결하지 않았다.

오늘 PR #27은 **`main` 병합 완료**다.

오늘 별도의 개인용 쇼츠 제작 도구 저장소가 생성되었으며, GitHub에서 **Initial commit과 기본 README**를 확인했다.

현재 확인 가능한 단계는 저장소 초기화뿐이다.

- 프로젝트 초기 Git 커밋: 확인
- 실제 로컬 폴더와 원격 연결: GitHub 커밋만으로 확인 불가
- 영상 자동 생성 프로그램: 구현 완료 증거 없음
- 디자인·음성·자막·합성 파이프라인: 구현 완료 증거 없음
- 실행 테스트·배포: 확인되지 않음

이 저장소는 **비공개**이므로 공개 TIL에는 상세 저장소 주소, 파일 내용이나 내부 설정을 기재하지 않는다.

## 10. 오늘 배운 기술 개념

### 실제 API와 Mock UI는 다르다

```text
Mock 데이터
  → 화면 구조·상태 전환 실험

Staging API
  → 실제 HTTP 응답 구조와 페이지·필터 검증

운영 서비스
  → 권한·실제 사용자·정식 원천 데이터·보안·배포 검증
```

T23/T24는 Mock 시안에서 정식 API 연동 단계로 나아갔지만, 전체 운영 환경이 완성됐다는 뜻은 아니다.

### NULL과 0은 구분해야 한다

```text
원본 NULL:
  사용자가 숙련도를 아직 입력하지 않음

계산용 0:
  특정 계산 계약에서 미입력값을 임시로 0으로 해석

두 상태를 데이터베이스 원본에서 동일하게 덮어쓰면 안 됨
```

### RAG는 검색 결과에도 권한이 적용되어야 한다

문서 검색에 관한 계약은 단순히 벡터 검색이 빠르게 되는지보다 **사용자가 어떤 문서를 볼 수 있는지**를 먼저 다뤄야 한다.

문서 검색 전과 결과 반환 전에 권한을 검증하고, 삭제·동의 철회 같은 변화가 색인에도 반영되는지 확인해야 한다. 현재 이 원칙은 **계약·테스트 단계**이며 완성된 실서비스 구현을 뜻하지 않는다.

## 12. 오늘의 회고

오늘은 프론트엔드 화면을 만드는 것에서 나아가 **팀이 이미 구현한 백엔드 API의 실제 계약에 맞춰 화면을 연결하는 과정**을 경험했다.

검색어와 필터를 URL에 보존하고, 커서 기반 페이지 이동과 늦게 도착한 응답을 처리하면서 프론트엔드는 예쁜 화면만이 아니라 **비동기 상태와 데이터 의미를 책임지는 계층**이라는 점을 확인했다.

또 직무의 요구 수준과 보유 기술을 비교할 때는 원본 NULL을 보존하고 단순 UI 비교·Skill Gap 계산·추천 점수를 혼동하지 않아야 한다.

팀 프로젝트에서는 PR을 만들거나 테스트를 통과한 상태, `main`에 병합된 상태, 실사용 환경에서 검증된 상태가 다르다. 앞으로도 **실제 구현·검증 범위와 HOLD 조건을 구분**해 기록해야겠다.
