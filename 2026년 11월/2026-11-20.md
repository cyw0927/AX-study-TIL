## 2. RAG 과제의 목적과 범위

이번 과제는 일반적인 챗봇을 만드는 것이 아니라 **공식 기술문서를 검색한 뒤 관련 근거에 기반하여 질문에 답하는 AI Agent**를 구축하는 것이다.

프로젝트에서 다루는 요구사항:

1. 공식 한국어 PDF 2종에서 10개 제품 모델에 관한 기술지원 정보를 찾는다.
2. 단순 Vector 검색에 그치지 않고 **BM25 / Hybrid / Re-ranking**을 비교한다.
3. 답변에 참조한 **문서와 페이지 정보**를 제공한다.
4. **생성 모델 2개**를 비교하고, 캐싱 또는 쿼리 재작성 등 추가 개선 요소를 다룬다.
5. 검색 실험 결과 및 실행 로그를 남겨 성능 판단의 근거를 확보한다.

여기서 중요한 점은 LLM이 알고 있는 일반 지식으로 답변하는 것이 아니라, **매뉴얼에 실제로 기재된 내용으로 답을 뒷받침해야 한다**는 것이다. 모델명·지원 기능·설정 절차를 잘못 섞으면 기술지원 답변이 그럴듯해 보여도 실제로는 틀린 안내가 된다.

## 3. 검색 파이프라인 구조 이해

이번에 비교한 접근을 개념적으로 정리하면 다음과 같다.

    사용자 질문
         ↓
    질문 전처리 / 검색 질의 구성
         ↓
    PDF에서 추출한 문서 조각(Chunk) 검색
         ├─ Vector: 의미적으로 비슷한 내용 검색
         └─ BM25: 질문에 등장한 용어와 문서 키워드 매칭
         ↓
    Hybrid: 두 검색 결과를 결합
         ↓
    Re-ranking: 후보 문서의 관련성을 다시 평가
         ↓
    관련 문서와 출처 페이지를 LLM에 전달
         ↓
    근거 기반 답변 생성 + 출처 표시

**주의:** 위 흐름은 수업 내용의 개념적 파이프라인이다. 실제 저장소의 함수명·모델·점수 결합식 및 처리 순서까지 오늘 직접 확인했다는 뜻은 아니다.

### Vector 검색과 BM25의 차이

- **Vector 검색**: 문장 표현이 달라도 의미가 비슷한 내용을 찾는 데 적합하다. 반면 모델명이나 짧은 오류 코드처럼 정확한 문자열이 중요한 질의에서는 주의가 필요하다.
- **BM25**: 검색어가 문서에 얼마나 관련 있게 등장하는지를 기반으로 순위를 산정한다. 제품 모델명, 부품명, 오류 코드와 같은 명시적 키워드를 처리할 때 유용하다.
- **Hybrid 검색**: 의미 유사성과 키워드 일치를 함께 활용하여 한쪽 방식의 약점을 보완하려는 방법이다.
- **Re-ranking**: 앞선 검색 단계에서 확보한 후보를 별도의 관련성 기준으로 재정렬한다. 처음부터 전체 문서를 재검색하는 작업과는 다르다.

기술지원 문서는 **비슷한 기기명과 정확한 모델번호가 함께 등장**하므로 검색 방식을 한 가지만 쓰는 것보다, 질문 유형에 따라 실제 성능을 비교하는 절차가 중요하다.

## 4. Hit@5 검색 평가 결과

오늘 대화에서 공유된 Claude의 평가 보고를 정리했다.

| 평가 구분 | 검색 방식 | 보고된 Hit@5 |
| --- | --- | ---: |
| 연습 평가 | Vector | 84.4% |
| 연습 평가 | Hybrid | 84.4% |
| 연습 평가 | Re-ranking | **93.3%** |
| 별도 시험 평가 | Hybrid | **77.8%** |
| 별도 시험 평가 | Re-ranking | 75.0% |

**Hit@5**는 일반적으로 정답 근거 문서가 검색 상위 5개 후보 안에 포함됐는지를 측정하는 지표다. 예를 들어 정답 근거가 1위가 아니어도 5위 안에 있으면 해당 질의는 성공으로 계산할 수 있다.

### 수치에서 배운 점

1. 연습 평가에서는 Re-ranking이 Vector 및 Hybrid보다 높은 수치를 보였다.
2. 별도 시험 평가에서는 오히려 **Hybrid(77.8%)가 Re-ranking(75.0%)보다 높았다**.
3. 따라서 'Re-ranking을 붙이면 언제나 좋아진다'고 단정할 수 없다.
4. 검색 평가가 좋더라도 LLM이 관련 문서를 올바르게 읽고 설명했는지는 **별도의 답변 평가**가 필요하다.
5. 데이터셋의 질문 수, 정답 근거 지정 방법, 검색 후보 수, 평가 기준 등이 확정되지 않으면 퍼센트만으로 일반화하기 어렵다.

위 수치는 **Claude가 보고한 실행 결과**이며, 오늘 별도 터미널이나 저장소에서 재실행하여 재현한 결과로 기록하지 않는다.

## 5. PDF 기반 답변과 출처 표시의 중요성

RAG의 품질은 '답변 문장이 자연스러운가'만으로 판단하면 안 된다. 특히 공식 제품 문서 기반 기술지원에서는 다음을 함께 확인해야 한다.

- **근거 적합성:** 검색된 PDF 조각이 질문한 제품·기능을 정확하게 다루는가?
- **페이지 추적성:** 답변에서 제시한 페이지가 실제 PDF의 해당 설명으로 이어지는가?
- **모델 구별:** 다른 제품 모델의 규격이나 조작법을 섞지 않았는가?
- **모르는 내용의 처리:** 매뉴얼에 근거가 없는데도 추측하여 확정적으로 말하지 않는가?
- **답변 충실성:** 근거를 찾았더라도 조건·예외·설정 순서를 빠뜨리지 않는가?

검색이 상위 5위 안에 올바른 문서를 올려놓는 것은 시작일 뿐이다. **정확한 문서 선택 → 올바른 인용 → 사실에 부합하는 최종 답변**을 각각 점검해야 한다.

## 7. 단위 테스트와 실제 RAG 품질 평가의 차이

**단위 테스트(Unit Test)**는 함수나 모듈이 정해진 조건에 맞게 동작하는지 검사한다. 문서 입력 처리, 검색 함수 반환 형식, UI 또는 평가 계산 과정의 오류를 줄이는 데 도움이 된다.

하지만 이 테스트만으로 실제 기술지원 답변의 정확도가 확보되는 것은 아니다.

- 테스트 72개 통과: **코드의 정의된 검사 조건을 만족**한다는 보고.
- Hit@5 평가: **정답 근거가 검색 결과에 들어왔는지** 측정.
- 답변 평가: **질문에 맞는 내용으로 정확히 답했는지** 확인.
- 출처 검증: **답변에 적힌 문서/페이지가 실제 근거인지** 확인.

서로 다른 검증을 '전체 구현 완료'라는 한 문장으로 합치면 문제를 놓치기 쉽다.

## 9. 오늘의 회고

오늘 가장 중요한 학습은 **RAG의 품질을 검색 성공률 하나로 설명할 수 없다는 점**이다.

Vector와 Hybrid의 연습 성능이 같았고, Re-ranking은 연습 평가에서 더 좋아졌지만 별도 시험에서는 Hybrid보다 낮게 나왔다. 검색 단계를 복잡하게 늘리는 것만으로 성능을 보장할 수 없다는 사실을 숫자로 확인한 셈이다.

또한 AI 개발 도구가 코드를 작성하고 여러 테스트에 통과했다고 보고하더라도, **검색 결과·출처·최종 답변을 실제 질문에 대입해 검증하는 단계**가 남아 있다. 앞으로는 단순히 '작동한다'를 넘어서, 어떤 질문에서 왜 맞고 틀리는지 근거와 로그로 설명할 수 있어야 한다.
