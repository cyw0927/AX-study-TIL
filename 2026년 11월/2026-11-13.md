## 2. STEP 20 — CartItem과 React State

상품 타입 `Product`에 장바구니 수량을 합쳐 계산용 `CartItem`을 정의하는 실습이다.

```ts
type CartItem = Product & {
  quantity: number;
};
```

React 상태:

```tsx
const [cart, setCart] = useState<CartItem[]>([]);
```

기존 상품 데이터의 `stock`은 DB에 저장된 재고다. 반면 `cart`는 **현재 브라우저의 메모리 상태**이므로 새로고침 시 초기화되고, 장바구니 수량 변경만으로 PostgreSQL의 주문·재고가 변경되지는 않는다.

- 수업 README: **STEP 20 로컬 PASS**
- GitHub: `types/cart.ts`와 실제 장바구니 적용 코드 **아직 동기화되지 않음**

## 3. STEP 21 — 상품 담기·중복 방지·Badge

`ProductCard`의 선택적 `onAdd` 콜백에 실제 담기 함수를 연결하는 단계다.

핵심 규칙:

1. 처음 담는 상품은 `quantity=1`로 추가한다.
2. 같은 상품을 다시 담으면 **새 항목을 중복 생성하지 않고 기존 수량을 증가**시킨다.
3. `stock=0`인 품절 상품은 담을 수 없다.
4. 담은 수량이 실제 `stock`을 넘어가지 않게 한다.
5. Badge는 장바구니에 담긴 **종류 수가 아니라 총 수량**을 나타낸다.

초기 Playwright 검사에서는 **6 failed**가 나타났다. README 기록에 따르면 이때 `localhost:3000`의 Next.js 서버가 꺼져 있어 `ERR_CONNECTION_REFUSED`가 발생했다. 서버를 다시 실행한 후 사용자가 테스트 성공을 보고했다.

**학습:** 테스트 실패가 항상 로직 오류는 아니다. 프론트·백엔드 실행 여부를 먼저 확인해야 한다. 하지만 최종 로그 전문이 보존되지 않았으므로 임의의 총 PASS 수를 확정하지 않는다.

## 4. STEP 22~23 — 장바구니 수량과 합계

STEP 22에서는 장바구니의 `+`·`−` 버튼으로 수량을 조절하고, `quantity 1 → 0`이 되면 행을 제거한다. 재고가 부족할 때 더 늘어나지 않도록 한다.

STEP 23에서는 합계를 따로 수동 동기화하는 대신 **현재 cart에서 계산하는 Derived State**로 정리한다.

```tsx
const cartTotal = cart.reduce(
  (sum, item) => sum + item.price * item.quantity,
  0
);

const cartQuantity = cart.reduce(
  (sum, item) => sum + item.quantity,
  0
);
```

계산 예시:

```text
아이스 말차 라떼: 5,500원 × 2 = 11,000원
말차 휘낭시에: 3,000원 × 1 =  3,000원

장바구니 총액: 14,000원
총 수량: 3개
```

사용자는 로컬 브라우저에서 증감·제거와 총액 동작이 정상이라고 확인했다. 다만 이 기능은 **아직 GitHub에서 실제 소스·테스트 결과를 독립 검증할 수 없는 상태**다.

## 5. STEP 24 — useEffect, GET 요청과 POST 주문의 차이

이번 실습에서 중요한 구분은 다음과 같다.

```text
처음 화면 열기 / 다시 조회
  → useEffect + GET /products
  → 서버 상품 데이터 가져오기

장바구니 + / −
  → React setCart
  → 화면의 수량·합계만 변경
  → 상품 GET이나 주문 POST가 추가 호출되지 않음

실제 주문하기 버튼 (향후 STEP 27~29)
  → 사용자 클릭 이벤트
  → POST /orders
  → 서버 DB 가격·재고 검증 및 단일 트랜잭션
```

사용자가 제공한 Network 화면에서는 `GET /products` 중 이전 요청 1건이 `canceled`, 이후 요청 1건은 **200**으로 표시되었다. 개발 모드 Strict Mode에서 Effect 재실행과 AbortController 정리가 연관될 수 있는 정상 패턴이다.

장바구니 `+`·`−`를 눌렀을 때 상품 요청이 새로 발생하지 않고 React State의 표시만 달라지는 점도 확인했다.

**핵심:** `useEffect` 안에서 주문 POST를 자동 실행하지 않는다. 주문은 사용자가 명시적으로 클릭할 때 수행하고 서버가 그때 재고·가격을 다시 확인해야 한다.

## 7. STEP 26 — 로딩·HTTP 503·빈 목록·재시도

새 테스트 파일은 **로컬** `tests/store-state-step26.spec.ts`로 기록돼 있다.

검증 시나리오:

- `page.route("**/products", ...)`로 GET 응답을 지연시켜 **로딩 UI** 표시 확인
- 첫 응답을 `503`으로 만들어 **오류 UI** 확인
- '다시 시도하기'를 누른 후 정상 **200** 응답·상품 복구 확인
- `200 []` 응답에서 **정상 빈 목록 UI** 확인

처음에는 선택자가 Next.js 자체 `role=alert`와 충돌했고, 이후 장바구니의 `role=status`와 충돌하면서 실패했다. 범위를 스토어 영역과 특정 문구로 좁혀 선택자를 수정했다.

기록된 중간 결과는 `1 passed, 2 failed` → `2 passed, 1 failed`이고, 사용자는 이후 **3개 테스트 최종 통과**를 보고했다. 최종 로그 전체는 보관되지 않아 **사용자 보고 기반 PASS**로 표시한다.

Playwright HTML 리포트는 `npx playwright show-report`로 확인했으며, `npx playwright test --ui`에서 발생한 Chromium `Browser.getVersion` 세션 종료 문제는 별도 미해결 사항이다.

**GitHub 상태:** 이 추가 로컬 Playwright 파일은 아직 푸시되지 않았다.

## 8. 다음 STEP 27 — 주문 API는 아직 구현 전

다음 목표는 `POST /orders`다.

필수 안전 조건:

- 요청에서 `product_id`와 `quantity`만 받고 가격은 신뢰하지 않는다.
- Backend가 PostgreSQL의 **현재 상품 가격·재고**를 조회한다.
- 동일 상품의 중복 주문 항목은 수량 합산 후 검증한다.
- 필요한 행을 잠금 처리하여 동시 주문 시 초과 판매를 방지한다.
- `orders`·`order_items` 저장과 `products.stock` 감소를 **한 트랜잭션**에서 처리한다.
- 실패하면 모든 변경을 `rollback`한다.
- 성공 시 201, 없는 상품 404, 재고 부족 409, 잘못된 요청 422를 검증한다.
- 별도 테스트 DB에서 실패·동시성·회귀 케이스를 확인한다.

현재 실제 GitHub에는 `Product`·`Order`·`OrderItem` SQLAlchemy 모델과 세 테이블이 있지만, **주문 POST Route, 주문 저장, 재고 감소를 완료했다고 기록할 증거는 없다.**

또한 STEP 04 개발환경 전체 사전 검증도 **HOLD**로 남아 있다. STEP 20~26 로컬 변경사항을 보존한 뒤 `git status --short`와 변경 파일을 확인하고 **선별 커밋**해야 한다. `git reset --hard`나 무차별 `git add -A`로 기존 변경을 손상시키면 안 된다.

## 15. 오늘의 회고

오늘은 기술적으로 두 가지 중요한 구분을 배웠다.

첫째, **React에서 동작하는 장바구니는 아직 주문 데이터가 아니다.** `useState`에 들어 있는 상품 수량과 합계는 화면의 임시 상태일 뿐이다. 실제 주문을 저장하려면 Backend가 DB의 가격·재고를 다시 확인하고, 여러 테이블의 변경을 하나의 트랜잭션으로 묶어야 한다. 지금은 장바구니 UI와 상태 전이 및 오류 복구까지 확인한 단계다.

둘째, **개발 결과가 로컬에서 잘 동작하더라도 GitHub에 코드가 없으면 다른 환경에서 재현할 수 없다.** 오늘 STEP 20~26 관련 README는 최신이지만 관련 소스와 테스트 파일은 아직 동기화되지 않아, 다음 작업자가 원격 코드만 읽으면 진도를 오해할 수 있다. 그래서 이번 TIL에는 '로컬 PASS'와 'GitHub 코드 미반영'을 동시에 적었다.

AI Agent 학습에서도 비슷하다. 실습 시작 파일을 만들거나 15강 로드맵 이미지를 게시한 것과 실제 에이전트 프로그램을 구현·평가한 것은 다르다. 앞으로도 **코드·실행·테스트·원격 반영·운영 검증을 각각 독립된 증거로 기록**해야겠다.
