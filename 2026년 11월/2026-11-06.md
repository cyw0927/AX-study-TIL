## 1. FastAPI 백엔드 9강 — DELETE API 상태 복습

기존 Chapter 09에는 회원 상세 조회와 삭제 API가 구현되어 있다.

| Method | Path | 성공 응답 | 대표 오류 |
| --- | --- | --- | --- |
| GET | `/members/{member_id}` | 200 + 회원 JSON | 404·422·500 |
| DELETE | `/members/{member_id}` | **204 No Content** | 404·422·500 |

핵심 SQL:

```sql
DELETE FROM public.members
WHERE id = %s
RETURNING id;
```

여기서 `%s`에는 `cur.execute(sql, (member_id,))` 형태로 매개변수를 전달한다. 실습에 사용한 실제 테이블의 기본키는 `member_id`가 아니라 **`id`**다.

삭제 처리에서 구분할 사항:

- 삭제 대상이 존재하고 트랜잭션이 확정되면 HTTP 204를 반환한다.
- **204 응답에는 Body가 없다.**
- 삭제 대상이 없는 경우 HTTP 404를 반환한다.
- 정수형 ID로 변환할 수 없는 입력은 HTTP 422로 처리한다.
- DB 예외가 나면 rollback하고 내부 예외 내용을 클라이언트에 그대로 노출하지 않는다.
- 연결은 성공·실패와 관계없이 정리해야 한다.

**현재 확인 범위:** 코드와 Mock 기반 검증은 이전에 작성됐지만, 실제 `public.members`에 테스트 회원을 추가해 삭제한 뒤 DB가 0행인지 확인하는 최종 실습 증거는 아직 없다.

## 2. 응답 코드와 실제 DB 상태는 별도 검증

HTTP 응답만 보고 DB에 반영됐다고 단정하지 않는 것이 중요하다.

```text
실습용 회원 생성
→ GET 상세 조회 200
→ DELETE 요청 204 + 빈 Body
→ DBeaver SELECT 결과 0행
→ GET 상세 재조회 404
→ 동일 ID 재삭제 404
```

이 검증에서는 기존 수업 회원을 지우지 말고 **별도의 삭제 전용 테스트 행**만 사용한다. 외래키 제약조건이 있을 수 있으므로 임의로 CASCADE를 추가하지 않는다.

```sql
SELECT id, name, email, age
FROM public.members
WHERE id = 999999; -- 실제 테스트용 ID로 교체
```

이 코드는 검증 방법을 설명하는 예시이며 **11월 6일에 실제로 실행한 SQL은 아니다.**

## 3. FastAPI 백엔드 10강 — 계층 분리

기존 Chapter 10은 완성된 CRUD 프로젝트가 아니라 **구조화 실습의 출발점**이다.

```text
HTTP 요청
  ↓
Router       : URL/Method와 HTTP 입력·응답
  ↓
Service      : 업무 규칙, 존재 여부·중복 확인
  ↓
Repository   : SQL 실행, 데이터 조회·변경
  ↓
PostgreSQL   : 영구 데이터 저장
```

현재 준비된 파일 역할:

| 파일 | 역할 |
| --- | --- |
| `app/main.py` | FastAPI 앱과 라우터 연결 |
| `app/routers/members.py` | 회원 API 경로 정의 위치 |
| `app/services/member_service.py` | 회원 비즈니스 로직 작성 위치 |
| `app/repositories/member_repository.py` | 데이터 접근 함수 작성 위치 |
| `app/schemas.py` | 요청·응답 Pydantic 모델 |
| `app/db.py` | 기존 공통 DB 연결 재사용 |

README 기준으로 **회원 목록 조회 SQL은 준비되어 있으나 회원 CRUD 라우터·서비스 로직·나머지 SQL은 아직 구현하지 않았다.**

강의 시작 명령(참고용):

```powershell
cd C:\dev\fullstack-web-course\practice\phase02
python -m uvicorn chapter10.app.main:app --reload --port 8000
```

위 명령도 **오늘 실행했다고 주장하지 않는다.** 기존 실행 안내를 정리한 것이다.

## 4. 앞으로 검증할 API 계약

10강의 파일 분리가 끝난 다음에는 실제 동작을 연결하고 다음을 확인해야 한다.

| 작업 | 검증할 내용 |
| --- | --- |
| GET 목록 | 회원 배열 응답과 DB SELECT 일치 |
| GET 상세 | 존재하면 200, 없으면 404 |
| POST | 유효 입력 201, 검증 실패 422, DB INSERT 확인 |
| PUT | 전체 필드 수정, 200과 DB UPDATE 확인 |
| PATCH | 입력한 필드만 수정, 빈 Body·null 처리 검증 |
| DELETE | 204 빈 Body, DB 0행, 재조회 404 |
| 오류 처리 | 중복·형식 오류·SQL 오류와 rollback |
| 보안 | `.env` 파일 Git 제외, SQL 매개변수 바인딩 |

**상태:** 이 항목들은 후속 학습 체크리스트이며 11월 6일에 완료한 결과가 아니다.

## 5. 기존 학습에서 연결되는 핵심 개념

- **API Contract:** Method, Path, Request, Response, Status의 약속.
- **Validation:** 유효하지 않은 입력이 DB 로직으로 넘어가지 않게 검사.
- **Transaction:** 실행한 SQL이 성공적으로 확정되거나 오류 시 롤백되도록 관리.
- **Separation of Concerns:** Router·Service·Repository가 서로 다른 책임을 담당.
- **Evidence:** 코드가 존재한다는 것, 모의 테스트를 통과했다는 것, 실제 DB 반영을 확인했다는 것을 구분해 기록.

특히 다음 두 식을 기억한다.

```text
HTTP 204 응답 확인 ≠ DB에서 삭제된 행을 직접 검증

프로젝트 파일 구조 생성 ≠ 모든 CRUD 구현 완료
```
