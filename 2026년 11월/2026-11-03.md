## 1. Chapter 09 — 회원 DELETE API

이번 장에서는 이미 구현한 POST·PUT·PATCH를 다시 한 화면에 나열하지 않고 **회원 상세 조회와 삭제**에 집중했다.

| Method | Path | 성공 | 주요 실패 |
| --- | --- | --- | --- |
| GET | `/members/{member_id}` | 200 + 회원 JSON | 404, 422, 500 |
| DELETE | `/members/{member_id}` | **204 + 빈 Body** | 404, 422, 500 |

DELETE 요청은 Path Parameter로 회원 ID를 받아 처리한다. Request Body를 따로 요구하지 않는다.

- **204 No Content:** 삭제가 처리됐고 응답 본문이 없다.
- **404 Not Found:** 삭제 대상 ID가 존재하지 않는다.
- **422 Validation Error:** 정수형 ID가 아닌 값을 입력했다.
- **500 Internal Server Error:** 데이터베이스 처리 중 예외가 발생했다.

특히 삭제 성공 시 JSON 메시지를 반환하는 대신 실제 HTTP 204와 빈 응답을 반환하도록 작성했다.

## 2. PostgreSQL DELETE와 RETURNING

이번 과제의 SQL은 다음 형태다.

```sql
DELETE FROM public.members
WHERE id = %s
RETURNING id;
```

`RETURNING id`를 사용하면 삭제된 행의 ID를 확인할 수 있다.

강의 예시에는 `member_id` 컬럼이 등장하지만, 현재 실습에 사용하는 실제 테이블은 `public.members(id, name, email, age)`이므로 **PK 컬럼 `id`에 맞춰 SQL을 작성**했다.

값을 SQL 문자열에 직접 끼워 넣지 않고 다음처럼 바인딩한다.

```python
cur.execute(sql, (member_id,))
```

SQL 매개변수 바인딩을 사용하면 요청 데이터와 SQL 구문을 분리할 수 있다.

## 3. 트랜잭션: commit, rollback, close

이번 DB 코드에서는 성공·실패 경로를 명시적으로 나눴다.

```text
DELETE 실행
  ├─ 삭제 행 존재 → commit → 204
  ├─ 대상 없음     → rollback → 404
  └─ 예외 발생     → rollback → 500
                       ↓
                  항상 close
```

SQL 명령이 실행됐다는 사실과 트랜잭션이 확정됐다는 사실은 다르다.

- `commit()`: 성공한 변경을 확정한다.
- `rollback()`: 실패한 작업을 취소한다.
- `close()`: 연결 자원을 정리한다.
- `DELETE ... RETURNING`: 실제 영향을 받은 행을 확인한다.

오류 메시지에 DB 내부 정보가 그대로 노출되지 않도록 예외 처리도 구성했다.

## 4. 삭제 전후 검증 방법

삭제 작업은 파괴적이므로 기존 학습용 회원을 무작정 지우지 않고, **별도로 만든 테스트 회원**을 사용해야 한다.

검증 순서:

1. DBeaver에서 삭제 전용 테스트 회원을 준비하고 ID를 확인한다.
2. `GET /members/{id}`가 200을 반환하는지 확인한다.
3. `DELETE /members/{id}`를 실행하고 204 및 빈 Body를 확인한다.
4. DBeaver에서 같은 ID를 조회해 **0 rows**인지 검사한다.
5. 같은 회원을 다시 GET하면 404여야 한다.
6. 이미 삭제한 ID로 DELETE를 재요청하면 404여야 한다.
7. 잘못된 ID 형식은 422여야 한다.

```sql
SELECT id, name, email, age
FROM public.members
WHERE id = 999999; -- 실제 실습용 ID로 교체
```

**현재 상태:** 위 검증 절차와 SQL은 작성했지만, 실제 `public.members` 테이블에 테스트 회원을 생성하고 API로 삭제한 전후 Evidence는 아직 완료로 확인되지 않았다. 따라서 **DELETE 기능 구현 ≠ 실DB 삭제 실습 완료**로 구분한다.

## 10. Chapter 10 — 백엔드 구조화 시작

오늘 Chapter 10에서는 처음부터 CRUD 전체를 완성하지 않고 **역할별 파일 구조를 나누는 실습 출발점**을 만들었다.

```text
chapter10/
└── app/
    ├── main.py
    ├── db.py
    ├── schemas.py
    ├── routers/
    │   └── members.py
    ├── services/
    │   └── member_service.py
    └── repositories/
        └── member_repository.py
```

구조의 핵심:

```text
HTTP 요청
→ Router
→ Service
→ Repository
→ PostgreSQL
```

각 계층의 역할은 다음과 같다.

- **Router:** URL, Method, HTTP 입력·응답
- **Service:** 회원 존재 여부, 중복 등 업무 규칙
- **Repository:** SQL 실행과 데이터 조회·변경
- **Schema:** Request/Response 데이터 구조
- **DB:** 실제 PostgreSQL 연결

현재 `schemas.py`에는 회원 생성·전체 수정·부분 수정·응답 모델이 들어 있고, Repository에 회원 목록 조회 `find_all()`의 SQL이 작성돼 있다.

**다만 회원 CRUD 라우터, 서비스 로직과 나머지 SQL은 아직 TODO이며, Chapter 10을 완성한 것은 아니다.**

## 11. Chapter 10 코드 구조의 의미

처음에는 `main.py` 하나에 모든 코드를 작성해도 간단한 API가 동작한다. 그러나 기능이 많아지면 HTTP 처리, 업무 규칙, SQL이 뒤섞여 유지보수가 어려워진다.

오늘 배우기 시작한 구조에서는 다음처럼 역할을 나눈다.

```text
Router: "어떤 API 요청인가?"
Service: "업무적으로 허용되는 요청인가?"
Repository: "어떤 데이터를 가져오거나 바꿀 것인가?"
DB: "어느 데이터베이스에 연결하는가?"
```

이 구조는 같은 데이터 접근을 여러 API에서 재사용하고 테스트할 때도 유용하다.

다음 단계에서는 실제 회원 CRUD 엔드포인트를 하나씩 연결하고, HTTP 결과와 DB 결과가 일치하는지 검증해야 한다.
