이 문서는 개인 학습 기록이다. 비공개 협업 저장소의 주소, 원문·문항·답변·실험 수치·개인정보와 세부 구현은 공개하지 않는다. 팀의 공식 제출 및 공식 성적은 확인되지 않았으므로 완료로 기록하지 않는다.

## 2. 정확도와 토큰 비용을 함께 판단하기

RAG에서는 많은 문서 조각을 모델에 제공하면 질문에 필요한 근거가 포함될 가능성이 높아진다. 하지만 입력이 길어질수록 토큰 사용량과 처리 비용이 증가하고, 불필요한 정보가 정답 근거를 가릴 수도 있다.

오늘은 문맥을 짧게 구성하는 방식과 더 풍부한 문맥을 제공하는 방식을 비교한 작업을 검토했다. 답변 정확도에서 유리해 보이는 설정도 토큰 비용을 포함한 평가 기준에서는 반드시 유리하지 않다는 점을 배웠다.

후보 비교 시 함께 볼 지표:

- 답변 정확도(Answer Accuracy)
- 답변과 근거의 일치 여부
- 정답이 있는데도 답변을 거부한 비율
- 근거가 없는 질문에 잘못 답하는 비율
- 모델별 실제 토큰 사용량
- P95 응답 지연시간

P95는 관측한 요청의 약 95%가 해당 시간 이내에 완료된다는 의미다. 평균만 확인하면 일부 매우 느린 요청이 가려질 수 있다.

중요한 것은 단일 지표를 최대화하는 것이 아니라, **평가 기준 전체에서 어떤 선택이 합리적인지 확인하는 것**이다. 공식 평가 결과가 없는 상황에서 최종 순위 상승을 확정할 수는 없다.

## 3. 평가 데이터 오염과 실험 설계

오늘 비교 보고서에 대한 리뷰에서 특히 중요했던 부분은 평가 데이터의 독립성이다.

- DEV: 개발 중 설정과 코드를 개선할 때 사용하는 질문
- Held-out: 개발과 설정 선택에서 분리해 최종 일반화 성능을 확인하는 질문
- 표현 변형: 기존 질문의 어순, 표현, 오타 등을 바꾸어 견고성을 탐색하는 질문

시험용 질문의 표현을 바꿨다고 해서 독립적인 개발 질문이 되는 것은 아니다. 정답이나 문제 구조가 동일하다면 그 결과를 반복 확인하면서 설정을 선택하는 과정 자체가 시험용 데이터에 대한 간접적인 최적화가 될 수 있다.

    개발 질문으로 수정
          ↓
    개발 질문에서 후보 비교
          ↓
    설정 및 코드 확정
          ↓
    독립 평가 질문으로 검증

오늘 비교 보고서에는 이 한계가 명시되고, 초기 권고가 철회된 것을 확인했다. 해당 실험은 탐색 기록으로 보존하되 독립적인 최종 성능이나 제출 후보 선택의 근거로 과장하지 않는 것이 중요하다.

또한 평가 정답 자체에 오류가 있으면 원문을 대조해 수정해야 한다. 정답 라벨을 바꾼 전후 결과는 평가 기준이 달라지므로 그대로 비교하면 안 된다.

## 4. 기술지원 RAG의 거부 문제

기술지원 AI는 모르는 내용을 만들어 내지 않아야 한다. 그러나 관련 문서가 특정 모델에서 기능을 지원하지 않는다고 명시한다면, 그 사실 자체가 질문에 대한 정답이 될 수 있다.

| 문서에서 확인된 상태 | 적절한 답변 |
| --- | --- |
| 해당 모델에서 기능을 지원함 | 근거를 인용해 기능이나 절차 설명 |
| 해당 모델에서 기능을 지원하지 않음이 명시됨 | 지원하지 않는다고 답변 |
| 다른 모델에 관한 내용만 있음 | 질문 모델에 그대로 적용하지 않음 |
| 필요한 내용이 문서에 없음 | 근거 부족을 명확하게 표시 |

'기능 미지원'과 '근거 없음'은 서로 다른 상태다.

이 차이를 고려하지 않고 모든 부정적인 질문을 거부하면 사실상 정답이 존재하는 질문에서도 점수를 잃고 사용자에게 유용한 정보를 주지 못한다. 반대로 근거 없이 미지원이라고 단정하는 것 역시 잘못이다.

오늘 검토한 개선에서는 모델과 문서의 적용 범위가 맞는지 확인하는 것이 핵심이었다.

## 5. 사양표와 결정론적 답변

제품 사양은 매뉴얼의 표에 명확한 수치로 제시되는 경우가 많다. 검색 단계에서 올바른 표를 찾았더라도 생성 모델이 답변을 거부하는 일이 발생할 수 있다.

이런 상황에서는 LLM에 추가 질문을 반복하기보다 **값을 확실하게 결정할 수 있는 경우에만 규칙 기반으로 답변을 복구하는 방식**을 고려할 수 있다.

개념적인 조건:

    생성 모델이 근거 부족으로 거부
        ↓
    단일 제품 / 단일 사양 질문인가?
        ↓
    문서에서 적용 모델과 사양 조건이 일치하는가?
        ↓
    서로 충돌하지 않는 하나의 값이 존재하는가?
        ↓
    모두 충족하면 값과 근거를 반환
    충족하지 않으면 기존 거부를 유지

규칙 기반으로 답할 때에는 표에 수치가 있다는 사실만으로 충분하지 않다. 질문의 의미와 표의 행 조건이 정확하게 일치해야 한다.

가상의 예를 들면 평균 소비 전력 400W라는 자료가 있을 때 최대 소비 전력을 질문한 사람에게 400W라고 답하면 안 된다.

- 평균과 최대는 다르다.
- 대기, 절전, 인쇄, 복사 등 작동 상태가 다를 수 있다.
- 단위가 같은 숫자라도 측정 조건이 다르면 답이 달라진다.
- 잘린 표나 적용 모델이 불명확한 행으로는 답변하지 않는 편이 안전하다.

오늘 팀 코드 리뷰에서는 이런 조건어의 차이에서 생기는 반례를 발견했고, 조건 일치 검사를 개선한 뒤 회귀 테스트를 추가했다는 기록을 확인했다.

## 6. 반례 검증과 회귀 테스트

AI가 작성한 코드가 기존 단위 테스트를 모두 통과하더라도 새로운 종류의 입력에서 오답이 발생할 수 있다.

오늘 리뷰 과정에서 배운 검증 순서는 다음과 같다.

1. 다른 에이전트의 설명만 믿지 않고 실제 입력과 결과를 확인한다.
2. 문제를 일으키는 최소한의 재현 사례를 만든다.
3. 수정 전후에 동일한 입력을 사용해 결과를 비교한다.
4. 이전 정상 동작이 깨지지 않았는지도 확인한다.
5. 재현 사례를 회귀 테스트로 남긴다.
6. 전체 테스트와 독립 평가를 구분한다.

회귀 테스트는 한 번 해결한 버그가 미래 변경에서 다시 나타나는 것을 막기 위한 테스트다.

특히 규칙 기반 사양 답변을 검증할 때에는 실제 생성 API를 호출하지 않고도 표와 질문의 조건 일치 여부를 재현할 수 있다. 이는 API 비용을 줄이고 문제 원인을 좁히는 데 유용하다.

단, 오프라인 테스트가 성공했다고 해서 실제 LLM을 사용하는 전체 서비스의 품질까지 입증되는 것은 아니다.

## 7. API 사용량 기록과 비동기 처리

모델 호출 비용을 기록하는 기능은 성공 응답만 저장하는 단순한 방식으로는 충분하지 않다.

오늘 협업 과정에서는 다음과 같은 예외 상황을 검토했다.

- 공급자 API가 오류를 반환한 경우
- 토큰 usage 정보가 없는 실패 응답
- HTTP 응답은 시간 초과됐지만 내부 작업이 계속 진행되는 경우
- 답변 생성 외에 질의 임베딩에도 과금이 발생하는 경우
- 여러 요청이 같은 로그 파일에 동시에 기록되는 경우
- 테스트 실행이 실제 운영 로그를 오염시키는 경우

특히 비동기 코드에서 시간 초과가 발생했다고 내부 스레드까지 반드시 중단되는 것은 아니다.

    사용자 요청
         ↓
    백그라운드 스레드에서 모델 호출
         ↓
    HTTP 응답 시간 제한 초과
         ↓
    사용자에게 504 반환
         ↓
    내부 스레드는 작업을 계속할 수도 있음
         ↓
    실제 종료 시점에 사용량 기록 필요

따라서 응답 반환 시점에만 사용량을 기록하면 뒤늦게 완료된 호출이 빠질 수 있다. **HTTP 응답의 생명주기와 실제 작업의 생명주기를 구분**해야 한다.

또한 실패 호출에서 실제 사용량을 알 수 없다면 이를 임의로 0으로 기록하는 것이 아니라, 누락된 이유를 구분하는 것이 더 정확하다.

생성 모델과 검색용 임베딩 호출의 사용량을 분리하고, 로그에는 필요한 요청 식별자·시각·모델·사용량 및 실패 상태만 남기는 방식도 학습했다. 테스트 로그는 임시 경로에서 관리해 운영 기록과 분리해야 한다.

## 8. 동시 기록과 JSONL

JSONL은 JSON 객체를 한 줄에 하나씩 기록하는 형식이다.

예시(실제 운영 기록이 아닌 설명용 가상 데이터):

```json
{"kind":"generation","status":"ok","total_tokens":1200}
{"kind":"embedding","status":"ok","total_tokens":35}
{"kind":"generation","status":"timeout","total_tokens":null}
```

여러 스레드가 같은 파일에 동시에 쓰면 구현 방식에 따라 기록이 섞이거나 누락될 수 있다. 프로세스 내부의 잠금 또는 단일 기록 담당자를 이용해 쓰기 작업을 직렬화하고, 동시 요청 테스트로 예상 행 수와 각 행의 파싱 가능 여부를 확인할 수 있다.

프로세스 내부 잠금은 여러 독립 프로세스까지 자동으로 보호하지는 않으므로, 서비스 구조가 달라지면 기록 방식도 다시 검토해야 한다.

## 9. 문맥 압축과 출처 정합성

토큰 사용량을 줄이는 다른 방법은 검색된 근거에서 질문과 관련성이 낮은 부분을 제거하는 것이다.

그러나 검색 결과와 실제 생성 모델 입력은 압축 이후 서로 달라질 수 있다.

    원래 검색 결과: A, B, C
    실제 모델 입력: A, B
    최종 인용: A, B, C  ← C가 답변 근거라는 보장 없음

이처럼 모델에게 전달하지 않은 문서 조각이 근거인 것처럼 남으면 추적성과 인용의 신뢰성이 낮아진다.

따라서 압축 기능을 구현할 때는 다음 정보를 구분해 관리해야 한다.

- 검색 단계에서 발견한 후보 근거
- 압축 이후 실제로 전달한 근거
- 생성 호출별 사용 근거의 기록
- 최종 답변에 표시된 인용

압축 후 정답률이 떨어졌다면 모델의 무작위 실행 편차인지, 필요한 근거가 제거된 결과인지 구별해야 한다. 같은 버전과 조건에서 반복 실행하고 실제 전달된 근거를 대조해야 원인을 판단할 수 있다.

오늘 압축 실험의 초안은 병합되지 않은 상태였다. 테스트가 통과했다는 이유만으로 인용 정합성과 비교 기준 문제가 해결됐다고 보지 않는다.

## 10. Claude Code와 Codex의 협업 방식

오늘 작업에서 AI 코딩 도구를 사용하는 방법 자체도 중요한 학습이었다.

- 구현 담당 AI는 변경 코드, 실험 기록, 테스트 결과, 한계를 남긴다.
- 검증 담당 AI는 기존 결론을 그대로 받아들이지 않고 반례를 찾는다.
- 리뷰 지적은 구체적인 입력, 재현 조건, 수정 요청으로 작성한다.
- 수정이 완료되면 동일한 반례를 다시 확인한다.
- 변경 범위와 제출 후보를 분리하며, 미완료 실험을 기존 기능에 무리하게 합치지 않는다.

공동 작업 기록을 유지하면 AI 도구 사이에 모든 대화를 복사해 전달하지 않고도, 변경 사항과 남은 검증을 추적할 수 있다.

오늘은 제출 후보 비교 문서와 두 가지 코드 개선의 병합을 GitHub에서 확인했다. 별도 최적화 초안은 미병합 상태로 구분했다.

## 12. 회고

오늘의 핵심은 **더 높은 정확도를 보고하는 것보다, 왜 그 결과가 나왔으며 그 결과를 어디까지 신뢰할 수 있는지를 설명하는 능력**이었다.

RAG 시스템의 평가에는 검색과 생성뿐 아니라 문서의 적용 범위, 근거 인용, 비용, 로그, 평가 데이터의 독립성까지 포함된다. 복잡한 모델을 붙이거나 테스트 통과 수를 늘리는 것만으로 이러한 문제들이 자동으로 해결되지는 않는다.

AI 도구가 서로의 변경을 검증하고, 반례를 발견해 수정하며, 검증 결과가 불충분한 실험을 보류하는 과정 자체가 개발 역량의 중요한 부분이라고 생각한다.
