## 4. PostgreSQL — 회원관리와 매장 스키마 분리

처음에는 기존 `public` 스키마에 상품·주문 테이블을 생성했지만, 회원관리와 새로운 매장의 데이터 경계를 분명히 하기 위해 전용 스키마로 옮겼다.

현재 구조:

```text
PostgreSQL
├── public
│   └── members
└── matcha_store
    ├── products
    ├── orders
    └── order_items
```

테이블을 삭제·재생성하지 않고 `ALTER TABLE ... SET SCHEMA matcha_store` 방식으로 이동했다. README의 검증 기록에 따르면 트랜잭션 내 이동 전후 데이터 일치를 확인했고, Backend SQLAlchemy Session에서 상품 **7건**을 조회했다.

주요 데이터 계약:

- `products`: `id`, `name`, `price`, `category`, `stock`
- `orders`: `id`, `total_price`, `status`, `created_at`
- `order_items`: `id`, `order_id`, `product_id`, `quantity`, `price`
- 상품 가격·재고와 주문 총액은 음수 불허
- 주문 상세의 수량은 1 이상
- 주문 상세는 `orders`와 `products`를 FK로 참조
- 주문 상세의 `price`는 **주문 당시 단가 스냅샷**으로 사용할 예정

실제 테이블 컬럼·PK·FK·CHECK를 확인했고 **모델에 정의한 CHECK 제약의 이름은 실제 DB와 일부 다르다**는 사실도 기록했다. 제약 이름 차이와 제약이 실제로 작동하는지는 별개다.

[스키마 분리 커밋](https://github.com/cyw0927/fullstack-web-course/commit/dccf5f1bb7542c175f41679e2bf3c53f3dad75e3)

## 5. SQLAlchemy — 모델과 조회 계층

기존 `Member` 모델은 `public.members`를 유지하고, `Product`·`Order`·`OrderItem`은 `matcha_store`에 매핑한다.

상품 Repository는 실제 DB 데이터를 ID 순으로 조회한다.

```python
from sqlalchemy import select
from app.models import Product

def find_all(db):
    return db.scalars(
        select(Product).order_by(Product.id)
    ).all()
```

Service는 Repository의 조회 결과를 반환하고, Router는 HTTP 요청과 응답 모델을 담당한다.

```text
GET /products
→ product_router
→ product_service.get_products(db)
→ product_repository.find_all(db)
→ SQLAlchemy select(Product)
→ matcha_store.products
```

Repository·Service와 직접 SQL 결과를 대조한 기록에서는 상품 **7건의 ID·이름·가격·카테고리·재고가 일치**했다.

## 9. STEP 16~19 — Component·Props·map/key와 Playwright

상품 목록을 큰 JSX 코드 하나로 유지하지 않고 **`ProductCard.tsx`와 `Product` 타입**으로 분리했다.

```ts
export type Product = {
  id: number;
  name: string;
  price: number;
  category: string;
  stock: number;
};
```

`StoreFront`에서는 다음 패턴을 사용한다.

```tsx
<ul>
  {products.map((product, index) => (
    <ProductCard
      key={product.id}
      product={product}
      index={index}
    />
  ))}
</ul>
```

- **Component:** 한 상품의 표시 책임을 분리
- **Props:** 상품별 데이터를 동일한 카드에 전달
- **`key`:** 목록 항목을 안정적으로 구분
- **조건부 렌더링:** `stock===0`이면 품절 표시 및 버튼 비활성화
- **가격:** `toLocaleString("ko-KR")`로 원화 천 단위 표기

## 13. 오늘의 핵심 정리

```text
React Props      = 각 상품 데이터를 재사용 컴포넌트에 전달
React map/key    = 상품 배열을 목록으로 렌더링하고 항목을 구분
React State      = 로딩·오류·성공 상태 및 향후 장바구니 상태 관리
FastAPI Router   = HTTP GET /products와 응답 모델
Service          = 상품 조회의 업무 흐름
Repository       = SQLAlchemy로 실제 DB 조회
PostgreSQL Schema = 회원관리와 매장의 데이터 경계

상품 카드 7개 렌더링 ≠ 장바구니 기능 완료
orders 테이블 생성 ≠ POST /orders 구현
GET 테스트 5 passed ≠ 주문 트랜잭션 테스트 완료
Playwright 카드 Smoke 4 passed ≠ 결제·주문 E2E 완료
STEP 04 HOLD ≠ 전체 프로젝트 환경 무조건 PASS
GitHub 커밋 확인 ≠ AI의 미푸시 로컬 작업까지 확인
```

## 14. 오늘의 회고

어제는 Next.js 회원관리 CRUD와 동적 상세 페이지를 연결했다. 오늘은 같은 풀스택 환경을 확장해 **기존 회원 데이터를 유지하면서 완전히 다른 상품 도메인**을 만드는 연습을 했다.

특히 `public.members`와 `matcha_store`를 구분하고 세 상품·주문 테이블을 전용 스키마로 옮긴 경험은 **기존 서비스를 망가뜨리지 않고 기능을 확장하는 방법**을 이해하는 데 도움이 됐다.

또 처음에는 상품 카드 한 개를 확인하고, 다른 Props 두 개로 늘리고, 실제 DB에서 가져온 일곱 개를 `map`으로 렌더링했다. 여기에 읽기 전용 Playwright 회귀 검사를 더해 **현재 기능을 확인하면서 기존 회원관리도 보존하는 검증 방식**을 연습했다.

오늘은 **상품 조회와 화면 표시 단계의 성공**이다. 다음 STEP 20에서 장바구니 State를 만들고, 이후 상품 수량·합계·주문·재고 감소를 실제로 연결할 예정이다. 완료되지 않은 기능을 완료했다고 적지 않는 것이 이번 TIL의 원칙이다.
