## 2. 복합 질문에서 발생하는 오류의 원인

기존 RAG는 질문과 관련된 문서를 검색해 생성 모델에 전달한다. 하지만 복합적인 질문에서는 정답 페이지를 검색하더라도 필요한 모든 조건이 전달되지 않을 수 있다.

오늘 검토한 문제 유형은 다음과 같다.

- 여러 제품을 비교하는 질문에서 일부 제품의 근거만 찾음
- 하나의 표에서 서로 다른 모델 열의 값을 혼동함
- 페이지가 넘어가면서 끊긴 표의 행을 별개의 항목으로 해석함
- 각주에만 있는 적용 조건을 놓침
- 설정 절차의 앞부분만 읽고 뒷부분을 빠뜨림
- 질문에 명시된 기능 이름을 토큰화하는 과정에서 정확한 표현을 잃음
- 여러 요구사항 가운데 첫 번째만 답하고 나머지는 누락함

이러한 문제는 단순히 생성 모델을 더 강력한 모델로 교체한다고 모두 해결되지는 않는다. **검색 결과 선정 → 문서 구조 복원 → 근거 구성 → 생성 지시 → 답변 검증** 중 어느 단계에서 정보가 사라지는지 살펴야 한다.

## 3. PDF 표의 구조 보존

PDF를 텍스트로 바꾸는 과정에서 빈 칸을 제거하거나 반복되는 값을 한 번만 남기면, 원래 표의 열 위치가 무너질 수 있다.

가상의 예:

| 모델 | 기본 모드 | 절전 모드 |
| --- | ---: | ---: |
| A | 100W | 20W |
| B | — | 20W |

두 번째 행을 단순히 `B | 20W`로 저장하면 모델이 20W를 기본 모드의 값으로 읽을 수 있다. 빈 칸도 정보이므로, 행을 직렬화할 때 열의 위치를 보존하거나 열 이름을 함께 전달하는 것이 필요하다.

오늘 변경에서 확인한 접근은 표 셀 구조, 열 이름, 페이지 사이의 행 연결, 각주 정보를 보존하는 것이다.

다만 페이지가 이어진다는 이유만으로 무조건 앞뒤 행을 연결하면 다른 항목을 잘못 합칠 수 있다. 실제 표의 구조와 행 조건이 맞는지 확인해야 한다.

## 4. 각주와 적용 범위

사양표에서 숫자 자체보다 각주에 담긴 조건이 더 중요할 때가 있다.

예를 들어 어떤 표의 수치가 특정 모델이나 용지 조건에서만 적용된다면, 각주를 제거한 채 수치만 전달하는 것은 잘못된 정보 제공으로 이어진다.

각주 처리에서 고려할 점:

- 각주 번호와 일반 숫자를 구별한다.
- 다른 표에서 우연히 같은 번호를 사용한 각주를 섞지 않는다.
- 조건을 보완하는 각주가 실제로 전달됐는지 추적한다.
- 각주에서 제한하는 적용 모델 및 측정 조건을 확인한다.
- 페이지와 청크 ID를 모두 관리한다.

오늘 리뷰에서는 다른 청크의 각주 본문이 모델 입력에 들어갔음에도 그 청크의 출처 ID가 기록되지 않는 문제가 지적됐다. 후속 수정에서는 실제 사용한 각주 출처가 전달 근거와 인용 추적에 포함되도록 개선했다.

**모델에 보내는 문장이 동일하더라도, 추적 기록이 잘못되어 있으면 개선이 필요하다.** 모델의 답변 성능과 출처 감사 가능성은 별개의 품질 요소다.

## 5. 긴 질문의 근거 선정과 적용 모델 필터

긴 질문은 여러 기능, 조건, 제품을 한꺼번에 묻기 때문에 제한된 문맥만으로 답하기 어려울 수 있다.

오늘은 기존 검색에서 선정한 주요 근거를 유지하면서 관련성이 높은 추가 근거를 제한적으로 전달하는 방법을 검토했다.

    질문
      ↓
    기본 검색과 주요 근거 선정
      ↓
    복합 질문인지 판단
      ↓
    관련성이 높은 추가 후보 검토
      ↓
    문서의 적용 범위 확인
      ↓
    필요한 부분만 전달

중요한 것은 추가 근거가 항상 도움이 되는 것은 아니라는 점이다.

- 질문과 관련 없는 후보를 추가하면 토큰만 늘어날 수 있다.
- 다른 모델에만 적용되는 설명은 오히려 잘못된 답변을 유도할 수 있다.
- 제품군이 다른 모델을 비교할 때 한 문서에 모든 모델이 있어야 한다고 판단하면 올바른 근거를 버릴 수 있다.
- 이미 선택된 핵심 근거를 추가 후보가 밀어내지 않도록 주의해야 한다.

특히 '이 표 또는 절의 적용 모델 목록에 없다'는 사실과 '제품이 해당 기능을 지원하지 않는다'는 결론은 동일하지 않다. 다른 문서나 다른 행에 해당 제품의 정보가 있을 수 있기 때문이다.

오늘의 관련 PR들은 추가 후보의 질문 관련성, 같은 제품군 내 적용 범위, 다른 근거와의 관계를 각각 점검하며 개선됐다.

## 6. 실제 모델 입력을 기준으로 실험 비교하기

오늘 실험에서 유용했던 방법은 서로 다른 코드와 설정이 실제로 생성 모델에 어떤 요청을 보내는지 비교하는 것이다.

설정 A와 B의 답변 점수가 달라졌더라도 두 설정이 특정 문항에 동일한 모델 입력을 보냈다면, 그 점수 차이를 설정 변경 효과로 곧바로 해석할 수 없다.

| 관측 결과 | 판단 |
| --- | --- |
| 모델 입력 변경, 점수 개선 | 변경 효과일 가능성이 있어 반복 확인 필요 |
| 모델 입력 변경, 점수 하락 | 필요한 근거 제거 또는 방해 정보 가능성 분석 |
| 모델 입력 동일, 답변 다름 | 생성 과정의 변동 가능성 |
| 오프라인 요청 동일 | 비교한 조건에서 입력 동등성 확인 |
| 실제 API 미실행 | 실제 답변 품질은 아직 별도 검증 필요 |

같은 질문·문서·검색 순서·평가 기준으로 후보를 비교하고, 가능하면 동일 채점 세션에서 결과를 판정해야 한다. 두 번 실행했을 때 보수적으로 낮은 점수를 참고하는 방식도 검토했다.

오프라인 비교는 API 비용 없이 변경 범위를 파악하는 데 유용하지만, 그것만으로 실제 답변 정확도를 증명하지는 않는다.

또한 개발 과정에 사용한 문항과 독립 평가 문항은 구분해야 한다. 이미 결과를 보고 수정한 질문은 더 이상 완전히 독립적인 시험 자료로 볼 수 없다.

## 7. 답변의 숫자를 근거와 비교하는 검사

RAG가 답한 수치가 실제 근거에서 확인되는지 살펴보는 진단 기능도 검토했다.

개념적으로 다음을 구분할 수 있다.

- 인용한 근거에 있는 수치
- 모델이 읽었으나 인용하지 않은 다른 근거에만 있는 수치
- 전달한 어느 근거에도 없는 수치

이 방식은 별도의 LLM 호출 없이 이상 징후를 찾을 수 있다. 그러나 숫자 문자열을 찾았다고 답변이 맞는 것은 아니다.

예를 들어 인용한 표에 100W와 200W가 모두 있을 때, 제품 A에 제품 B의 200W를 답하면 단순 숫자 대조는 오답을 발견하지 못한다. 단위 환산이나 계산으로 얻은 정상 값이 근거에 동일 문자열로 없을 수도 있다.

오늘 확인한 기능은 **진단 표시만 추가하는 단계**다. 답변을 자동 수정하거나 강제로 거부하게 만드는 기능이 아니다. 코드가 병합됐지만 공식 설정은 비활성 상태였다. 정확도가 향상됐다고 기록하지 않는다.

## 8. 질의 임베딩 캐시와 재현성

임베딩은 질문을 벡터로 변환해 문서 검색에 사용하는 과정이다. 같은 질문을 반복 평가할 때 이전 벡터를 재사용하면 불필요한 임베딩 호출을 줄일 수 있다.

    질문 + 임베딩 설정
            ↓
         캐시 조회
        /         \
      적중         미스
       ↓            ↓
    저장 벡터     임베딩 API
       ↓            ↓
       └────── 검색 ─┘
                ↓
        생성 모델로 답변 생성

오늘 병합된 캐시는 SQLite 기반 영속 저장 방식이다. 애플리케이션을 재시작해도 기존 캐시를 사용할 수 있게 한다.

일반적으로 캐시 키에는 입력 문자열뿐 아니라 모델, 벡터 차원, 전처리 또는 정규화 버전을 구분하는 정보도 포함해야 한다. 임베딩 모델을 변경했는데 이전 벡터를 재사용하면 검색 결과가 잘못될 수 있기 때문이다.

오늘 검토한 검증의 주요 개념:

- 캐시 적중 시 임베딩 API 호출 감소
- 캐시 비활성화 시 기존 요청 경로 유지
- 벡터의 차원, 유한값 및 유효성 확인
- 캐시 읽기·저장 오류가 있어도 일반 임베딩 경로로 복구
- 생성 모델 호출과 사용량 기록은 기존대로 수행
- 동일 저장 벡터를 사용할 때 검색 및 모델 입력 동등성 확인

**임베딩 캐시는 답변 캐시가 아니다.** 검색에 사용하는 질문 벡터만 재사용하며, 답변은 요청할 때마다 생성한다.

질의 임베딩의 변동으로 검색 근거가 달라지는 원인 하나를 줄일 수 있지만, 동일한 근거에서 발생하는 생성 모델의 답변 변동이나 인용 차이까지 제거하지는 않는다. 동시 미스에서는 중복 호출이 발생할 수도 있다.

팀의 반복 실험 보고와 리뷰를 확인했으며, 직접 최신 병합 커밋의 설정 파일을 확인한 결과 캐시는 아직 꺼져 있었다. **병합 완료와 기능 활성화를 구분**한다.

## 9. 성능 분석 화면과 평가 지표

사용자 질문 하나를 처리하는 화면 외에, 여러 문항을 실행하고 결과를 표 및 CSV로 확인하는 화면과 성능 분석 탭이 병합됐다.

주요 설계:

- 질문과 답변 및 인용을 구분해 표시
- 여러 문항의 결과를 일괄 확인
- 기존 측정 파일에서 실제 평가 지표 불러오기
- 토큰, 지연시간, 거부 및 오류 상태 표시
- 과거 결과와 비교할 때 지표의 변화 확인

특히 계산하지 않은 지표를 임의의 숫자로 채우지 않는 것이 중요하다.

| 지표 | 의미 |
| --- | --- |
| Hit@k | 상위 k개 결과에 정답 근거가 포함됐는지 |
| Recall@k | 전체 관련 근거 중 상위 k개에서 찾아낸 비율 |
| Precision@k | 상위 k개 결과 중 관련 근거의 비율 |
| MRR | 첫 번째 정답 근거의 순위를 역수로 변환한 평균 |
| Answer Accuracy | 최종 답변의 정확도 |
| Grounding Accuracy | 답변을 인용 근거가 뒷받침하는 정도 |
| P95 | 요청의 약 95%가 완료되는 시간 기준 |

실제 채점 전에는 정확도를 채점 대기로 표시하고, 계산하지 않은 검색 지표는 미측정으로 표시하는 것이 맞다. 정적 화면 예시의 가상 수치와 실제 평가 결과도 구분해야 한다.

오늘 화면 변경은 병합됐고 화면 렌더링 테스트 기록은 확인했으나 실제 브라우저에서의 전체 동작과 실제 질문 전송 검증은 미확인이다.

## 10. 기능 스위치와 안전한 코드 정리

오늘 여러 변경에서 공통적으로 사용한 방식은 기능 스위치다.

새 기능의 코드를 먼저 반영하더라도 기본값을 꺼 두면 기존 동작을 유지하면서 별도로 실험할 수 있다. 그러나 스위치를 껐다는 사실만으로 동작이 동일하다고 가정해서는 안 된다. 실제 모델 입력, 응답 형태, 근거와 추적 정보 등을 비교해야 한다.

미사용 코드 정리에서도 호출하지 않는 함수나 모듈을 삭제한 뒤 기존 동작이 동일한지 확인하는 과정이 필요하다.

오늘 코드 정리 PR에서는 작성자와 별도 리뷰의 테스트 통과 기록을 확인했다. 모델 요청 해시 및 오프라인 결과 동등성 비교도 보고됐다. 다만 이번 TIL 작성 과정에서 원자료를 확보해 그 모든 테스트를 새로 실행한 것은 아니다.

테스트 수가 줄었다고 반드시 품질이 떨어진 것도 아니고, 테스트 수가 늘었다고 반드시 성능이 좋아진 것도 아니다. 삭제된 기능의 테스트를 함께 정리했는지, 유지해야 할 동작의 검사가 남아 있는지가 더 중요하다.

## 11. 신규 자료를 반영한 평가 준비

기술지원 프로젝트에 새로운 제품 자료가 추가될 예정이어서 자료 범위가 넓어질 때의 평가 문제를 준비했다.

새로운 문서가 추가되면 검색 범위가 늘어나지만, 비슷한 모델의 사양과 다른 조건을 잘못 인용할 가능성도 커진다.

검토할 평가 유형:

- 해당 자료에 없는 제품을 질문하는 경우
- 여러 문서의 정보를 연결해야 하는 질문
- 표의 병합 셀과 서로 다른 측정 조건
- 각주가 제한하는 제품 범위
- 동일한 의미를 다른 말투나 표현으로 묻는 질문
- 여러 요구사항을 모두 답해야 하는 복합 질문

팀의 신규 평가 자료 관련 PR 중 일부는 병합됐고, 별도 모의 평가 문항 PR은 요청 시점에 열려 있었다. 평가 질문 작성과 실제 색인·서비스 반영·공식 점수 확인은 서로 다른 작업이다.

모의시험 결과를 공식 포털의 성적처럼 기록하지 않는다.

## 14. 회고
