## 2. 5강 — 회원 CRUD 연결

React 상태에서 입력한 데이터를 FastAPI로 보내고, 데이터베이스에 반영된 후 **회원 목록을 다시 조회**하도록 만들었다.

| 동작 | 요청 | 정상 응답 및 처리 |
| --- | --- | --- |
| 회원 목록 | `GET /members` | 200, 회원 배열 |
| 회원 등록 | `POST /members` | 201, 생성된 회원 |
| 회원 수정 | `PUT /members/{member_id}` | 200, 수정된 회원 |
| 회원 삭제 | `DELETE /members/{member_id}` | 204, 응답 Body 없음 |

프론트엔드의 `lib/members-api.ts`에 요청 함수를 모아 두고 `MemberWorkspace.tsx`에서 검색·폼·등록·수정·삭제 상태를 관리한다.

### 등록과 수정의 차이

- **등록:** 이름·이메일·나이·성별을 입력하고 POST한다.
- **수정:** 기존 정보를 폼에 불러와 값을 바꾼 후 PUT한다.
- **삭제:** 확인창을 거쳐 DELETE하며 성공 후 목록을 다시 불러온다.
- **조회:** 처음 화면을 열거나 변경 후 GET으로 최신 DB 상태를 확인한다.

회원 정보를 화면의 배열에만 더하면 재접속 시 사라질 수 있다. 이번 단계는 API가 실제 PostgreSQL에 요청을 반영하고 다시 조회하는 흐름을 확인한 것이 중요하다.

## 3. Backend: Router → Service → Repository → DB

이번 Phase 03의 회원관리 백엔드는 SQLAlchemy ORM을 사용한다.

```text
Next.js
  ↓ fetch + JSON
FastAPI Router
  ↓ 입력 검증(Pydantic)
Service
  ↓ 존재 여부·이메일 중복 확인
Repository
  ↓ SQLAlchemy Session / commit·rollback
PostgreSQL public.members
  ↓ 응답 모델
Next.js 목록·상세 갱신
```

핵심 역할을 구분했다.

- `member_router.py`: URL·HTTP Method·Status Code
- `member_service.py`: 회원 존재 여부, 중복 이메일, 업무 오류
- `member_repository.py`: 실제 DB 조회·등록·수정·삭제, 트랜잭션
- `schemas.py`: Pydantic의 Request/Response 계약
- `models.py`: `public.members` SQLAlchemy ORM 매핑
- `db.py`: Engine·Session 관리

요청 실패 시에는 상황에 따라 404(회원 없음), 409(중복 이메일), 422(요청 검증 실패) 등을 반환한다. 삭제 시 204는 본문을 반환하지 않는다.

**핵심:** `commit()`은 변경 확정, `rollback()`은 실패 시 변경 취소, `close()`는 DB 연결 정리의 역할이다.

## 4. 6강 — 동적 회원 상세 페이지

Next.js App Router로 목록 화면과 개별 회원 화면을 나눴다.

```text
app/
├── page.tsx
└── members/
    ├── page.tsx
    └── [memberId]/
        └── page.tsx
```

예시 URL:

```text
http://localhost:3000/members
http://localhost:3000/members/1
```

목록에서 **상세 보기**를 누르면 `Link`로 개별 회원 페이지로 이동한다. 상세 컴포넌트는 `useParams()`로 URL의 `memberId`를 읽고 `GET /members/{member_id}`를 호출한다.

- `Link`: Next.js 내부 페이지 이동
- `[memberId]`: 동적 경로 세그먼트
- `useParams()`: URL 파라미터 읽기
- `MemberDetail`: 선택 회원 한 건의 정보를 표시
- `Suspense`: Next.js 16 빌드에서 상세 페이지 경계 처리

개발 서버에서 보인다고 프로덕션 빌드가 반드시 성공하는 것은 아니다. 오늘은 상세 페이지의 `Suspense` 경계를 조정한 뒤 **최종 `npm run build` 성공 기록**을 확인했다.

## 5. 추가 실습 — 성별 필드를 DB부터 화면까지 확장

오늘 회원 정보에 `gender`를 추가했다.

| 값 | 의미 |
| --- | --- |
| `M` | 남성 |
| `F` | 여성 |
| `null` | 미지정 |

기존 `public.members` 테이블의 성별 칼럼이 없는 경우, 테이블 정의를 확인한 후 다음 SQL을 **한 번** 적용하는 방식으로 안내했다.

```sql
ALTER TABLE public.members
ADD COLUMN IF NOT EXISTS gender VARCHAR(20);
```

기존 회원의 성별을 이름으로 추측해서 채우지 않는다. 기존 `NULL` 값은 그대로 유지한다.

변경 범위:

```text
PostgreSQL gender 컬럼
→ SQLAlchemy Member.gender
→ Pydantic MemberCreate/Update/Patch/Response
→ Repository 등록·수정
→ Service
→ FastAPI JSON
→ TypeScript Member 타입
→ 회원 목록·등록/수정 폼·상세 화면
```

### 선택값을 다룰 때 배운 점

`gender`는 필수값이 아니므로 예전 요청과 호환된다.

- POST에서 생략 가능
- PUT에서 생략하면 기존 성별 보존
- PUT에서 명시적으로 `null`을 보내면 미지정 처리 가능
- PATCH에서는 현재 구현된 명시적 `null` 거부 규칙이 적용됨
- 화면에서 미지정을 선택하면 폼은 `gender: null`을 보냄

한 개의 필드를 추가하더라도 DB·Backend·Frontend의 계약을 함께 바꿔야 한다는 점을 알게 되었다.

**주의:** Phase 03의 실제 회원 식별자는 `member_id`이다. Phase 02 초기 강의의 `id` 스키마와 혼동하지 않는다. SQLAlchemy 모델을 바꾼다고 PostgreSQL의 실제 컬럼이 자동으로 추가되는 것도 아니다.

```text
Frontend State 변화 ≠ DB 저장
API 성공 후 GET 재조회 = DB 반영 상태를 화면에서 다시 확인

[memberId] = 동적 URL 경로
useParams  = 경로 변수 읽기

ORM 모델 변경 ≠ DB 컬럼 자동 변경
null / 필드 생략 = 서로 다른 의미
개발 서버 성공 ≠ 프로덕션 빌드·운영 배포 성공
```

## 12. 오늘의 회고

어제는 FastAPI에서 회원 목록을 읽어 화면에 표시하는 단계였다면, 오늘은 **실제 회원 등록·수정·삭제까지 가능한 프론트엔드와 개별 상세 페이지**를 만들었다.

특히 회원 정보를 수정하거나 삭제한 후 실제 API를 다시 조회해 화면에 반영하도록 구현하면서 **화면의 데이터와 DB의 상태를 일치시키는 방식**이 중요하다는 점을 배웠다. 동적 라우팅에서는 URL의 ID를 읽어 한 사람의 데이터를 조회하는 흐름도 익혔다.

추가로 성별 하나를 넣는 작업이 단순한 폼 항목 추가가 아니라 **DB 스키마, ORM 모델, API 입력/출력, TypeScript 타입, 목록과 상세 화면**을 함께 수정해야 하는 문제라는 것도 경험했다.

마지막으로 로컬 수동 검증과 빌드 통과는 확인했지만, **자동 E2E·CI·운영 환경 검증까지 된 것으로 과장하지 않는다.** 다음에는 안전한 테스트 데이터로 예외·빈 목록·오류 복구 시나리오를 더 체계적으로 검증할 계획이다.
