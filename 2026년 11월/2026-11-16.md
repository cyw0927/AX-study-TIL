## 1. 아파트 방송문 프로그램 — 실무 샘플을 코드 요구사항으로 바꾸기

기존 목표는 아파트 관리업무에서 쓸 방송문을 **대상·방송 종류·일정·장소 등의 입력값으로 빠르게 작성**하도록 만드는 것이었다.

오늘은 실제로 쓰였던 방송문 샘플을 분석한 후, 기존의 일반적인 안내문 생성 방식과 실무의 차이를 찾아 프로그램에 반영했다.

확인한 주요 개선 방향:

- 방송문을 한 번만 읽는 방식뿐 아니라 **같은 본문을 두 번 안내하는 형식** 지원
- 안내 시작과 종료의 **발신 주체를 설정·선택**할 수 있게 확장
- 날짜를 숫자만 적지 않고 **오늘·금일·내일** 등으로 표현
- 실제 날짜에 따른 **요일 계산** 옵션
- 특정 세대 안내에서 필요한 **동·호수 정보** 입력
- 기존 분류에 없던 **이사, 세대 공사 소음, 선거·투표** 유형 추가
- 준비된 개발환경에서 실행·종료하기 쉽도록 더블클릭용 실행 방법 정리

**원본 방송문 자체와 민감한 주소·세대 정보는 Git에 게시하지 않았다.** 실제 방송문은 공개 데이터가 아니므로 이 공개 TIL에도 포함하지 않는다.

### 배운 점: 기존의 템플릿만으로는 현장 문체가 재현되지 않는다

실제 문서를 받아 프로그램을 개선할 때는 무작정 AI 모델에 문서를 넣기 전에 다음을 구분해야 한다.

1. **반복되는 구조:** 도입부, 본문, 두 번째 낭독, 마무리
2. **고정된 사실:** 대상, 일정, 장소, 동·호수
3. **기관별 가변 표현:** 발신 주체와 인사말
4. **방송 유형별 필수 항목:** 이사·공사·선거 등 서로 다른 입력값
5. **사람의 최종 검토:** 사실이나 안전 관련 문구의 오기·누락 확인

실무에서 자주 쓰이는 문장 형태를 먼저 구조화하면, AI 모델을 사용하지 않는 **규칙 기반 생성기**도 유용한 초안을 만들 수 있다.

## 2. 기능 확장 — 데이터·Backend·Frontend를 함께 수정

이번 변경은 화면 항목만 추가한 것이 아니다. 입력값을 저장하고 다음에 불러올 수 있도록 **데이터 모델, Pydantic 스키마, 생성 로직, 설정 화면과 테스트 코드**를 함께 변경했다.

개념적인 데이터 흐름:

```text
방송 종류·대상·날짜·발신 주체 입력
        ↓
Frontend 폼 검증
        ↓
FastAPI / Pydantic
        ↓
종류별 필수 입력 확인
        ↓
규칙 기반 방송문 생성
        ↓
직원 미리보기·편집·저장
        ↓
DB에 원본/수정본 보관
```

오늘 중요한 구현 개념:

- **단일 필드 추가의 파급 범위:** Frontend 타입, Backend 입력/응답 모델, DB 칼럼, 저장·수정 로직을 일관되게 변경해야 한다.
- **요일은 날짜에서 계산:** 사용자가 요일을 임의 입력하게 두면 날짜와 요일이 서로 달라질 수 있다.
- **비어 있는 정보는 만들어 내지 않기:** 문장을 자연스럽게 만든다고 입력되지 않은 일정·호수를 추측하지 않는다.
- **기존 기본 동작 호환:** 새 옵션을 지정하지 않은 기존 사용자는 기존 방식으로 방송문을 생성할 수 있어야 한다.
- **반복 본문 생성:** 같은 내용을 두 번 읽을 경우 본문이 완전히 일치해야 중복 낭독에서 정보가 달라지지 않는다.

## 3. 기존 SQLite 스키마에 새 칼럼 추가

SQLAlchemy의 `Base.metadata.create_all()`은 **새 테이블 생성에는 편리하지만, 이미 존재하는 테이블에 새 칼럼을 자동으로 추가하지 않는다.**

이번에는 기존 SQLite 데이터를 유지하면서 새 필드를 추가할 수 있도록, 현재 칼럼을 확인하고 누락된 칼럼만 추가하는 보완 로직을 코드에 반영했다.

```text
앱 시작
→ 테이블 존재 확인
→ 현재 칼럼 목록 조회
→ 새 버전에 필요한 칼럼과 비교
→ 누락된 칼럼만 ALTER TABLE
→ 기존 레코드는 유지
```

이는 현재 로컬 시제품을 위한 간단한 대응이며, 장기적으로 복잡한 DB 마이그레이션을 관리할 때는 **Alembic과 명시적 버전 관리**가 더 적합하다.

**이번 커밋은 코드 반영을 확인한 것이며, 실제 사용자의 DB 백업·복원 시나리오를 오늘 완전히 검증했다는 뜻은 아니다.**

## 4. 한글 문장 생성과 테스트

방송문에는 조사, 날짜, 시간 표현과 같은 **한국어 특유의 규칙**이 필요하다.

오늘 변경된 코드에서는 숫자에 받침이 있는지 판정하는 도우미의 이름 오타를 수정하고, 날짜로 요일을 계산하는 함수를 추가했다. 생성한 날짜 표현이 본문과 검증 조건에서 동일하게 사용되도록 정리했다.

새 테스트 코드에는 다음 상황들이 포함된다.

- 새 옵션을 사용하지 않을 때 기존 기본 출력 유지
- 반복 낭독 선택 시 본문 두 번 생성
- 발신 주체에 따른 첫 문장 변화
- 날짜의 실제 요일 계산
- 오늘·금일·내일 표현
- 필수 동·호수 누락 시 검증 오류
- 새 방송 종류의 문구 생성
- 기존 방송문 저장·수정에 새 필드 반영

**상태:** 테스트 코드가 커밋에 포함된 사실은 확인했지만, 당일 `pytest` 전체 실행 결과와 통과 개수는 확인하지 못했다. 따라서 **테스트 추가 ≠ 테스트 통과**로 기록한다.

또한 이 프로그램은 **방송문을 작성·보관하는 도구**이며 실제 방송 송출 장비를 제어하는 기능은 아니다. 로그인 없는 로컬 시제품을 외부에 공개 배포한 것으로 보아서도 안 된다.

## 8. OIBC 모델 성능과 실험을 기록할 때 주의할 것

실험 기록에는 다양한 예측 모델·앙상블·잔차 보정·날씨 기반 방법이 포함된다.

새로운 방법이 복잡해 보이거나 이론적으로 타당하더라도, **모든 평가 기간에서 기존 기준보다 개선되는 것은 아니다.** 기존 실험에서는 일부 방법이 기준보다 오히려 성능이 나빠 채택되지 않았다.

그런 부정적인 결과도 삭제하지 않고 보관하는 이유는 다음과 같다.

1. 동일한 실패 실험을 반복하지 않는다.
2. 모델 채택·기각의 이유를 기록한다.
3. 과거 시점에 사용 가능한 데이터만 사용했는지 추적한다.
4. 다른 기간이나 새 데이터에서 재현할 수 있는지 판단한다.

또한 GitHub에 공개된 코드가 있다고 해서 **모델 학습용 원천 데이터와 파생 데이터가 함께 제공되거나 즉시 실행 가능한 것은 아니다.** README는 외부 입력 조건과 이전 스크립트의 재사용 위험을 별도로 설명한다.

## 9. 공개 문서에서 개인정보·협업 기록 관리

오늘 두 번째 OIBC 커밋은 기존 연구 문서에 포함됐던 팀원 이름을 **역할명으로 교체**하는 변경이다.

기술 기록에서는 누가 어떤 역할을 수행했는지 설명해야 할 수 있지만, 공개 저장소에 개인의 실명을 꼭 남겨야 하는 것은 아니다.

- 개인 이름 대신 역할 설명 사용
- 비공개 팀 자료와 공개 가능한 연구 요약 분리
- 실험에 필요한 코드·버전·지표는 유지
- 개인정보가 없어도 재현 가능한 기술 근거는 보존

이러한 문서 정리는 개발 산출물의 **공개 범위와 재사용성**을 함께 관리하는 일이다.

## 12. 오늘의 회고

오늘은 새로운 기술을 처음 배우는 일보다 **기존 프로그램을 실제 사용 상황에 맞게 고치는 방법**과 **오래 진행한 AI 프로젝트의 근거를 정돈하는 방법**을 경험했다.

방송문 프로그램은 단순히 자연스러운 문장을 만드는 것보다 **현장에서 반복해서 쓰는 구조, 누락하면 안 되는 정보, 작성 기관의 차이**를 반영하는 것이 중요했다. 특히 날짜·요일·동·호수와 같은 사실값은 사람이 입력하거나 계산할 수 있는 규칙으로 처리하고, AI가 임의로 만들어 내지 않게 해야 한다.

OIBC는 Claude·Codex가 수행한 과거 실험을 정리하며 **모델 결과를 설명하는 능력과 재현할 수 있는 기록의 중요성**을 확인했다. 좋은 결과뿐 아니라 기각된 실험도 모아 두면, 나중에 어떤 판단이 적절했는지 돌아볼 수 있다.

오늘의 핵심은 **코드를 만들었다는 것, 테스트 코드가 있다는 것, 테스트에 통과했다는 것, 실제 현장에서 검증됐다는 것을 서로 구별하는 일**이다.
