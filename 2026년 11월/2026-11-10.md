## 2. 1강 — Next.js 첫 화면과 개발환경

Next.js App Router를 이용해 회원관리 첫 화면을 만들었다. 초기 단계에서는 API나 데이터베이스를 연결하지 않고 프론트엔드 화면과 개발환경을 먼저 준비했다.

프로젝트에 확인된 주요 파일:

```text
member-next-app/
├── app/
│   ├── layout.tsx
│   ├── page.tsx
│   └── globals.css
├── package.json
├── tsconfig.json
└── next.config.ts
```

README의 환경 확인 기록:

- Node.js 24.20.0
- npm 11.19.0
- Next.js 16.4.6

Next.js 실행에 필요한 `@swc/helpers`가 빠져서 시작하지 못한 문제를 기존 잠금 파일을 활용한 `npm install --prefer-offline`으로 복구했다. 프로젝트를 새로 만드는 대신 의존성을 복원했다.

`npm run dev`, `npx tsc --noEmit`, `npm run lint`, `npm run build` 통과 기록이 있으며, 설치 과정에서 중간 등급 보안 감사 경고 7건이 표시됐다. 임의의 의존성 갱신을 피하기 위해 `npm audit fix`는 자동 실행하지 않았다.

**학습 포인트:** JavaScript 프론트엔드를 실행하는 Node/npm 환경과 Python 백엔드 가상환경은 서로 다른 역할을 한다.

## 4. 3강 — State·Event와 검색·폼

3강에서는 `MemberWorkspace` 클라이언트 컴포넌트에 React State를 추가했다.

## 5. 4강 — Next.js와 FastAPI 연결

오늘 가장 중요한 실습은 **샘플 배열을 실제 API 조회 결과로 교체한 것**이다.

```text
Next.js (localhost:3000)
  ↓ fetch GET /members
FastAPI (127.0.0.1:8000)
  ↓ SQLAlchemy / PostgreSQL
public.members
  ↓ 회원 JSON 배열
React 상태 갱신 → MemberList / MemberCard 출력
```

Phase 03에 별도 `backend/app` 코드를 준비해 기존 회원관리 API를 활용했다. FastAPI 앱에는 회원 조회·생성·수정·삭제 라우트, Service·Repository, SQLAlchemy ORM 모델, Pydantic 스키마가 들어 있다. **이번 4강 프론트엔드 실습의 실제 수행 범위는 GET 목록 조회**이며, 다른 CRUD까지 브라우저에서 모두 검증했다고 주장하지 않는다.

프론트엔드 파일의 역할:

| 파일 | 역할 |
| --- | --- |
| `lib/members-api.ts` | `fetch`, HTTP/JSON 검사, API 데이터 정규화 |
| `components/MemberWorkspace.tsx` | 데이터 요청과 React 상태 관리 |
| `components/MemberList.tsx` | 목록·카드 렌더링 |
| `components/MemberCard.tsx` | 회원별 정보 표시 |
| `app/page.tsx` | 화면 뼈대 |

환경변수 `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000`으로 백엔드의 주소를 지정하고, 인증정보를 담는 실제 `.env` 파일은 Git에 올리지 않았다.

### API 응답 스키마

README와 코드에 따르면 확인된 `GET /members` 결과의 필드는 다음과 같다.

```json
{"member_id":1,"name":"Kim","email":"kim@example.com","age":30}
```

학습 단계에 따라 ID 컬럼 이름이 `id`인 경우도 있어 API 클라이언트는 `member_id ?? id`로 정규화하도록 작성했다. 단, 실제 수업의 회원 테이블은 **`member_id`**로 확인됐으며, 이전 Phase 02의 다른 DB 스키마와 혼동하지 않도록 주의했다.

API가 HTTP 200을 반환했는지만 보는 것이 아니라 배열 여부와 `member_id/name/email/age` 형식도 검사한다.

### 비동기 요청 처리

`useEffect`에서 처음 목록을 불러오고 `AbortController`로 이전 요청을 취소한다.

다음 UI 상태를 구분했다.

- 불러오는 중
- 회원 0명

- 다시 조회

입력 폼은 이전 강의처럼 **미리보기 전용**이며 실제 저장은 다음 강의의 작업이다.

### 데이터 출처와 스냅샷

도구로 사용할 수 있는 데이터의 시간 범위를 모델이 임의로 넓히지 않고 **질문 시점(as-of)에 이용 가능한 관측값**만 제공한다.

### 에이전트 도구

```text
list_series
get_latest
get_change
conditional_outcomes
```

각 도구가 반환한 수치를 Evidence로 등록한다. 모델이 수치를 기억이나 추측으로 끼워 넣지 못하도록 답변 근거를 별도로 추적한다.

### 메모 검증 방식

에이전트가 생성한 메모의 숫자는 다음과 같은 Evidence 슬롯으로 관리한다.

```text
{{ev:<id>}}
{{date:<id>}}
```

검증기는 근거 없이 직접 적힌 숫자, 존재하지 않는 Evidence, 기준 시점 이후의 자료, 잘못된 슬롯 등을 거부한다. 위반한 답변은 모델에 돌려주어 최대 두 번 수정하도록 설계했다.

## 11. 오늘의 핵심 정리

```text
Component = 역할별 UI 단위
Props     = 부모 → 자식 데이터 전달
State     = 변경 시 렌더링에 반영되는 상태
Event     = 입력·클릭 등 사용자 동작 처리

useEffect       = 화면에서 외부 요청 같은 부수효과 연결
AbortController = 더 이상 유효하지 않은 요청 취소
fetch/JSON 검증 = HTTP 성공과 데이터 형식 모두 확인

GET 200 + 화면 출력 ≠ POST 저장까지 검증
단위 테스트 성공 ≠ 실 LLM API 실행 성공
PR 생성 ≠ main 병합
팀원 PR 병합 ≠ 내가 구현한 기능
```

## 12. 오늘의 회고

오늘은 **회원 목록을 화면에 가짜 배열로 표시하는 것과 실제 API에서 읽어오는 것의 차이**를 분명하게 이해할 수 있었다. Next.js와 React에서는 컴포넌트를 나누는 것뿐 아니라, API 로딩과 오류·취소·검색 같은 비동기 상태를 관리하는 일이 중요했다.

또 기존 FastAPI 백엔드를 재활용하면서 프론트엔드와 백엔드가 서로 다른 실행 환경·포트·데이터 계약을 가진다는 점을 직접 확인했다. 폼은 아직 미리보기여서 회원 생성까지 완료한 것은 아니며, 다음 강의에서 POST를 연결해야 한다.

GMIA에서는 AI가 작성한 금융 분석 문장에 **실제로 조회된 데이터 근거를 붙이고 기준 시점 이후의 정보를 차단하는 구조**를 설계했다. 그러나 실제 Claude 호출과 미병합 브랜치 정리가 남아 있으므로 시제품의 검증 범위를 과장하지 않는 것이 중요하다.

팀 프로젝트에서도 같은 원칙을 적용해야 한다. PR이 병합된 사실, 스테이징에 실제 데이터가 들어간 사실, 사용자가 정상적으로 기능을 이용하는 사실은 각각 별도로 확인해야 한다.
