# 🐱 게임 프로젝트 ERD 분석 — 현재 최종 ERD 기준

> **목적**  
> 현재 팀에서 사용하는 **최종 ERD 19개 테이블**을 기준으로, 각 테이블이 어떤 역할을 하고 서로 어떻게 연결되는지 정리한 문서이다.
>
> **정리 원칙**  
> 기존 ERD에 실제로 존재하는 테이블과 컬럼명을 그대로 사용한다. 설명을 지나치게 섹터별로 쪼개지 않고, **한 테이블 = 한 덩어리** 형식으로 1번부터 19번까지 순서대로 정리한다.
>
> **현재 최종 ERD에서 반영된 주요 변경**  
> `USERS.external_student_id`, `TASKS.title/description/hint_text`, `TASK_ATTEMPTS`의 모드별 context 연결, `CAT_MEMORIES.created_at`, nullable `is_correct/is_passed`, `ROOM_TASKS.task_order = int` 등이 반영된 상태를 기준으로 한다.

---

# 0. 전체 구조 한눈에 보기

현재 19개 테이블은 기능상 다음처럼 묶어 볼 수 있다.

| 기능 | 테이블 |
| --- | --- |
| 사용자 / 출석 | `USERS`, `ATTENDANCES` |
| 학습 / 문제 / 숙련도 | `CONCEPTS`, `TASKS`, `USER_PROFICIENCY`, `TASK_ATTEMPTS` |
| 실시간 배틀 | `ROOMS`, `ROOM_PARTICIPANTS`, `ROOM_TASKS` |
| 랭킹 | `RANKING_GROUPS`, `RANKING_PARTICIPANTS`, `RANK_CHALLENGES`, `RANK_CHALLENGE_TASKS` |
| 아이템 / 하우징 | `ITEMS`, `INVENTORIES`, `PLACED_OBJECTS` |
| 고양이 | `CATS`, `USER_CATS`, `CAT_MEMORIES` |

## 기능별 관계도

```text
[사용자 / 출석]
USERS ──────────────< ATTENDANCES

[학습]
CONCEPTS ───────────< TASKS ───────────< TASK_ATTEMPTS >──────── USERS
   │                                        │
   └───────────────< USER_PROFICIENCY >─────┘

[실시간 배틀]
USERS ─────< ROOM_PARTICIPANTS >──── ROOMS ─────< ROOM_TASKS >──── TASKS

[랭킹]
USERS ─────< RANKING_PARTICIPANTS >──── RANKING_GROUPS
  │                                           │
  └─────< RANK_CHALLENGES >───────────────────┘
                 │
                 └────< RANK_CHALLENGE_TASKS >──── TASKS

[아이템 / 하우징]
USERS ─────< INVENTORIES >──── ITEMS
  │                              │
  └─────< PLACED_OBJECTS >───────┘

[고양이]
USERS ─────< USER_CATS >──── CATS
                │
                └────< CAT_MEMORIES
```

# 0-1. PK / FK 기본 이해

- **PK(Primary Key)**: 각 테이블의 한 행을 고유하게 식별하는 키이다.
- **FK(Foreign Key)**: 다른 테이블의 PK를 참조하여 테이블 사이 관계를 연결하는 값이다.
- 대부분의 테이블이 `id`를 별도의 PK로 가지며, `user_id`, `task_id`, `room_id`처럼 다른 테이블을 가리키는 컬럼이 FK가 된다.
- 서로 다른 테이블의 `id` 값이 같아도 문제없다. 각 테이블의 PK는 서로 독립적이다.

# 1. USERS

## 역할

플랫폼 내 사용자 데이터의 중심이 되는 테이블이다. 사용자 계정 식별 정보뿐 아니라 현재 재화, 마일리지, 하우스 레벨, 현재 적용 중인 벽지와 바닥처럼 **사용자에게 직접 귀속되는 현재 상태값**을 함께 저장한다.

쉽게 말하면 **“이 사용자가 누구이고 현재 게임에서 어떤 상태인가?”**를 나타내는 테이블이다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 게임 내부에서 사용하는 사용자 고유 식별자 |
| `external_student_id` | string UK | 외부 학생관리 시스템의 학생 식별자 |
| `username` | string | 사용자 이름 또는 닉네임 |
| `role` | string | 학습자·교육 담당자·운영자 등 역할 |
| `soft_balance` | int | 일반 재화 보유량 |
| `hard_balance` | int | 특수 재화 보유량 |
| `mileage` | int | 중복 보상 등에 사용하는 마일리지 |
| `house_level` | int | 현재 하우스 레벨 |
| `wallpaper_item_id` | int FK, nullable | 현재 적용 중인 벽지 `ITEMS.id` |
| `floor_item_id` | int FK, nullable | 현재 적용 중인 바닥 `ITEMS.id` |
| `created_at` | datetime | 계정 생성 시각 |

## 관계

`USERS`는 거의 모든 사용자 활동 데이터의 출발점이다.

```text
USERS
 ├─ ATTENDANCES
 ├─ USER_PROFICIENCY
 ├─ TASK_ATTEMPTS
 ├─ ROOM_PARTICIPANTS
 ├─ RANKING_PARTICIPANTS
 ├─ RANK_CHALLENGES
 ├─ INVENTORIES
 ├─ PLACED_OBJECTS
 └─ USER_CATS
```

## 설계 의미

`id`는 게임 내부 UUID로 유지하고, 외부 학생관리 시스템 식별자는 `external_student_id`로 분리했다. 외부 시스템의 ID 규칙이 바뀌더라도 내부 PK 구조가 영향을 덜 받도록 하기 위한 구조이다.

---

# 2. ATTENDANCES

## 역할

사용자의 날짜별 출석 기록과 연속 출석 일수, 일일 미션 완료 여부를 저장한다.

즉 **“오늘 출석했는가?”, “현재 몇 일 연속 출석 중인가?”, “오늘 일일 미션을 완료했는가?”**를 판단하는 기준이 된다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 출석 기록 한 건의 고유 ID |
| `user_id` | uuid FK | 출석한 사용자 `USERS.id` |
| `check_in_date` | date | 출석 날짜 |
| `streak_count` | int | 해당 날짜 기준 연속 출석 일수 |
| `daily_quest_completed` | boolean | 일일 미션 완료 여부 |

## 관계

```text
USERS 1 ───── N ATTENDANCES
```

한 사용자는 여러 날짜의 출석 기록을 가진다.

또한 현재 최종 구조에서는 일일 미션에서 발생한 제출을 연결하기 위해 `TASK_ATTEMPTS.attendance_id`가 이 테이블을 참조할 수 있다.

```text
ATTENDANCES ─────< TASK_ATTEMPTS
                 context_type = DAILY
```

---

# 3. CONCEPTS

## 역할

Python 학습 내용을 개념 단위로 분류하는 기준 테이블이다.

예를 들어 변수, 조건문, 반복문, 리스트, 딕셔너리, 함수 같은 학습 단원을 정의한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int PK | 개념 고유 ID |
| `name` | string | 개념명 |

## 관계

```text
CONCEPTS
 ├────< TASKS
 └────< USER_PROFICIENCY
```

- `TASKS.concept_id` → 문제의 대표 학습 개념
- `USER_PROFICIENCY.concept_id` → 사용자의 해당 개념 숙련도

즉 문제 분류와 개인별 숙련도 계산이 같은 개념 기준을 공유하도록 하는 테이블이다.

---

# 4. TASKS

## 역할

사용자가 실제로 풀 문제의 원본 데이터를 저장하는 **문제 은행 테이블**이다.

문제 제목과 설명, 문제 유형, 난이도, 기본 코드, 테스트 케이스, 힌트, 활성 상태를 가지고 있으며 실제 제출 기록은 저장하지 않는다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 문제 고유 ID |
| `concept_id` | int FK | 대표 학습 개념 `CONCEPTS.id` |
| `title` | string | 문제 제목 |
| `type` | string | 문제 유형 |
| `difficulty` | string | 문제 난이도 |
| `description` | text | 화면에 표시할 문제 설명 |
| `template_code` | text | 코드 작성형 문제의 기본 코드 틀 |
| `test_cases` | text | 자동 채점용 테스트 케이스 |
| `hint_text` | text, nullable | 문제별 고정 힌트 |
| `is_active` | boolean | 현재 출제 가능 여부 |

## 관계

```text
CONCEPTS ─────< TASKS
TASKS ────────< TASK_ATTEMPTS
TASKS ────────< ROOM_TASKS
TASKS ────────< RANK_CHALLENGE_TASKS
```

하나의 문제 은행을 일반 학습, 일일 미션, 배틀, 랭킹전에서 공통으로 재사용한다.

## 설계 의미

문제에 오류가 생겼다고 실제 행을 삭제하면 과거 `TASK_ATTEMPTS` 같은 기록과 연결이 깨질 수 있으므로 `is_active`로 출제 여부를 관리한다.

---

# 5. USER_PROFICIENCY

## 역할

사용자가 각 Python 개념을 얼마나 잘 이해하고 있는지를 개념별로 저장하는 테이블이다.

예를 들어 전체 점수 하나가 아니라 다음처럼 관리한다.

```text
반복문 3
조건문 4
리스트 2
함수 1
```

이 데이터는 다음 문제 추천과 개인화에 사용할 수 있다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 숙련도 행 고유 ID |
| `user_id` | uuid FK | 사용자 `USERS.id` |
| `concept_id` | int FK | 학습 개념 `CONCEPTS.id` |
| `proficiency_level` | int | 해당 개념에 대한 현재 숙련도 |

## 관계

```text
USERS ─────────< USER_PROFICIENCY >──────── CONCEPTS
```

`USERS`와 `CONCEPTS`의 관계를 연결하면서 **특정 사용자의 특정 개념 숙련도**를 저장한다.

---

# 6. TASK_ATTEMPTS

## 역할

사용자가 문제를 실제로 제출한 **풀이 시도 및 비동기 채점 작업 기록**을 저장한다.

누가 어떤 문제에 어떤 코드를 제출했는지, 현재 채점 상태가 무엇인지, 정답인지, 힌트를 사용했는지, 언제 제출했는지를 기록한다.

현재 최종 ERD에서는 여기에 **풀이가 발생한 게임 모드의 맥락(context)**까지 저장한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 제출 시도 한 건의 ID |
| `user_id` | uuid FK | 제출한 사용자 `USERS.id` |
| `task_id` | uuid FK | 제출한 문제 `TASKS.id` |
| `context_type` | string | `LEARNING`, `DAILY`, `BATTLE`, `RANKING` 중 하나 |
| `attendance_id` | uuid FK, nullable | 일일 미션이면 해당 `ATTENDANCES.id` |
| `room_task_id` | uuid FK, nullable | 배틀이면 해당 `ROOM_TASKS.id` |
| `rank_challenge_task_id` | uuid FK, nullable | 랭킹전이면 해당 `RANK_CHALLENGE_TASKS.id` |
| `submitted_code` | text | 사용자가 실제 제출한 코드 |
| `status` | string | 비동기 채점 처리 상태 |
| `is_correct` | boolean, nullable | 채점 전 `NULL`, 정답 `true`, 오답 `false` |
| `used_hint` | boolean | 힌트 사용 여부 |
| `attempted_at` | datetime | 제출 시각 |

## 모드별 저장 규칙

| 모드 | `context_type` | 연결 FK |
| --- | --- | --- |
| 일반 학습 | `LEARNING` | 세 context FK 모두 `NULL` |
| 일일 미션 | `DAILY` | `attendance_id` 사용 |
| 팀 배틀 | `BATTLE` | `room_task_id` 사용 |
| 랭킹전 | `RANKING` | `rank_challenge_task_id` 사용 |

잘못된 `context_type`과 FK 조합이 저장되지 않도록 현재 구조에서는 `ck_task_attempts_context` CHECK 제약조건으로 모드와 연결 ID의 조합을 검증한다.

## 비동기 채점 흐름

```text
사용자 코드 제출
      ↓
TASK_ATTEMPTS 생성
status = PENDING
      ↓
백그라운드 채점 작업에 attempt_id 전달
      ↓
status = RUNNING
      ↓
Docker 샌드박스에서 실행
      ↓
is_correct / 최종 status 저장
      ↓
context_type 확인
      ↓
DAILY / BATTLE / RANKING 진행 상태 반영
```

서버가 채점 중 재시작되더라도 제출 코드와 상태, context 연결 정보가 DB에 남아 있기 때문에 `PENDING` 또는 `RUNNING` 작업을 다시 확인할 수 있다.

# 7. ROOMS

## 역할

실시간 배틀 방 자체의 정보를 저장한다.

방 제목, 방장, 현재 상태, 최대 인원을 관리한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 방 고유 ID |
| `title` | string | 로비에 표시되는 방 제목 |
| `host_user_id` | uuid FK | 방장 `USERS.id` |
| `status` | string | 방 상태 |
| `max_participants` | int | 최대 참가 인원 |

## 관계

```text
ROOMS
 ├────< ROOM_PARTICIPANTS
 └────< ROOM_TASKS
```

`ROOMS` 자체에는 참가자 목록이나 문제 목록을 직접 넣지 않고 각각 별도의 연결 테이블로 분리한다.

---

# 8. ROOM_PARTICIPANTS

## 역할

어떤 사용자가 어떤 배틀 방에 참가하고 있는지와 해당 사용자의 팀, 현재 점수, 준비 상태를 저장한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 방 참가 기록 ID |
| `room_id` | uuid FK | 참가 중인 방 `ROOMS.id` |
| `user_id` | uuid FK | 참가 사용자 `USERS.id` |
| `team_name` | string, nullable | 팀전이면 팀명, 개인전이면 `NULL` |
| `current_score` | int | 현재 획득 점수 |
| `is_ready` | boolean | 시작 준비 완료 여부 |

## 관계

```text
USERS ─────< ROOM_PARTICIPANTS >───── ROOMS
```

하나의 방에는 여러 사용자가 참가할 수 있고, 한 사용자도 여러 방에 참가할 수 있으므로 중간 연결 테이블 역할을 한다.

---

# 9. ROOM_TASKS

## 역할

하나의 배틀 방에서 어떤 문제를 어떤 순서로 출제할지 저장한다.

같은 방에 참가한 사용자나 양 팀이 동일한 문제를 동일한 순서로 풀도록 문제 목록을 고정하는 역할을 한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 방-문제 배정 기록 ID |
| `room_id` | uuid FK | 대상 배틀 방 `ROOMS.id` |
| `task_id` | uuid FK | 출제 문제 `TASKS.id` |
| `task_order` | int | 방 안에서 문제 출제 순서 |

## 관계

```text
ROOMS ─────< ROOM_TASKS >───── TASKS
```

또한 배틀 중 실제 제출은 `TASK_ATTEMPTS.room_task_id`를 통해 이 문제 배정 기록과 연결된다.

```text
ROOM_TASKS ─────< TASK_ATTEMPTS
                 context_type = BATTLE
```

---

# 10. RANKING_GROUPS

## 역할

글로벌 단일 랭킹이 아니라 특정 그룹 안에서 경쟁할 수 있도록 **랭킹 그룹 자체**를 저장한다.

예를 들어 `1분반`, `2분반` 같은 그룹 단위 랭킹을 구성할 수 있다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 랭킹 그룹 고유 ID |
| `name` | string | 랭킹 그룹 이름 |
| `owner_user_id` | uuid FK | 그룹 생성자/소유자 `USERS.id` |

## 관계

```text
RANKING_GROUPS
 ├────< RANKING_PARTICIPANTS
 └────< RANK_CHALLENGES
```

---

# 11. RANKING_PARTICIPANTS

## 역할

어떤 사용자가 어떤 랭킹 그룹에 참여하고 있으며, 그 그룹 안에서 현재 몇 점의 랭킹 점수를 가지고 있는지를 저장한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 랭킹 참가 기록 ID |
| `group_id` | uuid FK | 랭킹 그룹 `RANKING_GROUPS.id` |
| `user_id` | uuid FK | 참가 사용자 `USERS.id` |
| `current_rank_score` | int | 해당 그룹 내 현재 랭킹 점수 |

## 관계

```text
USERS ─────< RANKING_PARTICIPANTS >───── RANKING_GROUPS
```

랭킹 점수를 `USERS`에 하나만 두지 않고 그룹 참가 기록에 저장하기 때문에, 같은 사용자도 그룹마다 서로 다른 점수를 가질 수 있다.

---

# 12. RANK_CHALLENGES

## 역할

사용자가 특정 랭킹 그룹에서 진행한 **한 번의 랭킹 도전 세션 전체**를 저장한다.

누가 도전했는지, 어느 그룹의 도전인지, 현재 상태와 시작·만료 시각이 언제인지를 관리한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 랭킹 도전 ID |
| `user_id` | uuid FK | 도전 사용자 `USERS.id` |
| `group_id` | uuid FK | 대상 랭킹 그룹 `RANKING_GROUPS.id` |
| `status` | string | 도전 상태 |
| `started_at` | datetime | 도전 시작 시각 |
| `expires_at` | datetime | 도전 만료 시각 |

## 관계

```text
USERS ─────< RANK_CHALLENGES >───── RANKING_GROUPS
                    │
                    └────< RANK_CHALLENGE_TASKS
```

`expires_at`을 절대 시각으로 저장하므로 클라이언트가 재접속하더라도 서버 기준으로 제한시간 만료 여부를 판단할 수 있다.

---

# 13. RANK_CHALLENGE_TASKS

## 역할

한 번의 `RANK_CHALLENGES` 안에 어떤 문제들이 들어 있는지, 각 문제의 순서와 통과 여부, 작성 중 저장 코드가 무엇인지 관리한다.

즉 `RANK_CHALLENGES`가 시험 전체라면 이 테이블은 **시험 안의 각 문제 진행 상태**이다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 랭킹 도전 내 문제 기록 ID |
| `challenge_id` | uuid FK | 소속 도전 `RANK_CHALLENGES.id` |
| `task_id` | uuid FK | 실제 문제 `TASKS.id` |
| `is_passed` | boolean, nullable | 미시도 `NULL`, 통과/실패 상태 저장 |
| `saved_code` | text, nullable | 랭킹 도전 중 저장한 작성 코드 |
| `task_order` | int | 랭킹 도전 내 문제 순서 |

## 관계

```text
RANK_CHALLENGES ─────< RANK_CHALLENGE_TASKS >───── TASKS
```

랭킹전에서 실제 제출이 발생하면 `TASK_ATTEMPTS.rank_challenge_task_id`가 해당 문제 진행 기록을 가리킨다.

```text
RANK_CHALLENGE_TASKS ─────< TASK_ATTEMPTS
                           context_type = RANKING
```

## `saved_code`와 `TASK_ATTEMPTS.submitted_code`의 차이

- `saved_code` → 랭킹 도전 중 작성하다 저장해 둔 코드
- `submitted_code` → 실제 채점을 위해 제출한 코드

목적이 서로 다르다.

---

# 14. ITEMS

## 역할

게임에 존재하는 가구, 벽지, 바닥 등 **아이템 종류 자체의 원본 정보**를 저장한다.

사용자가 실제로 해당 아이템을 가지고 있는지는 `INVENTORIES`가 담당한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int PK | 아이템 종류 고유 ID |
| `category` | string | 아이템 종류 |
| `name` | string | 표시 이름 |
| `price` | int | 아이템 가격 |

## 관계

```text
ITEMS
 ├────< INVENTORIES
 ├────< PLACED_OBJECTS
 ├──── USERS.wallpaper_item_id
 └──── USERS.floor_item_id
```

즉 하나의 아이템 마스터 데이터를 상점, 인벤토리, 하우징 배치에서 공통으로 사용한다.

---

# 15. INVENTORIES

## 역할

어떤 사용자가 어떤 아이템을 몇 개 보유하고 있는지 저장한다.

`ITEMS`가 아이템 원본이라면 `INVENTORIES`는 **사용자별 실제 소유 상태**이다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 인벤토리 기록 ID |
| `user_id` | uuid FK | 소유 사용자 `USERS.id` |
| `item_id` | int FK | 보유 아이템 `ITEMS.id` |
| `quantity` | int | 보유 수량 |

## 관계

```text
USERS ─────< INVENTORIES >───── ITEMS
```

예를 들어 `ITEMS`에 파란 소파라는 아이템 종류가 한 번만 존재하고, `INVENTORIES`에서 사용자 A가 2개, 사용자 B가 1개를 가진 상태를 각각 저장한다.

---

# 16. PLACED_OBJECTS

## 역할

사용자가 보유한 아이템 중 **실제로 하우스 공간에 배치한 오브젝트**를 저장한다.

어떤 아이템을 어느 위치와 방향에 배치했는지 `position_data`에 보관한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 배치 오브젝트 기록 ID |
| `user_id` | uuid FK | 하우스 주인 `USERS.id` |
| `item_id` | int FK | 배치한 아이템 `ITEMS.id` |
| `position_data` | jsonb | 위치·회전 등 배치 데이터 |

## 관계

```text
USERS ─────< PLACED_OBJECTS >───── ITEMS
```

예시 `position_data`:

```json
{
  "x": 3,
  "y": 5,
  "rotation": 90
}
```

벽지와 바닥은 좌표 배치가 필요한 오브젝트가 아니므로 `PLACED_OBJECTS`가 아니라 `USERS.wallpaper_item_id`, `USERS.floor_item_id`로 관리한다.

---

# 17. CATS

## 역할

뽑기 등으로 획득할 수 있는 **고양이 종류의 원본 정보**를 저장한다.

고양이의 기본 이름, 페르소나, 희귀도를 정의한다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int PK | 고양이 종류 고유 ID |
| `name` | string | 고양이 이름 |
| `persona` | string | 기본 성격과 대화 스타일 |
| `rarity` | string | 희귀 등급 |

## 관계

```text
CATS 1 ───── N USER_CATS
```

`CATS`는 고양이 원본 마스터이며, 사용자가 실제로 획득한 상태는 `USER_CATS`에 저장한다.

---

# 18. USER_CATS

## 역할

특정 사용자가 획득한 고양이 보유 정보를 저장한다.

같은 `CATS` 원본을 사용하더라도 사용자마다 별도의 `USER_CATS.id`를 가지므로 이후 고양이별 기억을 독립적으로 연결할 수 있다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 사용자 고양이 보유 기록 ID |
| `user_id` | uuid FK | 고양이 소유 사용자 `USERS.id` |
| `cat_id` | int FK | 고양이 원본 `CATS.id` |

## 관계

```text
USERS ─────< USER_CATS >───── CATS
                 │
                 └────< CAT_MEMORIES
```

`CATS.id`는 고양이 종류를 뜻하고, `USER_CATS.id`는 **특정 사용자가 가진 그 고양이**를 뜻한다.

---

# 19. CAT_MEMORIES

## 역할

특정 사용자가 보유한 특정 고양이와의 대화나 관계에서 **다음 대화에 기억할 핵심 내용**을 요약해 저장한다.

고양이 종류 전체가 기억을 공유하는 것이 아니라 `USER_CATS.id`에 연결되므로 사용자별 고양이마다 독립적인 기억을 가질 수 있다.

## 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid PK | 고양이 기억 기록 ID |
| `user_cat_id` | uuid FK | 기억 주체가 되는 사용자 고양이 `USER_CATS.id` |
| `context_summary` | text | 다음 대화에서 사용할 핵심 기억 요약 |
| `created_at` | datetime | 기억 생성 시각 |

## 관계

```text
USER_CATS 1 ───── N CAT_MEMORIES
```

`created_at`이 있기 때문에 여러 기억이 쌓였을 때 어떤 기억이 더 최근에 만들어졌는지 판단할 수 있다.

예시:

```text
사용자는 반복문을 어려워하지만 꾸준히 공부하고 있다.
```

# 20. 현재 최종 ERD의 핵심 연결

## 20-1. 학습 기록 흐름

```text
CONCEPTS
   ↓
TASKS
   ↓
TASK_ATTEMPTS
   ↓
USER_PROFICIENCY 갱신에 활용
```

`TASKS`는 문제 원본이고 `TASK_ATTEMPTS`는 실제 제출 이력이다. 이 둘을 구분해야 같은 문제를 여러 번 풀어도 모든 시도를 남길 수 있다.

## 20-2. 비동기 채점과 게임 모드 연결

```text
                    ┌─ attendance_id ─────────── DAILY
TASK_ATTEMPTS ──────┼─ room_task_id ─────────── BATTLE
 context_type       └─ rank_challenge_task_id ─ RANKING
```

일반 학습은 별도의 context FK 없이 `LEARNING`으로 저장한다.

## 20-3. 배틀 흐름

```text
ROOMS
 ├─ ROOM_PARTICIPANTS
 └─ ROOM_TASKS ── TASKS
         │
         └─ TASK_ATTEMPTS
```

`ROOMS`는 방 자체, `ROOM_PARTICIPANTS`는 참가자, `ROOM_TASKS`는 방에서 출제할 문제이다.

## 20-4. 랭킹 흐름

```text
RANKING_GROUPS
 ├─ RANKING_PARTICIPANTS
 └─ RANK_CHALLENGES
        └─ RANK_CHALLENGE_TASKS ── TASKS
                     │
                     └─ TASK_ATTEMPTS
```

랭킹 그룹의 현재 점수와 한 번의 도전 세션, 그 안의 문제 진행 상태를 서로 분리한다.

## 20-5. 하우징 흐름

```text
ITEMS
  ↓
INVENTORIES
  ↓
PLACED_OBJECTS
```

`ITEMS`는 원본, `INVENTORIES`는 소유, `PLACED_OBJECTS`는 실제 배치이다.

## 20-6. 고양이 흐름

```text
CATS
  ↓
USER_CATS
  ↓
CAT_MEMORIES
```

`CATS`는 고양이 종류, `USER_CATS`는 사용자 보유 상태, `CAT_MEMORIES`는 그 개별 고양이와의 기억이다.

# 21. 헷갈리기 쉬운 테이블 비교

| 테이블 A | 테이블 B | 차이 |
| --- | --- | --- |
| `TASKS` | `TASK_ATTEMPTS` | 문제 원본 / 실제 제출 기록 |
| `CONCEPTS` | `USER_PROFICIENCY` | 개념 기준표 / 사용자별 개념 숙련도 |
| `ROOMS` | `ROOM_PARTICIPANTS` | 배틀 방 / 방 참가자 |
| `ROOM_TASKS` | `TASK_ATTEMPTS` | 방에 배정된 문제 / 사용자가 실제 제출한 시도 |
| `RANK_CHALLENGES` | `RANK_CHALLENGE_TASKS` | 랭킹 도전 전체 / 도전 안의 개별 문제 상태 |
| `ITEMS` | `INVENTORIES` | 아이템 원본 / 사용자 보유 수량 |
| `INVENTORIES` | `PLACED_OBJECTS` | 가지고 있는 아이템 / 실제 하우스에 배치한 아이템 |
| `CATS` | `USER_CATS` | 고양이 종류 / 사용자가 실제 보유한 고양이 |
| `USER_CATS` | `CAT_MEMORIES` | 보유 고양이 / 그 고양이의 기억 |

# 23. 현재 최종 ERD에서 특히 중요한 포인트

1. `USERS.id`와 외부 학생 ID를 분리해 내부 식별자를 안정적으로 유지한다.
2. `TASKS`에 `title`, `description`, `hint_text`가 있어 실제 문제 화면 구성에 필요한 데이터를 저장할 수 있다.
3. `TASK_ATTEMPTS.is_correct`는 nullable이므로 비동기 채점 전/후 상태를 구분할 수 있다.
4. `TASK_ATTEMPTS.context_type`과 세 개의 nullable FK를 이용해 일반 학습·일일 미션·배틀·랭킹전 제출을 하나의 제출 테이블에서 관리한다.
5. `ROOM_TASKS.task_order`는 `int`로 문제 순서를 표현한다.
6. `RANK_CHALLENGE_TASKS.is_passed`도 nullable이라 미시도 상태와 채점 후 결과를 구분할 수 있다.
7. `CAT_MEMORIES.created_at`을 통해 여러 기억의 생성 순서를 판단할 수 있다.
8. 문제 원본, 사용자 상태, 행동 이력을 서로 분리해 같은 데이터를 여러 기능에서 재사용할 수 있다.

---

> **정리:** 현재 ERD의 핵심은 `USERS`를 중심으로 학습 기록, 실시간 배틀, 랭킹, 하우징, 고양이 기능을 연결하면서도 **원본 데이터와 사용자별 상태, 실제 행동 이력은 별도 테이블로 분리**한 것이다. 특히 현재 최종 버전에서는 `TASK_ATTEMPTS`에 풀이 맥락이 추가되어 비동기 채점 완료 후 어느 게임 모드의 상태를 갱신해야 하는지 식별할 수 있게 되었다.
