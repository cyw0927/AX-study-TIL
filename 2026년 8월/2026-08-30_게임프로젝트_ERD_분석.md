# 게임 프로젝트 ERD 분석 백업

> **용도**: 팀 게임 프로젝트 ERD를 테이블별로 이해하고, Notion에 옮겨 정리하기 위한 백업 문서
>
> **기준**: 현재 ERD의 19개 테이블 구조를 그대로 읽되, 각 테이블의 역할·관계·제약조건·실제 사용 흐름까지 함께 분석한다.
>
> **주의**: 아래의 `수정/검토 포인트`는 현재 ERD에서 바로 수정해야 하는 확정 사항과, 팀에서 정책을 정한 뒤 반영해야 하는 제안 사항을 구분해서 적었다.

---

# 0. 전체 구조 한눈에 보기

현재 ERD는 크게 6개 섹터로 나눌 수 있다.

| 섹터 | 담당 기능 | 테이블 |
| --- | --- | --- |
| 사용자/출석 | 계정, 재화, 출석 상태 | `USERS`, `ATTENDANCES` |
| 학습/숙련도 | 문제 은행, 제출 기록, 개념별 숙련도 | `CONCEPTS`, `TASKS`, `TASK_ATTEMPTS`, `USER_PROFICIENCY` |
| 학습방/배틀 | 실시간 방, 참가자, 출제 문제 | `ROOMS`, `ROOM_PARTICIPANTS`, `ROOM_TASKS` |
| 랭킹/도전 | 소규모 랭킹, 랭크 도전 세션 | `RANKING_GROUPS`, `RANKING_PARTICIPANTS`, `RANK_CHALLENGES`, `RANK_CHALLENGE_TASKS` |
| 아이템/하우징 | 아이템 원본, 인벤토리, 배치 정보 | `ITEMS`, `INVENTORIES`, `PLACED_OBJECTS` |
| 고양이 | 고양이 종류, 유저 보유 고양이, 대화 기억 | `CATS`, `USER_CATS`, `CAT_MEMORIES` |

전체 서비스 흐름은 다음처럼 볼 수 있다.

```text
사용자 접속
   ↓
USERS ── ATTENDANCES
   ↓
문제 선택/추천
   ↓
CONCEPTS → TASKS → TASK_ATTEMPTS
     ↑                 ↓
     └──── USER_PROFICIENCY
                       ↓
                  학습 성과/보상
                       ↓
       ┌───────────────┴───────────────┐
       ↓                               ↓
  ITEMS / INVENTORIES             CATS / USER_CATS
       ↓                               ↓
 PLACED_OBJECTS                  CAT_MEMORIES
```

---

# 0-1. 모든 테이블에 `id`를 따로 두는 이유

각 테이블의 `id`는 **그 테이블 안의 한 행(row)을 고유하게 식별하는 기본키(PK)** 역할을 한다.

예를 들어 `USER_PROFICIENCY`는 `(user_id, concept_id)` 조합만으로도 한 행을 구분할 수 있지만, 별도의 `id`를 두면 다른 테이블에서 참조하기 쉽고 향후 관계가 추가될 때 구조가 단순해진다.

즉 이 ERD는 대부분의 테이블에서 **surrogate key(대리키)인 `id`를 PK로 사용하고, 실제 업무상 중복되면 안 되는 값은 `UNIQUE` 제약으로 막는 구조**로 이해하면 된다.

> `USERS.id = 1`, `TASKS.id = 1`처럼 서로 다른 테이블에서 같은 숫자/값이 존재해도 문제없다. 각 테이블의 PK는 서로 독립적이다.

# 1. 사용자 / 출석 섹터

## 섹터 관계도

```text
┌──────────────────────────────┐
│            USERS             │
│ 사용자 기본 정보 / 재화 / 집 │
└──────────────┬───────────────┘
               │ 1:N
               ↓
┌──────────────────────────────┐
│         ATTENDANCES          │
│ 날짜별 출석 / 연속 출석 / 미션 │
└──────────────────────────────┘
```

---

# 1-1. USERS

## 역할

플랫폼 내 사용자 데이터의 중심이 되는 테이블이다.

사용자의 닉네임과 권한뿐 아니라 현재 보유 재화, 마일리지, 하우스 레벨, 적용 중인 벽지와 바닥처럼 **사용자에게 직접 귀속되는 현재 상태값**을 저장한다.

쉽게 말하면 다음 질문에 답하는 테이블이다.

> **“이 사용자는 누구이고, 현재 게임에서 어떤 상태인가?”**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 사용자 고유 식별자, PK |
| `username` | string | 사용자 이름 또는 닉네임 |
| `role` | string | 학습자/교육 담당자/운영자 등 권한 |
| `soft_balance` | int | 일반 학습 재화 |
| `hard_balance` | int | 특수 재화 |
| `mileage` | int | 중복 뽑기 등에 대한 보상용 마일리지 |
| `house_level` | int | 사용자의 하우스 레벨 |
| `wallpaper_item_id` | int, FK | 현재 적용한 벽지 아이템 (`ITEMS.id`) |
| `floor_item_id` | int, FK | 현재 적용한 바닥 아이템 (`ITEMS.id`) |
| `created_at` | datetime | 계정 생성 시각 |

## 관계

`USERS`는 사실상 ERD의 중심 테이블이다.

한 사용자는 여러 개의 출석 기록, 문제 제출 기록, 숙련도 기록, 방 참가 기록, 랭킹 기록, 아이템, 고양이 등을 가질 수 있다.

```text
USERS
 ├─ ATTENDANCES
 ├─ TASK_ATTEMPTS
 ├─ USER_PROFICIENCY
 ├─ ROOM_PARTICIPANTS
 ├─ RANKING_PARTICIPANTS
 ├─ INVENTORIES
 ├─ PLACED_OBJECTS
 └─ USER_CATS
```

## 필요한 제약

```sql
CHECK (soft_balance >= 0)
CHECK (hard_balance >= 0)
CHECK (mileage >= 0)
```

재화가 음수가 되는 것은 일반적으로 정상적인 게임 상태가 아니므로 DB 수준에서도 막아두는 것이 안전하다.

## 실제 사용 예

| 컬럼 | 예시 값 |
| --- | --- |
| `id` | `user-001` |
| `username` | `cat_coder` |
| `role` | `USER` |
| `soft_balance` | `1250` |
| `hard_balance` | `30` |
| `mileage` | `450` |
| `house_level` | `3` |
| `wallpaper_item_id` | `21` |
| `floor_item_id` | `34` |
| `created_at` | `2026-08-01 14:30` |

## 설계 포인트

- 사용자 이름을 다른 모든 테이블에 반복 저장하지 않고 `user_id`로 연결한다.
- 현재 재화 잔액은 `USERS`에 두되, 향후 재화 지급/사용 이력까지 감사 로그로 남겨야 한다면 별도 거래 이력 테이블이 필요할 수 있다.
- `wallpaper_item_id`, `floor_item_id`는 위치 좌표가 필요 없는 하우징 배경이므로 `PLACED_OBJECTS`가 아니라 `USERS`에 직접 연결한 구조로 이해할 수 있다.

# 1-2. ATTENDANCES

## 역할

사용자의 날짜별 출석과 연속 출석 상태를 저장한다.

또한 `daily_quest_completed`를 함께 저장하여 **해당 날짜의 일일 미션 완료 상태를 판단하는 기준**으로 사용할 수 있다.

> **“오늘 출석했는가?” / “몇 일 연속 출석인가?” / “오늘 일일 미션을 완료했는가?”**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 출석 기록 한 건의 PK |
| `user_id` | uuid, FK | 출석한 사용자 (`USERS.id`) |
| `check_in_date` | date | 출석 날짜 |
| `streak_count` | int | 해당 날짜 기준 연속 출석 일수 |
| `daily_quest_completed` | boolean | 일일 미션 완료 여부 |

## 관계

```text
USERS 1 ───── N ATTENDANCES
```

한 사용자는 날짜마다 하나의 출석 기록을 가질 수 있다.

## 필요한 제약

```sql
UNIQUE (user_id, check_in_date)
```

같은 사용자가 같은 날짜에 출석 기록을 두 개 만드는 것을 막는다.

## 실제 사용 예

```text
user-001
 ├─ 2026-08-28 / streak 5
 ├─ 2026-08-29 / streak 6
 └─ 2026-08-30 / streak 7 / daily quest 완료
```

## 설계 포인트

`daily_quest_completed = true` 자체만으로 동시 요청에 의한 중복 보상이 100% 방지되는 것은 아니다. 보상 지급 로직에서는 **트랜잭션 또는 원자적 업데이트**가 함께 필요하다.

# 2-1. CONCEPTS

## 역할

Python 학습 내용을 개념 단위로 분류하는 기준 테이블이다.

예를 들면 다음과 같은 학습 단원을 관리할 수 있다.

```text
변수
조건문
반복문
리스트
딕셔너리
함수
문자열
```

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int | 개념 고유번호, PK |
| `name` | string | 개념 이름 |

## 관계

`CONCEPTS`는 두 가지 중요한 역할을 한다.

1. `TASKS.concept_id`를 통해 문제를 특정 개념으로 분류한다.
2. `USER_PROFICIENCY.concept_id`를 통해 사용자의 개념별 숙련도를 관리한다.

## 왜 별도 테이블인가?

`TASKS`에 `"반복문"`, `"for문"`, `"Loop"` 같은 문자열을 직접 반복 저장하면 같은 개념이 여러 이름으로 분산될 수 있다.

`CONCEPTS`를 기준표로 두면 문제 추천과 숙련도 계산이 같은 개념 ID를 사용하게 된다.

## 수정/검토 포인트

현재 `TASKS`에는 `concept_id`가 하나만 있으므로 **한 문제를 하나의 대표 개념에만 연결할 수 있다.**

실제 코딩 문제는 반복문 + 조건문 + 리스트처럼 여러 개념을 함께 사용할 수 있다.

정석적으로는 다음 구조가 더 유연하다.

```text
TASKS N ── TASK_CONCEPTS ── N CONCEPTS
```

다만 현재 19개 테이블 구조를 유지해야 한다면 MVP에서는 다음과 같이 비즈니스 룰을 정할 수 있다.

> 한 문제에는 가장 핵심적인 대표 개념 하나만 지정한다.

# 2-2. TASKS

## 역할

사용자가 실제로 풀게 되는 문제의 원본 정보를 저장하는 **문제 은행**이다.

`TASKS`는 “누가 풀었는가”를 저장하지 않는다. 오직 **문제 자체**를 정의한다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 문제 고유 ID |
| `concept_id` | int, FK | 문제의 대표 개념 (`CONCEPTS.id`) |
| `type` | string | 문제 유형 |
| `difficulty` | string | 난이도 |
| `template_code` | text | 사용자에게 제공할 기본 코드 골격 |
| `test_cases` | text | 자동 채점용 테스트 데이터 |
| `is_active` | boolean | 현재 출제 가능한 문제인지 여부 |

## 예시 문제 유형

```text
CODE
MULTIPLE_CHOICE
TRUE_FALSE
OUTPUT_PREDICTION
ERROR_FINDING
```

## 관계

```text
TASKS
 ├─ TASK_ATTEMPTS
 ├─ ROOM_TASKS
 └─ RANK_CHALLENGE_TASKS
```

하나의 문제 은행을 개인 학습, 배틀방, 랭크 도전에서 재사용한다.

## `is_active`가 필요한 이유

문제에 오류가 생겼다고 DB에서 행 자체를 삭제하면 기존 `TASK_ATTEMPTS`와의 연결이 깨질 수 있다.

따라서 실제 삭제 대신 다음처럼 **소프트 딜리트에 가까운 방식**으로 관리할 수 있다.

```text
is_active = true  → 출제 가능
is_active = false → 신규 출제 중단, 과거 기록은 유지
```

## `template_code`의 역할

문제의 함수 이름, 매개변수, 기본 코드 구조를 통일하여 사용자가 수정해야 할 범위를 명확하게 만든다.

> `template_code`는 채점 형식을 통일하기 위한 데이터이지, 악성 코드 실행을 막는 보안 장치 자체는 아니다.

악성 코드 방어는 별도의 Docker/샌드박스에서 CPU, 메모리, 시간, 네트워크, 파일 접근 등을 제한해야 한다.

## 수정/검토 포인트

- `test_cases`가 단순 `text`라면 내부 포맷(JSON 등)을 명확하게 정해야 한다.
- 문제 설명/제목/힌트 등이 필요하다면 현재 ERD에는 해당 컬럼이 없으므로 향후 추가 여부 검토가 필요하다.

# 2-3. TASK_ATTEMPTS

## 역할

사용자가 문제를 실제로 제출한 기록을 저장하는 **학습 이력/채점 로그 테이블**이다.

> **“누가 어떤 문제를, 어떤 코드로, 언제 제출했고, 결과는 어땠는가?”**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 제출 시도 한 건의 PK |
| `user_id` | uuid, FK | 문제를 푼 사용자 |
| `task_id` | uuid, FK | 어떤 문제를 풀었는지 |
| `submitted_code` | text | 실제 제출 코드 |
| `status` | string | 채점 처리 상태 |
| `is_correct` | boolean | 정답 여부 |
| `used_hint` | boolean | 힌트 사용 여부 |
| `attempted_at` | datetime | 제출 시각 |

## 왜 한 문제에 여러 행이 필요한가?

오답 재시도를 허용하기 때문이다.

```text
user-001 / task-020
 ├─ 1차 제출 → 오답 / 힌트 X
 ├─ 2차 제출 → 오답 / 힌트 O
 └─ 3차 제출 → 정답 / 힌트 O
```

세 번의 제출은 각각 별도의 `TASK_ATTEMPTS` 행으로 남는다.

## 활용

- 최초 정답까지 몇 번 시도했는지
- 특정 개념에서 오답이 반복되는지
- 힌트 사용 비율
- 최근 학습 성과
- 정답 이력을 이용한 최초 완료 보상 판단

## 중요한 구분

`TASK_ATTEMPTS`는 **과거에 실제로 일어난 행동 기록**이다.

반면 `USER_PROFICIENCY`는 여러 시도 기록을 종합해 계산한 **현재 상태값**이다.

## 수정/검토 포인트

현재 ERD에는 `feedback`, `error_message`, `execution_result` 같은 컬럼이 없다.

따라서 현 구조만 기준으로 문서화할 때는 “에러 피드백을 저장한다”고 표현하면 안 된다. 실제 피드백 저장이 필요하면 컬럼 추가를 검토해야 한다.

또한 최초 정답 여부를 조회해 중복 보상을 막을 수 있지만, 동시에 여러 요청이 들어올 수 있으므로 보상 지급은 트랜잭션 단위로 처리하는 것이 안전하다.

# 2-4. USER_PROFICIENCY

## 역할

사용자의 Python **개념별 현재 숙련도**를 저장한다.

총점 하나로 실력을 관리하는 대신 다음처럼 개념별 상태를 나눌 수 있다.

```text
변수     5
조건문   4
반복문   2
함수     1
```

이 값은 개인화된 문제 추천의 핵심 기준으로 사용할 수 있다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 숙련도 기록 PK |
| `user_id` | uuid, FK | 어떤 사용자인지 |
| `concept_id` | int, FK | 어떤 개념인지 |
| `proficiency_level` | int | 현재 숙련도 |

## 필요한 제약

```sql
UNIQUE (user_id, concept_id)
```

한 사용자의 동일 개념 숙련도 행이 두 개 생기면 현재 숙련도가 어느 쪽인지 판단할 수 없기 때문이다.

## 실제 사용 흐름

```text
TASK_ATTEMPTS 분석
      ↓
반복문 오답 비율 높음
      ↓
USER_PROFICIENCY 반복문 숙련도 낮게 반영
      ↓
다음 문제 추천 시 반복문 기초 문제 우선 추천
```

## 정책 결정 필요

- 숙련도는 몇 점 만점인가?
- 정답 시 몇 점 증가하는가?
- 오답 시 감소하는가?
- 힌트 사용 시 가중치를 다르게 줄 것인가?
- 오래된 기록의 가중치를 낮출 것인가?

이 로직은 ERD가 아니라 별도의 **추천/숙련도 계산 정책**으로 정의해야 한다.

# 3. 학습방 / 배틀 섹터

## 섹터 관계도

```text
                    ┌──────────────┐
                    │    USERS     │
                    └──────┬───────┘
                           │
                           ↓
┌──────────────┐   ┌─────────────────────┐
│    ROOMS     │──→│  ROOM_PARTICIPANTS  │
│   방 자체    │   │ 참가자/팀/점수/준비 │
└──────┬───────┘   └─────────────────────┘
       │
       ↓
┌──────────────────┐        ┌──────────────┐
│    ROOM_TASKS    │───────→│    TASKS     │
│ 방별 출제 문제표 │        │   문제 은행   │
└──────────────────┘        └──────────────┘
```

---

# 3-1. ROOMS

## 역할

실시간 학습 배틀/멀티플레이 세션 자체를 저장한다.

> **“어떤 방이 존재하고, 누가 방장이며, 지금 대기/진행/종료 중인가?”**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 방 ID |
| `title` | string | 로비에 표시할 방 이름 |
| `host_user_id` | uuid, FK | 방장 (`USERS.id`) |
| `status` | string | `WAITING`, `IN_PROGRESS`, `FINISHED` |
| `max_participants` | int | 최대 참가 인원 |

## 현재 참가자 수를 따로 저장하지 않은 이유

현재 참가자 수는 `ROOM_PARTICIPANTS`에서 해당 `room_id`의 행 개수를 세면 계산할 수 있다.

별도로 `current_participants` 값을 `ROOMS`에 저장하면 입퇴장 시 두 데이터가 어긋날 위험이 생긴다.

## 동시성 주의

여러 사용자가 동시에 마지막 자리에 들어오려고 하면 최대 인원을 초과할 수 있다.

따라서 서버에서는 **DB Lock, 조건부 원자 업데이트, Redis 등 적절한 동시성 제어 방식**이 필요하다.

---

# 3-2. ROOM_PARTICIPANTS

## 역할

어떤 사용자가 어떤 방에 참가 중인지와, 방 안에서의 팀/점수/준비 상태를 저장한다.

`ROOMS`와 `USERS` 사이의 다대다 관계를 연결하는 중간 테이블이다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 방 참가 기록 PK |
| `room_id` | uuid, FK | 참가한 방 |
| `user_id` | uuid, FK | 참가 사용자 |
| `team_name` | string | 팀전일 때 팀 이름, 개인전이면 `NULL` |
| `current_score` | int | 게임 진행 중 현재 점수 |
| `is_ready` | boolean | 시작 준비 완료 여부 |

## 필요한 제약

```sql
UNIQUE (room_id, user_id)
```

같은 사용자가 같은 방에 참가자로 두 번 등록되는 것을 막는다.

## 개인전 / 팀전

```text
team_name = NULL → 개인전
team_name = RED  → RED 팀
team_name = BLUE → BLUE 팀
```

별도의 TEAM 테이블을 만들지 않고 현재 구조 안에서 간단하게 팀을 표현한 설계다.

---

# 3-3. ROOM_TASKS

## 역할

한 방에서 어떤 문제를 어떤 순서로 출제할지 고정한다.

`ROOMS`와 `TASKS`의 다대다 관계를 연결하는 테이블이다.

## 주요 컬럼

| 컬럼 | 현재 ERD 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 방-문제 연결 PK |
| `room_id` | uuid, FK | 어느 방의 문제인지 |
| `task_id` | uuid, FK | 실제 출제 문제 |
| `task_order` | **현재 ERD: uuid** | 문제 출제 순서 |

## 필요한 제약

```sql
UNIQUE (room_id, task_order)
```

같은 방에서 1번 문제 두 개, 2번 문제 두 개가 생기는 것을 막는다.

## 확정 수정 후보

`task_order`는 순서값이므로 `uuid`보다 `int`가 자연스럽다.

```text
현재: uuid ❌
권장: int  ✅
```

예:

```text
1 → task-031
2 → task-052
3 → task-074
```

`RANK_CHALLENGE_TASKS.task_order`가 이미 `int`이므로 타입을 맞추는 것이 일관성 측면에서도 좋다.

# 4. 랭킹 / 도전 섹터

## 섹터 관계도

```text
┌──────────────────┐
│  RANKING_GROUPS  │
│ 소규모 랭킹 그룹 │
└────────┬─────────┘
         │
         ├──────────────────────┐
         ↓                      ↓
┌──────────────────────┐  ┌───────────────────┐
│ RANKING_PARTICIPANTS │  │  RANK_CHALLENGES  │
│ 그룹별 유저/현재점수 │  │ 한 번의 랭크 도전 │
└──────────────────────┘  └─────────┬─────────┘
                                     ↓
                          ┌─────────────────────────┐
                          │ RANK_CHALLENGE_TASKS    │
                          │ 도전 내 문제 진행 상태 │
                          └────────────┬────────────┘
                                       ↓
                                    TASKS
```

---

# 4-1. RANKING_GROUPS

## 역할

글로벌 랭킹 하나가 아니라, 원하는 소규모 그룹 안에서 경쟁할 수 있도록 **랭킹 보드의 단위**를 정의한다.

예:

```text
1분반
2분반
친구 랭킹
8월 반복문 챌린지
```

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 랭킹 그룹 PK |
| `name` | string | 그룹 이름 |
| `owner_user_id` | uuid, FK | 그룹 생성자/소유자 |

## 검토 포인트

`owner_user_id`에게 어떤 권한이 있는지 정책 정의가 필요하다.

- 멤버 초대/추방 가능?
- 그룹명 변경 가능?
- 랭크 시즌 초기화 가능?

---

# 4-2. RANKING_PARTICIPANTS

## 역할

특정 랭킹 그룹에 어떤 사용자가 참가하고 있고, 현재 랭킹 점수를 얼마나 가지고 있는지 저장한다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 참가 기록 PK |
| `group_id` | uuid, FK | 소속 랭킹 그룹 |
| `user_id` | uuid, FK | 참가 사용자 |
| `current_rank_score` | int | 해당 그룹에서의 현재 랭킹 점수 |

## 필요한 제약

```sql
UNIQUE (group_id, user_id)
```

같은 사용자가 같은 그룹 안에서 참가 기록을 두 개 가지지 않도록 한다.

## USERS에 점수를 두지 않은 이유

한 사용자가 여러 랭킹 그룹에 참가할 수 있기 때문이다.

```text
user-001
 ├─ 1분반 랭킹: 1520
 ├─ 친구 랭킹: 800
 └─ 특별 그룹: 430
```

---

# 4-3. RANK_CHALLENGES

## 역할

사용자가 랭킹 점수를 얻기 위해 시작한 **한 번의 랭크 도전 전체 세션**을 저장한다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 도전 세션 PK |
| `user_id` | uuid, FK | 도전 사용자 |
| `group_id` | uuid, FK | 대상 랭킹 그룹 |
| `status` | string | `IN_PROGRESS`, `SUCCESS`, `FAILED`, `TIMEOUT` |
| `started_at` | datetime | 시작 시각 |
| `expires_at` | datetime | 도전 만료 시각 |

## `expires_at`이 중요한 이유

클라이언트가 단순히 “10분 남음”만 들고 있으면 새로고침이나 재접속 시 시간 기준이 꼬일 수 있다.

서버에 절대 시각을 저장하면 다음처럼 판단할 수 있다.

```text
expires_at = 15:30
현재 15:27 → 3분 남음
현재 15:32 → TIMEOUT
```

---

# 4-4. RANK_CHALLENGE_TASKS

## 역할

한 번의 랭크 도전에 포함된 각 문제의 진행 상태를 저장한다.

`RANK_CHALLENGES`가 시험지 전체라면, 이 테이블은 그 시험지 안의 각 문제 상태에 해당한다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 도전 문제 기록 PK |
| `rank_challenge_id` | uuid, FK | 어떤 랭크 도전에 포함되는지 |
| `task_id` | uuid, FK | 실제 문제 |
| `is_passed` | boolean | 해당 문제 통과 여부 |
| `saved_code` | text | 문제 이동/이어하기를 위한 임시 코드 |
| `task_order` | int | 도전 내 문제 순서 |

## 필요한 제약

```sql
UNIQUE (rank_challenge_id, task_order)
```

## `saved_code`와 `TASK_ATTEMPTS.submitted_code`의 차이

- `saved_code`: 아직 제출하지 않은 **작성 중 상태**도 저장할 수 있음
- `submitted_code`: 사용자가 실제로 **채점 요청을 한 코드**

즉 임시 저장과 제출 이력을 분리한 구조다.

## 명칭 통일

현재 ERD의 FK 컬럼명은 `rank_challenge_id`이다.

문서나 코드에서도 `challenge_id` 등으로 축약하지 말고 가능하면 동일하게 맞추는 편이 좋다.

# 5. 아이템 / 하우징 섹터

## 섹터 관계도

```text
                   ┌──────────────┐
                   │    ITEMS     │
                   │ 아이템 원본  │
                   └──────┬───────┘
                          │
               ┌──────────┴──────────┐
               ↓                     ↓
┌─────────────────────┐   ┌─────────────────────┐
│     INVENTORIES     │   │   PLACED_OBJECTS    │
│ 유저별 아이템 보유량 │   │ 실제 하우스 배치값 │
└──────────┬──────────┘   └──────────┬──────────┘
           │                         │
           └──────────── USERS ──────┘
```

---

# 5-1. ITEMS

## 역할

게임에 존재하는 가구, 벽지, 바닥 등 **아이템 종류 자체의 원본 정보**를 저장한다.

`ITEMS`는 사용자가 가지고 있는 물건이 아니라 **게임 세계에 존재하는 상품/오브젝트의 마스터 데이터**다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int | 아이템 종류 PK |
| `category` | string | `WALLPAPER`, `FLOOR`, `FURNITURE` 등 |
| `name` | string | 표시 이름 |
| `price` | int | 가격 |

## 실제 예

```text
ITEM 21
category = WALLPAPER
name = 파란 별 벽지
price = 500
```

## 검토 포인트

상점에서 여러 재화를 사용할 경우 `price`만으로는 어떤 재화 가격인지 알 수 없다.

예:

```text
파란 소파   → soft 500
특별 벽지   → hard 10
```

이 정책을 사용한다면 다음 컬럼이 필요할 수 있다.

```text
currency_type
```

단, 마일리지가 중복 보상 전용이고 실제 상점 결제에는 사용되지 않는다면 반드시 3종류 재화 모두를 지원할 필요는 없다.

---

# 5-2. INVENTORIES

## 역할

어떤 사용자가 어떤 아이템을 몇 개 가지고 있는지 저장한다.

> **ITEMS = 아이템 종류**
>
> **INVENTORIES = 사용자의 실제 보유량**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 인벤토리 행 PK |
| `user_id` | uuid, FK | 아이템 소유 사용자 |
| `item_id` | int, FK | 어떤 아이템인지 |
| `quantity` | int | 보유 수량 |

## 필요한 제약

```sql
UNIQUE (user_id, item_id)
CHECK (quantity >= 0)
```

같은 아이템의 보유 행을 여러 개 만들기보다 하나의 행에서 수량으로 관리한다.

## 트랜잭션 주의

아이템 구매는 일반적으로 다음 두 작업이 함께 성공하거나 함께 실패해야 한다.

```text
1. USERS.soft_balance 차감
2. INVENTORIES.quantity 증가
```

따라서 하나의 DB 트랜잭션으로 묶는 것이 안전하다.

---

# 5-3. PLACED_OBJECTS

## 역할

사용자가 소유한 아이템 중 실제로 하우스에 배치된 오브젝트의 위치와 방향을 저장한다.

> **INVENTORIES = 가지고 있다**
>
> **PLACED_OBJECTS = 실제 방에 놓았다**

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 배치 오브젝트 PK |
| `user_id` | uuid, FK | 누구의 하우스인지 |
| `item_id` | int, FK | 어떤 아이템인지 |
| `position_data` | jsonb | 위치, 회전 등 배치 정보 |

## JSONB 예시

```json
{
  "x": 3,
  "y": 5,
  "rotation": 90
}
```

향후 다음처럼 확장할 수도 있다.

```json
{
  "x": 3,
  "y": 5,
  "rotation": 90,
  "layer": 2,
  "flipped": false
}
```

## JSONB를 쓴 이유

하우징 좌표 시스템이 바뀌거나 필드가 추가되어도 테이블 컬럼을 계속 늘리지 않고 유연하게 확장할 수 있다.

벽지와 바닥은 좌표가 필요 없으므로 `USERS.wallpaper_item_id`, `USERS.floor_item_id`로 처리하고 이 테이블에는 넣지 않은 구조다.

# 6. 고양이 섹터

## 섹터 관계도

```text
┌──────────────┐      ┌──────────────┐
│    USERS     │      │     CATS     │
│ 사용자/주인 │      │ 고양이 종류  │
└──────┬───────┘      └──────┬───────┘
       │                      │
       └──────────┬───────────┘
                  ↓
         ┌─────────────────┐
         │    USER_CATS    │
         │ 유저의 실제 고양이 │
         └────────┬────────┘
                  ↓
         ┌─────────────────┐
         │  CAT_MEMORIES   │
         │ 개별 고양이 기억 │
         └─────────────────┘
```

---

# 6-1. CATS

## 역할

뽑기에서 획득할 수 있는 **고양이 종류의 원본 정보**를 저장한다.

`ITEMS`와 마찬가지로 마스터 데이터 성격이다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | int | 고양이 종류 PK |
| `name` | string | 고양이 이름/종류명 |
| `persona` | string | 성격과 대화 스타일 |
| `rarity` | string | 희귀도 |

## 예

```text
cat_id = 4
name = 검은 고양이
persona = 차분하고 따뜻한 성격
rarity = SSR
```

## 중요한 점

`CATS.id = 4`는 특정 사용자가 보유한 한 마리를 의미하지 않는다.

그저 “검은 고양이라는 종류가 존재한다”는 정의다.

실제 사용자 소유 개체는 `USER_CATS`에서 생성된다.

---

# 6-2. USER_CATS

## 역할

특정 사용자가 실제로 획득한 고양이를 저장한다.

`USERS`와 `CATS`의 연결 테이블이며, 이후 개별 고양이 기억의 기준점 역할도 한다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 사용자가 보유한 고양이 개체/보유 기록 PK |
| `user_id` | uuid, FK | 고양이 주인 |
| `cat_id` | int, FK | 어떤 종류의 고양이인지 |

## 중복 뽑기 정책이 “마일리지 전환”일 경우 필요한 제약

```sql
UNIQUE (user_id, cat_id)
```

같은 사용자가 같은 종류의 고양이를 두 마리 이상 보유하지 못하게 한다.

중복 획득은 행 추가 대신 `USERS.mileage` 증가로 처리한다.

## 왜 `USER_CATS.id`가 중요한가?

두 사용자가 같은 `CATS.id`의 고양이를 가지고 있어도 각각의 관계와 기억은 달라야 한다.

```text
민지의 검은 고양이 → USER_CATS A
철수의 검은 고양이 → USER_CATS B
```

따라서 대화 기억은 `cat_id`가 아니라 `user_cat_id`에 연결된다.

## 검토 포인트

향후 개별 고양이에 아래 요소가 필요해지면 `USER_CATS`에 컬럼 추가를 검토할 수 있다.

- 유저가 정한 별명
- 레벨
- 호감도
- 획득일
- 현재 행동/상태

현재 ERD에는 존재하지 않는 정보이므로 MVP 범위에 따라 결정한다.

# 6-3. CAT_MEMORIES

## 역할

특정 사용자가 보유한 특정 고양이와의 대화나 관계에서 기억해둘 내용을 요약해 저장한다.

고양이 대화의 연속성을 만들기 위한 테이블이다.

## 주요 컬럼

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `id` | uuid | 기억 한 건의 PK |
| `user_cat_id` | uuid, FK | 누구의 어떤 고양이 기억인지 (`USER_CATS.id`) |
| `context_summary` | text | 다음 대화에서 활용할 기억 요약 |

## 예시

```text
사용자는 반복문 학습을 어려워했지만 끝까지 완료했고,
새 파란 소파를 구매해 하우스에 배치했다.
```

이후 고양이 대화에서 다음처럼 연속성을 만들 수 있다.

```text
“전에 반복문 끝까지 풀었던 거 기억나!
새 소파도 잘 어울리더라.”
```

## 수정/검토 포인트

현재 구조에는 기억 생성 시각이 없다.

기억이 여러 개 쌓이면 어떤 기억이 최신인지 판단하기 어렵기 때문에 다음 컬럼 추가를 검토할 가치가 높다.

```text
created_at datetime
```

특히 “최근 기억 몇 개만 불러오기” 같은 기능을 구현하려면 시간 정보가 매우 유용하다.

# 8. 현재 ERD에서 바로 확인할 수정/검토 포인트

## A. 수정 우선순위 높음

### 1) `ROOM_TASKS.task_order` 타입

현재 ERD의 `uuid`는 순서값과 맞지 않는다.

```text
uuid → int 권장
```

### 2) `RANK_CHALLENGE_TASKS` FK 명칭 통일

ERD 기준 컬럼명은 `rank_challenge_id`이다.

문서/코드/DTO에서도 동일한 명칭을 사용하는 것이 좋다.

### 3) `CAT_MEMORIES.created_at` 검토

여러 기억의 시간 순서를 판단하려면 생성 시각이 유용하다.

---

## B. 팀 정책 결정 후 반영

### 4) 한 문제에 여러 개념 연결 여부

현재는 `TASKS.concept_id` 하나만 존재한다.

- MVP: 대표 개념 1개만 지정
- 확장: `TASK_CONCEPTS` 중간 테이블 추가

### 5) TASK 실행 결과/피드백 저장 여부

현재 `TASK_ATTEMPTS`에는 제출 코드와 정답 여부는 있지만 `feedback`, `error_message`는 없다.

- UI에서 즉시 보여주고 버린다 → 현 구조 가능
- 나중에도 기록을 열람한다 → 컬럼/별도 로그 필요

### 6) 아이템 결제 재화 종류

여러 재화를 상점 가격으로 사용한다면 `ITEMS.currency_type` 같은 정보가 필요하다.

### 7) USER_CATS 개체 성장 요소

별명, 레벨, 호감도 등을 실제 기능으로 넣는다면 `USER_CATS` 확장이 필요하다.

# 9. 추천 UNIQUE / CHECK 제약 정리

```sql
-- USERS
CHECK (soft_balance >= 0)
CHECK (hard_balance >= 0)
CHECK (mileage >= 0)

-- ATTENDANCES
UNIQUE (user_id, check_in_date)

-- USER_PROFICIENCY
UNIQUE (user_id, concept_id)

-- ROOM_PARTICIPANTS
UNIQUE (room_id, user_id)

-- ROOM_TASKS
UNIQUE (room_id, task_order)

-- RANKING_PARTICIPANTS
UNIQUE (group_id, user_id)

-- RANK_CHALLENGE_TASKS
UNIQUE (rank_challenge_id, task_order)

-- INVENTORIES
UNIQUE (user_id, item_id)
CHECK (quantity >= 0)

-- USER_CATS
-- 중복 고양이를 마일리지로 전환하는 정책일 때 적용
UNIQUE (user_id, cat_id)
```

# 10. 가장 헷갈리기 쉬운 테이블 쌍

## `TASKS` vs `TASK_ATTEMPTS`

```text
TASKS         = 문제 자체
TASK_ATTEMPTS = 사용자가 실제로 문제를 푼 기록
```

## `TASK_ATTEMPTS` vs `USER_PROFICIENCY`

```text
TASK_ATTEMPTS     = 과거 행동 기록
USER_PROFICIENCY  = 행동 기록을 종합한 현재 실력 상태
```

## `ITEMS` vs `INVENTORIES` vs `PLACED_OBJECTS`

```text
ITEMS          = 게임에 어떤 아이템 종류가 존재하는가
INVENTORIES    = 사용자가 몇 개 가지고 있는가
PLACED_OBJECTS = 그중 무엇을 실제 집 어디에 놓았는가
```

## `CATS` vs `USER_CATS` vs `CAT_MEMORIES`

```text
CATS         = 고양이 종류의 원본
USER_CATS    = 특정 사용자가 실제 보유한 고양이
CAT_MEMORIES = 그 개별 고양이에게 쌓이는 기억
```

## `ROOMS` vs `ROOM_PARTICIPANTS` vs `ROOM_TASKS`

```text
ROOMS             = 방 자체
ROOM_PARTICIPANTS = 그 방에 들어온 사람
ROOM_TASKS        = 그 방에서 풀 문제
```

## `RANKING_PARTICIPANTS` vs `RANK_CHALLENGES`

```text
RANKING_PARTICIPANTS = 그룹에서 유지되는 현재 랭킹 상태
RANK_CHALLENGES      = 사용자가 실제로 수행한 한 번의 도전 세션
```

# 11. 최종 정리

이 ERD는 단순한 학습 서비스 DB가 아니라 다음 세 영역을 하나로 연결하는 구조다.

```text
학습 데이터
CONCEPTS → TASKS → TASK_ATTEMPTS → USER_PROFICIENCY

게임 보상/꾸미기
USERS → ITEMS → INVENTORIES → PLACED_OBJECTS

수집/관계 형성
USERS → USER_CATS ← CATS
              ↓
        CAT_MEMORIES
```

여기에 `ROOMS` 계열이 실시간 학습 경쟁을, `RANKING_*` 계열이 지속적인 소규모 경쟁 구조를 담당한다.

따라서 핵심 흐름을 한 문장으로 줄이면 다음과 같다.

> **사용자가 문제를 풀고 → 그 기록이 숙련도와 보상으로 이어지고 → 보상으로 고양이와 아이템을 모으며 → 방/랭킹에서 다른 사용자와 학습 경쟁을 하고 → 자신의 고양이와 하우스를 발전시키는 구조**

현재 19개 테이블만으로도 MVP 핵심 기능은 상당 부분 표현할 수 있다. 다만 구현 단계에 들어가기 전에 `ROOM_TASKS.task_order`, 다중 개념 문제 처리, 고양이 기억 시간 정보, 채점 결과 저장 범위 등의 정책은 팀에서 한 번 더 확정하는 것이 좋다.
