# 게임 프로젝트 ERD 분석

> 게임 프로젝트 ERD에 있는 19개 테이블을 보고, 각 테이블이 무슨 일을 하는지 초보자 입장에서 이해하기 쉽게 정리했다.
>
> 어려운 DB 용어를 많이 쓰기보다는 **“이 테이블이 왜 필요한지”, “각 컬럼이 뭘 뜻하는지”, “어디와 연결되는지”** 위주로 정리했다.

---

# 0. 먼저 알아둘 것

## PK와 FK가 뭔가?

- **PK(Primary Key)**: 그 테이블 안에서 한 줄의 데이터를 구분하는 고유번호
- **FK(Foreign Key)**: 다른 테이블의 데이터를 가리키는 값

예를 들어 `TASK_ATTEMPTS.user_id`가 `USERS.id`를 가리키면,

> “이 문제를 푼 사람이 누구인지”

알 수 있다.

각 테이블에 `id`가 따로 있는 이유도 비슷하다. 문제 1개, 출석 기록 1개, 고양이 보유 기록 1개처럼 **각 데이터 한 건을 구분하기 위해서**이다.

---

# 0-1. 전체 테이블을 크게 나누면

```text
[사용자 / 출석]
USERS ── ATTENDANCES

[학습]
CONCEPTS ── TASKS ── TASK_ATTEMPTS
     └──── USER_PROFICIENCY

[배틀방]
ROOMS ── ROOM_PARTICIPANTS
   └─── ROOM_TASKS ── TASKS

[랭킹]
RANKING_GROUPS ── RANKING_PARTICIPANTS
       └──────── RANK_CHALLENGES ── RANK_CHALLENGE_TASKS

[아이템 / 하우징]
ITEMS ── INVENTORIES
   └─── PLACED_OBJECTS

[고양이]
CATS ── USER_CATS ── CAT_MEMORIES
```

아래부터는 ERD에 있는 테이블 순서대로 하나씩 본다.

---

# 1. USERS

게임을 사용하는 **유저의 기본 정보와 현재 상태**를 저장하는 가장 중심이 되는 테이블이다.

쉽게 말하면,

> “이 유저가 누구고, 지금 돈이 얼마나 있고, 집 상태는 어떤가?”

를 저장한다고 보면 된다.

## PK

- `id` : 유저 한 명을 구분하는 고유 ID

## FK

- `wallpaper_item_id` : 현재 사용 중인 벽지 아이템의 ID
- `floor_item_id` : 현재 사용 중인 바닥 아이템의 ID

둘 다 `ITEMS` 테이블의 아이템을 가리킨다.

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `username` | 유저 이름 또는 닉네임 |
| `role` | 유저 역할 |
| `soft_balance` | 일반 재화, 주로 학습으로 얻는 돈 |
| `hard_balance` | 특수 재화, 배틀/승급/미션 등에 사용할 수 있는 돈 |
| `mileage` | 중복 뽑기 보상 등에 쓰는 마일리지 |
| `house_level` | 유저의 집 레벨 |
| `created_at` | 계정이 만들어진 시간 |

## 예시

```text
username = cat_coder
soft_balance = 1250
hard_balance = 30
mileage = 450
house_level = 3
```

이런 식으로 유저의 현재 게임 상태를 한 곳에서 확인할 수 있다.

## 연결되는 테이블

`USERS`는 거의 모든 기능의 시작점이다.

- `ATTENDANCES` : 출석
- `TASK_ATTEMPTS` : 문제 풀이
- `USER_PROFICIENCY` : 개념별 숙련도
- `ROOM_PARTICIPANTS` : 배틀방 참가
- `RANKING_PARTICIPANTS` : 랭킹 참가
- `RANK_CHALLENGES` : 랭킹 도전
- `INVENTORIES` : 보유 아이템
- `PLACED_OBJECTS` : 배치한 가구
- `USER_CATS` : 보유 고양이

---

# 2. ATTENDANCES

유저의 **출석 기록**을 저장하는 테이블이다.

게임에 매일 접속했는지, 며칠 연속으로 접속했는지, 그날의 일일 미션을 끝냈는지를 기록한다.

## PK

- `id` : 출석 기록 한 건의 고유 ID

## FK

- `user_id` : 누구의 출석 기록인지 나타냄 → `USERS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `check_in_date` | 출석한 날짜 |
| `streak_count` | 연속 출석 일수 |
| `daily_quest_completed` | 그날 일일 미션을 완료했는지 여부 |

## 예시

```text
2026-08-28 / 연속 5일
2026-08-29 / 연속 6일
2026-08-30 / 연속 7일 / 일일미션 완료
```

즉 한 유저에게 날짜별로 여러 개의 출석 기록이 쌓이게 된다.

---

# 3. CONCEPTS

Python 문제를 **어떤 학습 개념에 속하는지 나누기 위한 기준표**이다.

예를 들면 다음과 같다.

```text
변수
조건문
반복문
리스트
함수
딕셔너리
```

## PK

- `id` : 학습 개념 하나를 구분하는 번호

## 그 외 컬럼

- `name` : 개념 이름

## 왜 필요한가?

`TASKS`와 `USER_PROFICIENCY`가 둘 다 같은 `CONCEPTS`를 바라본다.

그래서,

> “이 문제는 반복문 문제다.”

와

> “이 유저의 반복문 숙련도는 3이다.”

를 같은 기준으로 연결할 수 있다.

---

# 4. TASKS

유저가 실제로 풀게 되는 **문제 원본을 저장하는 문제 은행**이다.

`TASKS`에는 유저의 답이 들어가는 것이 아니라 **문제 자체의 정보**가 들어간다.

## PK

- `id` : 문제 하나의 고유 ID

## FK

- `concept_id` : 이 문제가 어떤 개념 문제인지 나타냄 → `CONCEPTS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `type` | 문제 종류 |
| `difficulty` | 문제 난이도 |
| `template_code` | 문제를 풀 때 처음 보여줄 기본 코드 |
| `test_cases` | 제출한 코드가 맞는지 확인할 테스트 데이터 |
| `is_active` | 현재 이 문제를 사용할 수 있는지 여부 |

## 예시

```text
concept_id = 반복문
 type = CODE
 difficulty = BASIC
 template_code = 기본 함수 코드
 test_cases = 정답 확인용 테스트
 is_active = true
```

## 어디에서 사용되나?

같은 `TASKS`의 문제를 여러 기능에서 같이 쓸 수 있다.

- 개인 문제 풀이 → `TASK_ATTEMPTS`
- 배틀방 문제 → `ROOM_TASKS`
- 랭킹 도전 문제 → `RANK_CHALLENGE_TASKS`

즉 문제를 모드마다 새로 만들지 않고 하나의 문제 은행을 같이 사용하는 구조이다.

---

# 5. USER_PROFICIENCY

유저가 **각 Python 개념을 얼마나 잘하는지** 저장하는 테이블이다.

전체 점수 하나만 저장하는 것이 아니라 개념별로 따로 저장한다.

예를 들면,

```text
변수 4
조건문 3
반복문 2
함수 1
```

처럼 볼 수 있다.

## PK

- `id` : 숙련도 기록 한 건의 고유 ID

## FK

- `user_id` : 누구의 숙련도인지 → `USERS.id`
- `concept_id` : 어떤 개념의 숙련도인지 → `CONCEPTS.id`

## 그 외 컬럼

- `proficiency_level` : 해당 개념의 현재 숙련도

## 왜 필요한가?

유저가 반복문을 잘 못한다면 반복문 문제를 더 추천하는 식으로 **개인 맞춤 문제 추천**에 사용할 수 있다.

`TASK_ATTEMPTS`가 실제 풀이 기록이라면 `USER_PROFICIENCY`는 그 결과를 보고 정리한 **현재 실력 상태**라고 보면 이해하기 쉽다.

---

# 6. TASK_ATTEMPTS

유저가 문제를 **실제로 풀고 제출한 기록**을 저장하는 테이블이다.

`TASKS`가 문제 원본이라면 `TASK_ATTEMPTS`는 유저의 풀이 기록이다.

## PK

- `id` : 문제 풀이 시도 한 번의 고유 ID

## FK

- `user_id` : 누가 풀었는지 → `USERS.id`
- `task_id` : 어떤 문제를 풀었는지 → `TASKS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `submitted_code` | 유저가 실제로 제출한 코드 |
| `status` | 현재 제출/채점 상태 |
| `is_correct` | 정답인지 아닌지 |
| `used_hint` | 힌트를 사용했는지 |
| `attempted_at` | 언제 문제를 제출했는지 |

## 예시

같은 유저가 같은 문제를 여러 번 풀 수도 있다.

```text
1차 시도 → 오답 / 힌트 사용 안 함
2차 시도 → 오답 / 힌트 사용
3차 시도 → 정답
```

이 경우 `TASK_ATTEMPTS`에는 기록이 3개 생긴다.

그래서 나중에 “몇 번 만에 맞혔는지”, “힌트를 썼는지”, “어떤 문제에서 자주 틀리는지” 등을 확인할 수 있다.

---

# 7. ROOMS

여러 명이 같이 문제를 풀 수 있는 **배틀방 자체의 정보**를 저장하는 테이블이다.

## PK

- `id` : 방 하나의 고유 ID

## FK

- `host_user_id` : 방을 만든 방장 → `USERS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `title` | 방 이름 |
| `status` | 방의 현재 상태 |
| `max_participants` | 최대 참가 인원 |

ERD에는 상태가 다음처럼 적혀 있다.

```text
WAITING
IN_PROGRESS
FINISHED
```

즉 방을 만들고 기다리는 상태, 게임 중인 상태, 끝난 상태를 구분한다.

## 중요한 점

`ROOMS` 안에 참가자나 문제를 직접 여러 개 넣는 것이 아니다.

- 참가자는 `ROOM_PARTICIPANTS`
- 문제는 `ROOM_TASKS`

에서 따로 관리한다.

---

# 8. ROOM_PARTICIPANTS

배틀방에 **어떤 유저가 참가하고 있는지** 저장하는 테이블이다.

`ROOMS`와 `USERS`를 연결해 주는 역할을 한다.

## PK

- `id` : 방 참가 기록 한 건의 고유 ID

## FK

- `room_id` : 어느 방에 참가했는지 → `ROOMS.id`
- `user_id` : 누가 참가했는지 → `USERS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `team_name` | 팀전일 경우 팀 이름 |
| `current_score` | 현재 점수 |
| `is_ready` | 게임 시작 준비 완료 여부 |

ERD에는 `team_name`에 대해 **NULL이면 개인전**이라고 적혀 있다.

예를 들어,

```text
room A
 ├─ user 1 / RED / 30점 / READY
 ├─ user 2 / RED / 20점 / READY
 ├─ user 3 / BLUE / 25점 / READY
 └─ user 4 / BLUE / 40점 / READY
```

같은 정보를 저장할 수 있다.

---

# 9. ROOM_TASKS

배틀방에서 **어떤 문제를 출제할지** 연결해 주는 테이블이다.

한 방에 문제 하나만 있는 것이 아니라 여러 문제가 들어갈 수 있기 때문에 `ROOMS`와 `TASKS` 사이에 따로 존재한다.

## PK

- `id` : 방에 문제를 배정한 기록 한 건의 고유 ID

## FK

- `room_id` : 어느 방의 문제인지 → `ROOMS.id`
- `task_id` : 실제 어떤 문제인지 → `TASKS.id`

## 그 외 컬럼

- `task_order` : 문제를 몇 번째로 출제할지 나타내는 값

예를 들면,

```text
방 A
1번째 문제 → TASK 10
2번째 문제 → TASK 25
3번째 문제 → TASK 31
```

처럼 문제 순서를 만들 수 있다.

> 참고: 현재 ERD 그림에는 `task_order` 타입이 `uuid`로 적혀 있다. 여기서는 ERD에 적힌 내용을 그대로 기록했다.

---

# 10. RANKING_GROUPS

랭킹을 **어떤 그룹 안에서 진행할지** 저장하는 테이블이다.

모든 사용자가 한 랭킹에서 경쟁하는 것이 아니라 그룹을 나눠서 랭킹을 만들 수 있다.

예를 들면,

```text
다이아
플레티넘
골드
실버
브론즈
```

같은 식이다.

## PK

- `id` : 랭킹 그룹 하나의 고유 ID

## FK

- `owner_user_id` : 이 그룹의 소유자/생성자 → `USERS.id`

## 그 외 컬럼

- `name` : 랭킹 그룹 이름

---

# 11. RANKING_PARTICIPANTS

랭킹 그룹에 **누가 들어가 있고 현재 점수가 몇 점인지** 저장하는 테이블이다.

## PK

- `id` : 랭킹 참가 기록 한 건의 고유 ID

## FK

- `group_id` : 어느 랭킹 그룹인지 → `RANKING_GROUPS.id`
- `user_id` : 어떤 유저인지 → `USERS.id`

## 그 외 컬럼

- `current_rank_score` : 현재 랭킹 점수

예를 들면,

```text
1분반
민지 1500점
철수 1350점
영희 1200점
```

같은 정보를 저장할 수 있다.

점수를 높은 순서로 정렬하면 랭킹 화면을 만들 수 있다.

---

# 12. RANK_CHALLENGES

유저가 랭킹 점수를 얻기 위해 시작한 **한 번의 랭킹 도전 전체**를 저장하는 테이블이다.

쉽게 말하면 “랭킹 시험 한 판”이라고 생각하면 된다.

## PK

- `id` : 랭킹 도전 한 번의 고유 ID

## FK

- `user_id` : 누가 도전했는지 → `USERS.id`
- `group_id` : 어느 랭킹 그룹에서 도전했는지 → `RANKING_GROUPS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `status` | 현재 도전 상태 |
| `started_at` | 도전을 시작한 시간 |
| `expires_at` | 제한 시간이 끝나는 시각 |

ERD에 적힌 상태는 다음과 같다.

```text
IN_PROGRESS
SUCCESS
FAILED
TIMEOUT
```

`expires_at`에는 단순히 “10분 남음”을 저장하는 것이 아니라 **실제로 언제 끝나는지** 시각을 저장한다.

예를 들면,

```text
started_at = 15:00
expires_at = 15:10
```

이라면 15:10 이후에는 제한 시간이 끝났다고 판단할 수 있다.

---

# 13. RANK_CHALLENGE_TASKS

한 번의 랭킹 도전 안에 **어떤 문제들이 들어 있고 각 문제를 어디까지 풀었는지** 저장하는 테이블이다.

`RANK_CHALLENGES`가 시험 한 판 전체라면, `RANK_CHALLENGE_TASKS`는 그 안에 들어 있는 문제 하나하나라고 보면 된다.

## PK

- `id` : 랭킹 도전 속 문제 한 건의 고유 ID

## FK

- `rank_challenge_id` : 어느 랭킹 도전에 포함된 문제인지 → `RANK_CHALLENGES.id`
- `task_id` : 실제 어떤 문제인지 → `TASKS.id`

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `is_passed` | 해당 문제를 통과했는지 |
| `saved_code` | 문제를 풀다가 저장한 임시 코드 |
| `task_order` | 랭킹 도전 안에서 문제 순서 |

ERD에는 `saved_code`가 **이어하기용 임시 저장 코드**라고 적혀 있다.

예를 들면,

```text
랭킹 도전 A
1번 문제 → 통과
2번 문제 → 작성 중 코드 저장
3번 문제 → 아직 안 품
```

같은 상태를 저장할 수 있다.

---

# 14. ITEMS

게임 안에 존재하는 **아이템 종류 자체**를 저장하는 테이블이다.

예를 들면,

```text
파란 소파
나무 책상
별무늬 침대
벽지
바닥
화분
```

같은 아이템의 기본 정보를 저장한다.

## PK

- `id` : 아이템 하나의 고유 ID

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `category` | 아이템 종류 |
| `name` | 아이템 이름 |
| `price` | 가격 |

## 중요한 점

`ITEMS`는 “이 유저가 무엇을 가지고 있다”를 저장하는 곳이 아니다.

`ITEMS`는 그냥 **게임에 이런 아이템이 존재한다**는 원본 정보이고, 실제 유저의 보유 아이템은 `INVENTORIES`에서 관리한다.

---

# 15. INVENTORIES

유저가 **어떤 아이템을 몇 개 가지고 있는지** 저장하는 인벤토리 테이블이다.

## PK

- `id` : 인벤토리 기록 한 건의 고유 ID

## FK

- `user_id` : 아이템을 가진 유저 → `USERS.id`
- `item_id` : 어떤 아이템인지 → `ITEMS.id`

## 그 외 컬럼

- `quantity` : 해당 아이템을 몇 개 가지고 있는지

예를 들면,

```text
user A
파란 소파 2개
화분 5개
책상 1개
```

같은 정보를 저장한다.

`ITEMS`가 아이템 도감이라면 `INVENTORIES`는 **내 가방**이라고 생각하면 쉽다.

---

# 16. PLACED_OBJECTS

유저가 가지고 있는 아이템 중 **실제로 하우스에 배치한 물건**을 저장하는 테이블이다.

## PK

- `id` : 배치된 물건 하나의 고유 ID

## FK

- `user_id` : 누구의 집에 놓인 물건인지 → `USERS.id`
- `item_id` : 어떤 아이템인지 → `ITEMS.id`

## 그 외 컬럼

- `position_data` : 가구의 위치 같은 배치 정보

타입이 `jsonb`라서 위치나 방향 같은 여러 정보를 한 번에 넣을 수 있다.

예를 들면,

```json
{
  "x": 3,
  "y": 5,
  "rotation": 90
}
```

같은 식으로 사용할 수 있다.

## INVENTORIES와 차이

```text
INVENTORIES
→ 소파를 가지고 있다.

PLACED_OBJECTS
→ 그 소파를 집의 (3, 5) 위치에 놓았다.
```

둘은 비슷해 보이지만 역할이 다르다.

---

# 17. CATS

게임에서 획득할 수 있는 **고양이 종류의 기본 정보**를 저장하는 테이블이다.

## PK

- `id` : 고양이 종류 하나의 고유 ID

## 그 외 컬럼

| 컬럼 | 의미 |
| --- | --- |
| `name` | 고양이 이름 |
| `persona` | 고양이의 성격과 말투 |
| `rarity` | 희귀도 |

예를 들면,

```text
검은 고양이
persona = 차분하고 조용함
rarity = RARE
```

처럼 고양이 원본 정보를 만들 수 있다.

## 중요한 점

`CATS`는 아직 특정 유저의 고양이가 아니다.

“게임에 이런 종류의 고양이가 있다”는 정보이고, 실제 유저가 획득한 고양이는 `USER_CATS`에 저장한다.

---

# 18. USER_CATS

유저가 **실제로 획득해서 가지고 있는 고양이**를 저장하는 테이블이다.

`USERS`와 `CATS`를 이어주는 역할을 한다.

## PK

- `id` : 유저가 소유한 고양이 기록 한 건의 고유 ID

## FK

- `user_id` : 이 고양이의 주인 → `USERS.id`
- `cat_id` : 어떤 종류의 고양이인지 → `CATS.id`

예를 들면,

```text
CATS.id = 2
→ 검은 고양이 종류

USER_CATS
→ user A가 검은 고양이를 보유함
```

처럼 연결된다.

## 왜 따로 필요한가?

같은 종류의 고양이라도 유저마다 따로 소유하고 있기 때문이다.

그리고 다음 테이블인 `CAT_MEMORIES`가 `USER_CATS.id`를 바라보기 때문에 **각 유저의 고양이마다 다른 기억**을 가질 수 있다.

---

# 19. CAT_MEMORIES

유저가 가지고 있는 특정 고양이가 **사용자와의 대화에서 기억할 내용**을 저장하는 테이블이다.

## PK

- `id` : 기억 한 건의 고유 ID

## FK

- `user_cat_id` : 어떤 유저의 어떤 고양이 기억인지 → `USER_CATS.id`

## 그 외 컬럼

- `context_summary` : 고양이가 기억할 내용을 짧게 요약한 텍스트

예를 들면,

```text
사용자는 반복문을 어려워하지만 꾸준히 공부하고 있다.
```

같은 내용을 저장해두고 다음 대화에서 활용할 수 있다.

## 왜 `cat_id`가 아니라 `user_cat_id`를 쓰나?

검은 고양이라는 같은 종류를 여러 유저가 가지고 있을 수 있기 때문이다.

```text
A 유저의 검은 고양이 기억
B 유저의 검은 고양이 기억
```

은 서로 달라야 한다.

그래서 고양이 종류인 `CATS.id`가 아니라 실제 유저가 보유한 고양이인 `USER_CATS.id`와 연결한다.

---

# 마지막으로 전체 흐름 정리

## 학습 쪽

```text
CONCEPTS
   ↓
TASKS
   ↓
TASK_ATTEMPTS
   ↓
USER_PROFICIENCY
```

- `CONCEPTS` : 무엇을 배우는지
- `TASKS` : 어떤 문제가 있는지
- `TASK_ATTEMPTS` : 유저가 어떻게 풀었는지
- `USER_PROFICIENCY` : 그래서 현재 얼마나 잘하는지

## 배틀 쪽

```text
ROOMS
 ├─ ROOM_PARTICIPANTS → 누가 참가했는지
 └─ ROOM_TASKS → 어떤 문제를 풀지
```

## 랭킹 쪽

```text
RANKING_GROUPS
 ├─ RANKING_PARTICIPANTS → 그룹의 현재 랭킹
 └─ RANK_CHALLENGES
        └─ RANK_CHALLENGE_TASKS → 실제 도전 문제
```

## 하우징 쪽

```text
ITEMS
  ↓
INVENTORIES
  ↓
PLACED_OBJECTS
```

- 아이템이 존재한다.
- 유저가 아이템을 가진다.
- 그 아이템을 집에 배치한다.

## 고양이 쪽

```text
CATS
  ↓
USER_CATS
  ↓
CAT_MEMORIES
```

- 고양이 종류가 존재한다.
- 유저가 그 고양이를 획득한다.
- 그 유저의 고양이가 대화 내용을 기억한다.
